# D-043: Fixed synthetic AI release evaluation gate

- Date: 2026-07-18
- Owners: ai_safety, qa_security, architect, operations
- Related tasks: RIT-036, RIT-083
- Evidence references: scripts/ai-release-evaluation.ts, scripts/verify-ai-release-evals.ts, tests/ai-release-evaluation.test.ts, packages/ai/test/fixtures/tarot-release-evaluation-v1.json, packages/ai/test/fixtures/tarot-release-evaluation-baseline-v1.json, .github/workflows/ci.yml

## Context

RIT-030 through RIT-034 establish strict provider-neutral input, retrieval, prompt, pre-generation,
generation/fallback, and post-generation verification boundaries. Their focused tests are strong,
but a release decision also needs one versioned registry, one fixed non-negotiable threshold policy,
and one explicit CI command. A generic pass rate or model-authored score could hide a single
critical failure, while accepting every candidate as fallback could appear safe without preserving
useful safe controls.

The current runtime is deliberately hard safe-off. RIT-036 therefore cannot truthfully measure or
approve a production provider/model, live latency, cost, or multilingual quality. It can enforce the
local deterministic and synthetic safety boundary that every future candidate must pass before the
separate owner activation gate.

## Decision

Adopt a strict English/Tarot V1 release-evaluation contract with three separately versioned pieces:
an immutable synthetic suite, a metadata-only checksum-bound safe-off baseline, a pure scorer, and
an exact test-result executor. The suite may
declare only closed case metadata, exact expected outcomes, and applicable metric families. It may
not declare thresholds, executable code, self-reported pass fields, or arbitrary provider input.
The baseline retains only the exact suite ID/version/checksum, evaluator policy, safe-off execution
mode, and zero external/paid-call counts. Actual observations are generated in memory only after
the executor receives unique passing results from the exact production-boundary tests mapped to
every required case. Neither committed baseline nor emitted summary may retain questions,
generated prose, reviewer text, prompts, journals, identity data, or other private input.

Fix release thresholds in compiled code rather than fixture data. Every registered case and safe
control must match its exact outcome; every applicable fact, schema, source, and fallback assertion
must pass; and missing cases, unexpected cases, unsafe continuations, privacy leaks, and critical
failures must all be zero. A critical case cannot be offset by aggregate performance. Safe one-card,
three-card, theme-only, and safe-negation controls remain required so an all-fallback implementation
cannot qualify.

Run `pnpm test:ai-evals` explicitly in every active Quality workflow after unit tests. The fixed
executor runs the release contract plus the existing real interpretation, curated retrieval/prompt,
pre-generation safety, generation/fallback, and post-generation verification suites, requires one
unique passed result for every compiled case mapping, generates observations in memory, and only
then scores release eligibility. The CI contract pins the exact script and workflow order and
rejects deletion, replacement, or reordering. No new CI job, secret, artifact upload, network
adapter, provider SDK, or paid call is added.

Treat a passing result only as local synthetic release-gate evidence. It is not production model
approval, language launch approval, content publication approval, latency/cost evidence, deployment
approval, or a substitute for representative human review. A future prompt, model, content, safety,
or schema change must publish a new checksum-bound candidate/baseline comparison, preserve a prior
rollback version, and retain the applicable owner gates.

## Alternatives considered

| Option                                        | Benefits                  | Costs/risks                                                                                      | Why not selected                                                |
| --------------------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------- |
| Rely only on the full unit suite              | No new contract           | No machine-readable release threshold or fixed case registry; easy to omit from release workflow | Add an explicit pinned release gate                             |
| Let the fixture define thresholds             | Easy experimentation      | A candidate can weaken its own acceptance criteria                                               | Compile zero-tolerance thresholds in the scorer                 |
| Use one aggregate/model-judge score           | Compact report            | Critical failures can be averaged away and model output can self-certify                         | Require categorical deterministic assertions and exact outcomes |
| Treat every unsafe-looking output as fallback | Maximizes apparent safety | Safe controls become unusable and regressions are hidden                                         | Require exact verified/allowed safe-control outcomes            |
| Call a live provider in CI                    | Real model samples        | Adds secrets, network nondeterminism, paid usage, and an unauthorized provider/model decision    | Keep the repository gate synthetic and safe-off                 |
| Upload detailed evaluation artifacts          | Easy centralized review   | Risks retaining private or adversarial prose and expands CI data egress                          | Keep committed evidence categorical and privacy-minimal         |

## Consequences

The repository now has one fail-closed release eligibility decision tied to exact suite bytes and
versioned AI contracts. Drift in facts, schemas, sources, fallback behavior, safety outcomes, safe
controls, privacy, continuation, or case completeness blocks the explicit CI step. The scorer has no
provider/runtime authority and cannot activate or execute model work.

The V1 matrix intentionally covers only the existing English Tarot/secular-reflection boundary.
Unicode/confusable cases are adversarial input evidence, not multilingual quality evidence. Real
provider/model evaluation, human sample review, latency/cost comparison, canary evidence, and
production rollback rehearsal remain required at the later activation/release gates.

## Validation

Focused tests parse the exact checksum-bound suite/baseline, require every deterministic
verification code and pre-generation risk category, prove the all-green release decision, and
mutate critical outcome, fact, schema, source, fallback, privacy, continuation, safe-control,
case-completeness, checksum, self-report, executable-field, and paid/network boundaries. The
explicit executor binds all 34 cases to 145 passing assertions in the six exact production-boundary
and contract files before it can emit an eligible result.
The CI-contract mutation suite removes, changes, and reorders the release command and must fail.

## Rollout and rollback

No production provider, reviewer, model, SDK, key, network request, paid inference, content/safety
activation, database, payment, deployment, or public launch changes. Rollback removes the explicit
Quality step, script/contract entries, pure scorer, synthetic fixtures, and their tests. There is no
data migration or external state to reverse. After a future approved candidate is active, rollback
must select the previously preserved approved version rather than weakening this gate.
