# D-046: Split exact interpretation reporting from history and paid regeneration

- Date: 2026-07-23
- Owners: owner, product, architect, backend, qa_security, ai_safety, payments_risk
- Related tasks: RIT-037
- Evidence references: docs/reports/RITUVIA_PHASE_0_REALITY_AUDIT_2026-07-23.md, docs/codex/rituvia-production-2026-07-23/04_DOMAIN_MODEL_AND_DATABASE.md, docs/codex/rituvia-production-2026-07-23/08_AI_SAFETY_AND_EVALS.md, docs/codex/rituvia-production-2026-07-23/09_PAYMENTS_WALLET_AND_CREDITS.md

## Context

The pre-pack RIT-037 title combined interpretation regeneration, reporting, and version history.
The production source-of-truth pack now permits AI only for explicit paid Deep Readings and requires
one atomic Credit reservation/generation/persistence/consumption flow with exact release on every
failed path. The repository has strong append-only interpretation and verification evidence, but
it does not yet have the production Credit reservation/projection model. Extending the old free
safe-off POST boundary to create another interpretation would therefore encode the wrong commercial
and transaction authority. The current persistence also constrains `generation_number` to one and
offers no history/list contract, so expanding lineage now would prematurely freeze a second model.

## Decision

Re-scope RIT-037 to the non-spending vertical slice that is independently correct now: an
owner-scoped categorical report bound to one exact, immutable, displayable interpretation result.
Reuse and adapt the existing reading report route and `Interpretation`,
`InterpretationVerification`, and `ReadingReport` architecture. Preserve the existing
reading/position request contract and do not create a parallel reporting service or
`deep_readings` table.

RIT-037 must not add history/list behavior, permit `generationNumber > 1`, add a
regeneration/start route, or create a code path that can perform another provider attempt as a new
result. Paid Deep Reading creation, deliberate regeneration, and version lineage will be scheduled
as a separate task only after the server-authoritative Credit ledger, reservation, projection,
allocation, consumption, release, expiry, reversal, and concurrency contracts are accepted. An
internal provider retry remains the same business request and reservation; a deliberate user rerun
is a new quoted and reserved Deep Reading that may link to, but never overwrite, the prior result.

## Alternatives considered

| Option | Benefits | Costs/risks | Why not selected |
| --- | --- | --- | --- |
| Implement all original RIT-037 behavior now | Preserves the old title | Allows unreserved or duplicated paid work and conflicts with the new Deep Reading contract | Credits authority must exist first |
| Build history without regeneration | Adds read-only version UI earlier | Current schema fixes generation to one and future lineage belongs to paid Deep Readings | Defer history with regeneration |
| Block all of RIT-037 | Avoids premature schema work | Delays useful exact-result reporting that does not spend Credits | Split the independently safe slice |
| Copy the pack's `deep_readings` SQL table | Fast apparent schema parity | Duplicates existing interpretation evidence and bypasses repository constraints | Adapt the existing aggregate |

## Consequences

RIT-037 becomes the single active task after RIT-159. Its exact-result report implementation can
proceed without provider, payment, or legal activation, but it cannot be marked Done if it
introduces history, lineage, or a start/regeneration capability. The backlog must later add an
explicit Credits/Deep Reading task before any paid generation, regeneration, or version history
work begins.

## Validation

Validation requires exact owner/reading scoping, durable displayable-result eligibility,
categorical no-free-text reporting, inherited expiry, append-only persistence, idempotency and race
evidence, logical restore, least privilege, private-resource indistinguishability, backward request
compatibility, and a negative proof that no new route or runtime can start generation or expose
history.

## Rollout and rollback

Rollout begins with task-contract and design evidence, followed by the smallest expand-only
interpretation-target report slice. Rollback disables the new request arm and changes the
expand-only schema through a forward migration while preserving immutable evidence. It does not
authorize destructive data deletion, provider activation, Credit mutation, production deployment,
or public launch.

## Sources and approvals

or public launch.
