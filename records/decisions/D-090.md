# D-090: Public AGPL repository with enforced main protection

- Date: 2026-07-30
- Owners: owner, operations, qa_security, architect
- Related tasks: OWN-008, RIT-004, RIT-008
- Evidence references: `LICENSE`; `.github/workflows/ci.yml`; `.github/workflows/README.md`;
  GitHub Actions run `30494018585`; GitHub repository and branch-protection API responses

## Context

The complete RITUVIA deliverable is already licensed `AGPL-3.0-only`, and the owner previously
approved publication of exact deployed Corresponding Source. The GitHub repository remained
private while RIT-004 established hosted CI. GitHub Actions passed, but GitHub Free rejected
private-repository branch protection with HTTP 403.

The owner explicitly approved making the repository public and disclosing its complete source
history on 2026-07-30 so the existing CI contract can be enforced without GitHub Pro. Repository
secret scans and the three hosted jobs passed before this visibility change. Public source
disclosure is not a production product launch.

## Decision

Publish `CPTM511/RITUVIA` as a public GitHub repository under its existing GNU AGPLv3 license.

Protect `main` with this exact baseline:

- require strict, up-to-date `Quality`, `PostgreSQL integration`, and `Security scans`;
- apply protection to administrators;
- require changes through a pull request;
- require zero third-party approvals while the repository has one maintainer;
- require linear history and resolution of review conversations;
- deny force pushes and branch deletion; and
- keep the branch writable through compliant merges rather than locking it.

Keep production deployment, DNS, product indexing, provider activation, customer data, production
secrets, and public product launch behind their existing independent owner gates.

## Alternatives considered

| Option                              | Benefits                            | Costs/risks                                      | Decision |
| ----------------------------------- | ----------------------------------- | ------------------------------------------------ | -------- |
| Upgrade to GitHub Pro               | Retains private source              | Adds recurring cost                              | Rejected |
| Keep private with manual discipline | No cost or disclosure               | CI and workflow protection remain bypassable     | Rejected |
| Public repository without protection | Free source access                 | Does not close the governance requirement        | Rejected |
| Public AGPL repository plus protection | Free enforceable governance       | Complete Git history becomes permanently public  | Selected |

## Consequences

Anyone may read, clone, mirror, and fork the repository under the license. Returning the GitHub
setting to private cannot recall copies already obtained. The repository homepage intentionally
has no production URL until a separately approved domain and deployment exist.

The zero-approval pull-request rule avoids deadlocking the sole maintainer but is not independent
human review. Required CI, administrator enforcement, resolved conversations, linear history, and
force-push/deletion denial remain the mandatory automated and repository controls.

## Validation

GitHub reports repository visibility `PUBLIC`, recognizes the AGPL license, and exposes current
product/technology topics. The branch-protection API reports the three exact required contexts with
strict mode, administrator enforcement, pull-request requirement, linear history, resolved
conversations, no force pushes, and no deletion. Hosted run `30494018585` passes all three required
jobs on the current protected candidate tree.

## Rollout and rollback

Visibility was changed only after a clean worktree, a successful secret/security job, and a
three-job passing hosted run. No deployment environment, production secret, customer data, DNS,
provider, or production database was created or changed.

Visibility may be changed back only through a new owner decision acknowledging that prior
disclosure cannot be reversed. Any protection change must preserve or strengthen the release gates;
emergency changes require a recorded reason and subsequent restoration evidence.
