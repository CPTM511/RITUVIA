# D-068: Privacy-safe astrology location-search HTTP contract

- Date: 2026-07-26
- Owners: owner, privacy, backend, qa_security
- Related tasks: OWN-014, RIT-092, RIT-094
- Evidence references: owner reply `同意所有的内容，批准所有内容，并开始下一步`; D-067

## Context

D-067 identified a conflict between the historical API inventory's
`GET /api/v1/locations/search` and the repository rule that private birth-location queries cannot
enter URLs, browser history, access logs, analytics, or shared caches. OWN-014 requested an explicit
owner decision before any location-search UI or route could be implemented.

## Decision

Approve the D-067 recommendation:

- use authenticated `POST /api/v1/locations/search` with a bounded versioned JSON body;
- require exact same-origin evidence and a session-bound CSRF token;
- apply a dedicated database-atomic or equivalently durable bounded rate limit before provider
  work;
- return `Cache-Control: no-store` and never use a browser, CDN, proxy, or shared response cache;
- exclude the raw query from URLs, access/error logs, analytics, traces, metrics, metadata, and
  durable storage;
- use only the D-067 bounded private process-memory HMAC-keyed provider cache;
- return stable redacted errors and no provider internals; and
- keep the route absent until its authentication, authorization, rate-limit, privacy-canary,
  timeout, and abuse tests pass.

This approval authorizes the contract, not production deployment, a real GeoNames snapshot,
browser location permission, analytics, a paid vendor, or public launch.

## Alternatives considered

| Option                              | Benefits                            | Costs/risks                                      | Decision |
| ----------------------------------- | ----------------------------------- | ------------------------------------------------ | -------- |
| Authenticated same-origin POST      | Keeps the private query out of URLs | Requires CSRF, rate-limit, and no-store controls | Selected |
| Historical GET query                | Matches the earlier API inventory   | Leaks sensitive location into URL surfaces       | Rejected |
| Browser geolocation                 | Reduces typing                      | Adds permission, precision, and privacy risk     | Rejected |
| Unauthenticated public search proxy | Simple integration                  | Enables abuse and exposes private query metadata | Rejected |

## Consequences

OWN-014 is complete. RIT-094 no longer has an owner-decision blocker, but its remaining technical
dependencies still apply. RIT-092 may proceed without implementing this search route; it accepts
only an opaque selected location and exact D-067 resolution evidence.

The historical GET inventory remains documented only as rejected history. A future implementation
must use the approved POST contract or obtain another explicit owner decision.

## Validation

The future route gate must prove authentication, same-origin and session-CSRF enforcement,
request/body bounds, rate limiting, no-store responses, raw-query canary isolation, no shared
cache, provider timeout/cancellation, stable errors, and no cross-account birth-profile access.

## Rollout and rollback

There is no runtime rollout. Rollback reopens OWN-014 and blocks RIT-094 before route/UI work. No
route, migration, provider call, retained query, deployment, or customer behavior exists to
reverse in this decision-only change.
