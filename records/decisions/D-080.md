# D-080: Git-authored editorial registry with fail-closed publication authority

- Date: 2026-07-28
- Owners: product, content, architect, growth_seo, localization, qa_security
- Related tasks: RIT-110, RIT-112, RIT-113
- Evidence references: `content/editorial/manifest.v1.json`;
  `packages/content/src/repository.ts`; `scripts/verify-editorial-content.ts`

## Context

RITUVIA already has strict domain-specific content parsers for Tarot, numerology, astrology,
rituals, and localization, but no shared registry binds heterogeneous assets to one source,
rights, claims, review, version, localization, deprecation, preview, and publication workflow.
Adding a database, CMS, admin API, or public route before concurrent editorial operations exist
would introduce authorization, migration, audit, privacy, and operational complexity without
improving the current Git-reviewed workflow.

Self-declared approval fields and well-formed checksums are not sufficient publication authority.
A modified content file can declare a new digest or approval string, and a preview artifact must
never enter public routes, sitemaps, AI retrieval, or search indexes merely because it parses.

## Decision

Keep authored editorial assets and their shared registry in Git. Introduce pure
`@rituvia/content` contracts that parse exact immutable metadata, source and claim bindings,
rights and expiry, author/reviewer separation, review freshness, BCP 47 locale, source-bound
translation records, lifecycle provenance, reciprocal acyclic supersession, and unique active
canonical-path ownership.

Register only existing owner-approved English numerology and Western natal education catalogs in
the first repository version. Their domain-specific parsers remain authoritative for body-level
semantics; the shared registry adds a prerequisite cross-content governance boundary rather than
replacing those stricter contracts.

Use an explicit irreversible editorial status graph. Corrections create a new retained version;
published records can become deprecated only through a reciprocal replacement chain and cannot
return to draft or approved state.

Preview authorization requires the exact registered artifact digest and a reviewed editor, owner,
or reviewer role. It always returns `private, no-store` and
`noindex, nofollow, noarchive`.

Publication authorization requires:

- exact artifact checksum and a structurally publishable state;
- a process-owned record-authority fingerprint binding approval, reviewer, locale, rights,
  publication policy, safety review, and artifact digest;
- a process-owned source-authority fingerprint binding locator, version, reviewer, rights,
  allowed uses, expiry, and claim review;
- an explicitly approved locale;
- unexpired content, source, and rights review;
- public-display, commercial, and, when indexable, SEO rights;
- approved exact-source localization binding;
- non-deprecated content and complete source/claim evidence.

The repository verifier reads only bounded `content/**` JSON paths, rejects symlinks and resolved
paths outside `content/`, pins the complete manifest digest, reparses every artifact, verifies
record/source authority fingerprints, and invokes both authorization boundaries. English is the
only trusted locale. Review and rights expiry are compared with the current UTC date on every
verification run. No registry entry itself activates a route, sitemap, AI retrieval, deployment,
or production index.

## Alternatives considered

| Option                                                 | Benefits                             | Costs/risks                                                             | Decision |
| ------------------------------------------------------ | ------------------------------------ | ----------------------------------------------------------------------- | -------- |
| Continue only with domain-specific parsers             | No new package                       | No shared lifecycle, source, rights, or publication view                | Rejected |
| Add a database-backed CMS and admin API                | Concurrent editing and workflow UI   | Premature auth, audit, migration, and operations surface                | Rejected |
| Trust manifest approval fields and checksums           | Smallest implementation              | Modified files could mint their own authority                           | Rejected |
| Git registry plus pure contracts and process authority | Auditable, deterministic, reversible | Requires explicit adapters and later migration if editing scale changes | Selected |

## Consequences

New content families can adopt one shared envelope while preserving stricter domain validators.
Publication consumers must verify the exact branded authorization result and must not accept raw
manifest objects. Changing an artifact, source, claim, approval, locale, rights record, review
window, or replacement chain fails closed until the registry and trusted authority are reviewed
together.

This task does not provide near-duplicate or search-intent quality assessment owned by RIT-113,
structured-data publication owned by RIT-114, a content-report queue owned by RIT-125, or a CMS.
Those tasks may consume the registry without weakening it.

## Validation

Focused tests cover valid preview and publication, deterministic findings, checksum and authority
drift, locale denial, expired reviews, untrusted sources, unsafe paths, unknown fields,
author/reviewer conflicts, cross-lineage canonical collisions, exact translation binding,
localized-review denial, reciprocal version replacement, archived preview denial,
reference-only rights, and forward-only status transitions.

The repository verifier independently hashes and parses every registered artifact, rejects
symlinks in the content root, parent directories, manifest, or artifact, rejects out-of-root
resolution, advances review/rights expiry with the current UTC date, and checks the process-owned
English record/source authority fingerprints before publication authorization.

## Rollout and rollback

No database, migration, public route, locale activation, sitemap change, AI retrieval, provider,
payment, deployment, DNS, or public launch is involved. Roll forward by adding a reviewed artifact
and its exact registry evidence, then separately wiring an authorized consumer. Roll back by
removing the new package, manifest, verifier, and registrations; existing domain-specific content
continues to function independently.
