# D-092: Separate payment ingestion from source-linked fulfillment

- Date: 2026-07-30
- Owners: owner, payments_risk, security, backend
- Related tasks: RIT-065, RIT-066
- Evidence references: `packages/db/src/commercial-fulfillment-persistence.ts`;
  `packages/db/prisma/migrations/202607300002_commercial_fulfillment/migration.sql`;
  `tests/verify-commercial-fulfillment.ts`

## Context

The signed webhook role must remain unable to grant customer value. RIT-065 also needs truthful
dispute behavior: a dispute freezes unspent purchased Credits, while a refund creates a linked
reversal. Treating both events as final reversals would overstate refund completion and make later
reconciliation ambiguous.

## Decision

Use a distinct `rituvia_payment_fulfillment` database identity and DSN. It may read only the
commercial order/item/outbox and Credit source facts required for fulfillment, append grant,
restriction, and reversal evidence, update bounded projection/fulfillment/outbox columns, and
cannot read provider event payload evidence or private journal content.

Process one order's outbox versions in order under serializable transactions. Reread the current
order state rather than trusting a stale outbox snapshot. Grant each verified Credit pack through
one source ledger entry. On dispute, move only unspent source value into an append-only hold and a
nonspendable projection bucket. On refund, convert active holds and reverse remaining available
source value. Record consumed or reserved source value as `review_required`; never create a
negative balance or silently erase the shortfall.

## Alternatives considered

| Option                                     | Benefit                            | Risk                                               | Decision |
| ------------------------------------------ | ---------------------------------- | -------------------------------------------------- | -------- |
| Let the webhook role fulfill               | Fewer credentials                  | Ingestion compromise can issue value               | Rejected |
| Reverse all value on dispute               | Simple projection                  | Misstates refund status and loses freeze semantics | Rejected |
| Permit a negative purchased balance        | Preserves nominal debt             | Breaks Credit and restoration invariants           | Rejected |
| Dedicated role with hold/reversal evidence | Least privilege and truthful state | Adds one DSN and projection                        | Selected |

## Consequences

Webhook compromise cannot lease or complete fulfillment work. Worker compromise remains bounded
to the exact fulfillment tables/columns and cannot mutate orders, payment events, existing ledger
facts, or private content. Purchase restoration is owner-scoped and excludes held Credits from the
spendable total. Privacy export includes v2 order, Credit, restriction, fulfillment, and
entitlement evidence.

This decision does not activate Stripe Live Mode, initiate refunds, ingest currently unsupported
Stripe dispute/refund event types, add subscriptions or paid entitlements, reconcile provider
payouts, run a production migration, deploy, or launch.

## Validation

Focused domain/worker/Web tests must pass with exact result shapes. The isolated PostgreSQL gate
must prove concurrent exactly-once grant, current-order convergence, dispute hold, refund
conversion, consumed/reserved shortfall, stale-token denial, retry, dead letter, owner isolation,
role denial, and nonnegative restoration. Migration, configuration-boundary, privacy-export,
record, generated-evidence, architecture, type, formatting, lint, and secret checks must pass.

## Rollout and rollback

Rollout requires the additive migration, the dedicated secret DSN, focused database gates, and
worker activation in an approved non-production environment. Rollback stops the fulfillment
consumer and removes its runtime DSN. Existing append-only payment, grant, hold, reversal, and
shortfall evidence remains intact; rollback never deletes records or invents compensating value.
