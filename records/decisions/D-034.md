# D-034: Private one-card presentation and idempotent reveal boundary

- Date: 2026-07-17
- Owners: frontend, product, qa_security, ai_safety, architect
- Related tasks: RIT-025, RIT-026, RIT-027, RIT-028, RIT-035
- Evidence references: apps/web/app/[locale]/tarot/one-card/page.tsx, apps/web/app/_components/tarot-one-card-flow.tsx, apps/web/app/_components/tarot-one-card-machine.ts, apps/web/app/_components/tarot-one-card-transport.ts, apps/web/app/_contracts/tarot-reading-response.ts, apps/web/server/tarot-reading-presentation.ts, apps/web/proxy.ts

## Context

RIT-024 can create and replay owner-bound deterministic facts, but facts alone do not give an
anonymous user the useful perspective, limitation, reflection question, and small action required
by the one-card product outcome. The browser cannot select or compose interpretive content, and the
only repository catalog remains synthetic and publication-ineligible. A visible implementation must
therefore prove the complete interaction without weakening the existing runtime gate.

The interaction also crosses two independently idempotent commands: anonymous-session creation and
reading creation. Treating reveal or retry as a new draw would make network recovery change the
result and create a compulsive reroll path.

## Decision

Return `tarot-reading-response.v2` with verified deterministic facts plus one strict
`tarot-reading-presentation.v1` projection. The server resolves the exact approved catalog, card,
orientation, spread position, and selected theme and projects only the reviewed card title,
position title, theme invitation, core themes, constructive possibility, tension, explicit
limitation, reflection question, and small action. The client parses exact keys, bounded normalized
text, versions, one-card cardinality, and fact-to-presentation identity before rendering. Internal
catalog audit, rights, approval, entropy, digest, owner, session, and raw-input data stay server-side.

Use a private noindex/no-store English page at `/en/tarot/one-card`. It sends only one of the ten
reviewed theme codes and has no raw-question field, persistence, analytics event, AI generation,
payment, sharing, report, or redraw control. The result remains in the page and identifies that its
content is reviewed canonical material rather than AI output.

Generate separate Web Crypto UUID V4 idempotency keys for session and reading commands. A new
attempt creates both once. Manual network/service retry reuses the same pair; no retry is automatic.
An idempotency conflict offers only an explicit start-over that clears the saved operation. The
server fixes the card before the reveal button appears, and reveal changes only presentation state
without network access or another draw.

Gate the exact page and create/read APIs with the same independently approved tarot availability.
Normal runtime remains an empty private 404 while no eligible production catalog exists. Browser
success testing may intercept the static production artifact with an isolated deterministic
response, but must not modify runtime composition or mark the placeholder publishable.

## Alternatives considered

| Option                                     | Benefits                      | Costs/risks                                                     | Why not selected                                         |
| ------------------------------------------ | ----------------------------- | --------------------------------------------------------------- | -------------------------------------------------------- |
| Render only card IDs and orientation       | Small response                | Not a useful reflection outcome                                 | RIT-025 requires reviewed meaning and an action          |
| Let the client look up catalog text        | Less response projection code | Ships unpublished content and trusts client-selected references | Content authority and publication checks are server-side |
| Derive both commands from one retry key    | Fewer client values           | Conflates two idempotency domains                               | Session and reading commands must remain independent     |
| Draw when the user presses reveal          | Simpler visual sequence       | Reveal becomes a reroll/network boundary                        | The result must already be fixed                         |
| Activate the synthetic placeholder locally | Direct end-to-end success     | Creates an accidental publication path                          | Isolated interception proves UI without activation       |

## Consequences

An anonymous mobile user can choose one bounded theme, create a server-authoritative one-card draw,
explicitly reveal it, and leave with a transparent limitation, reflection question, and small
action. The client cannot request a card/orientation, accept extra response data, or silently redraw
after a transport failure. The response schema advances before public launch and the build gains a
second private production artifact and accessibility inventory entry.

The page is not publicly useful in normal runtime until an independently eligible production
catalog is approved and configured. Three-card semantics, calm redraw/report controls, broader E2E
coverage, AI interpretation, intention/ritual continuation, and production activation remain later
tasks.

## Validation

Unit and contract tests cover the strict V2 parser, fact/presentation matching, all ten themes,
state transitions, separate/reused idempotency keys, exact theme-only transport, failure mapping,
SSR/no-JavaScript behavior, proxy gate, metadata, routing, messages, and HTTP responses. The full
type, lint, architecture, formatting, unit, production build, size, accessibility, configuration,
record, generated-evidence, and secret gates remain required.

Production-artifact Chromium checks cover keyboard order, radio behavior, 320px reflow, expanded
text, RTL, dark, reduced motion, forced colors, no JavaScript, axe, local-only requests, explicit
reveal, and zero console warnings. The successful draw path uses only a browser-local intercepted
eligible response; a direct request to the same running build must remain an empty 404.

## Rollout and rollback

No catalog publication, production activation, deployment, domain change, or public launch is
authorized. Roll back the page, presentation projection, V2 response parser, and proxy allowlist
while retaining the RIT-024 safe-off API and facts. If a V2 response is ever stored or consumed in
an environment of record, retain its parser/projection compatibility and disable new creation
through the gate rather than rewriting historical facts.
