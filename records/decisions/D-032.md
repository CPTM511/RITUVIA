# D-032: Versioned unbiased tarot draw and internal audit boundary

- Date: 2026-07-17
- Owners: backend, architect, qa_security, product
- Related tasks: RIT-023, RIT-024, RIT-030, RIT-031
- Evidence references: packages/divination/src/tarot-draw.ts, packages/divination/test/tarot-draw.test.ts, packages/divination/test/fixtures/tarot-draw-v1.json, scripts/verify-workspace-build.mjs

## Context

RIT-023 must turn a validated exact-version tarot catalog into ordered draw facts without allowing
the client or AI to choose cards. The package boundary forbids Node, database, network, environment,
analytics, UI, and AI dependencies, so it can define and verify the algorithm and a caller-injected
entropy contract but cannot prove which production entropy adapter or database transaction a future
application service uses.

Reproducibility is not idempotency. Fixed bytes must reproduce an algorithm vector, while a retried
operation must return the already persisted execution without consuming new entropy. Durable
owner-scoped uniqueness, concurrent winner selection, HTTP conflict mapping, and persistence belong
to RIT-024. Combining those concerns here would make the calculation engine impure and preempt the
reading service and database model.

Internal audit fields also require a stricter boundary than card facts. Idempotency-key digests,
canonical-request digests, entropy commitments, and consumption counts are useful to a server-side
transaction but are not interpretation input, analytics, or public response data. A plain request
digest must never cover raw question text because low-entropy private text could be guessed.

## Decision

Freeze `tarot-draw-request.v1`, `tarot-draw-facts.v1`, `tarot-draw-execution.v1`,
`tarot-draw-rules.v1`, engine `1.0.0`, and algorithm
`partial-fisher-yates-rejection-uint8.v1` as independent exact contracts. V1 supports only
`without_replacement`, `upright_only`, and `upright_and_reversed`. A future replacement rule or
changed byte-consumption sequence requires a new rules/algorithm version rather than a mutable
switch.

Canonicalize deck cards and spread positions by their validated contiguous order. For each position,
perform one partial Fisher–Yates selection over the remaining suffix. Sample each bound from one
byte using rejection sampling: accept only values below `256 - (256 % bound)` and then apply the
remainder. A singleton bound consumes no selection byte. After selecting each card, sample its
orientation when the rule permits both orientations; `upright_only` consumes no orientation byte.
This card-then-orientation interleaving is part of V1 compatibility. A successful sample permits at
most 255 rejected bytes, and a 256th consecutive rejection fails closed rather than looping.

Require an injected `TarotCSPRNG` with exact one-byte reads and a SHA-256-shaped audit commitment.
The engine provides no default RNG, client seed, `Math.random`, deterministic production helper, or
raw entropy output. Test/replay code may inject fixed bytes. The commitment callback receives the
frozen public facts only after selection so a future adapter can bind the exact outcome. RIT-024
must provide a server-only operating-system CSPRNG adapter and a keyed, domain-separated commitment
covering the non-sensitive canonical request, facts, entropy counts, and exact engine/algorithm
versions. Raw key material, nonce, and entropy bytes must not be persisted or logged. The
provider-supplied commitment is correlation/integrity evidence, not proof that a server acted
fairly.

Treat `TarotDrawRequestV1` and `TarotDrawExecutionV1` as server-internal contracts, not HTTP DTOs.
The request contains only exact catalog/deck/spread references, rules, orientation policy, and
server-derived digests; it contains no question, theme free text, card selection, orientation result,
seed, entropy, or previous execution. RIT-024 must derive the idempotency and canonical-request
digests server-side, scope them to the owner and operation, exclude sensitive text, and never accept
client-supplied digest values as authority.

On an existing execution, require a caller-injected `TarotExecutionVerifierV1` before replay. The
core first parses a frozen snapshot, then the verifier must authenticate the complete execution
envelope; missing, false, or throwing verification fails closed. Exact key digest, request digest,
references, rules, orientation policy, position order, card membership/uniqueness, and
mathematically possible entropy counts must also validate. A match returns the frozen historical
execution without reading entropy; any mismatch fails with a stable conflict or validation code.
With no existing execution, a different key creates a new operation, though naturally it may draw
the same cards. RIT-024 must implement the verifier with the same server-only keyed commitment
scheme; a test equality verifier is compatibility evidence only.

Keep `TarotDrawFactsV1` mechanically separate from the internal execution audit. Only the explicit
`projectTarotDrawFactsV1` result may cross into a future API, AI fact bundle, or analytics-safe
layer, and that projection also requires successful execution verification. It contains exact
provenance, positions, cards, and orientations but no digest, commitment, entropy count, private
text, or interpretation prose.

Do not add a database migration, route, UI, content activation, provider, or logging path in RIT-023.
The RIT-022 synthetic catalog remains internal-validation-only and mechanically ineligible for
publication regardless of whether its draw vectors pass.

## Alternatives considered

| Option | Benefits | Costs/risks | Why not selected |
| --- | --- | --- | --- |
| Seed randomness from the idempotency key | Simple deterministic retries | Client-predictable and rerollable; conflates replay with entropy | Violates server-authoritative CSPRNG requirements |
| Use `byte % bound` | Minimal code | Biased for non-power-of-two bounds | Violates deterministic correctness |
| Shuffle with `Array.sort` and random comparator | Short implementation | Biased, engine-dependent, non-replayable | Cannot support fixed historical vectors |
| Put PostgreSQL idempotency in the engine | Concurrent durability now | Breaks the pure package and duplicates RIT-024 | Persistence belongs to the application service |
| Return one combined public result | Fewer types | Leaks internal correlation and entropy audit fields | Explicit projection is safer and testable |
| Store raw entropy for audit | Exact replay evidence | Enables result reconstruction/manipulation and secret leakage | Store only a bounded commitment |

## Consequences

The repository gains deterministic, reviewable byte-to-draw behavior and a stable replay contract
without pretending a production server adapter or concurrent database service exists. Historical V1
executions remain parseable and replayable after later engine versions; they are never recalculated
in place.

RIT-024 must still implement the server-only OS CSPRNG adapter, keyed execution verifier, canonical
server-derived digests, transactional owner-scoped idempotency, immutable persistence, concurrency
tests, limits, HTTP validation, and the safe public facts projection. It must load an eligible
canonical catalog rather than accepting one from a client. Production fairness cannot be inferred
from a commitment alone.

No user-facing copy, private data, analytics event, payment behavior, migration, runtime activation,
or deployment is introduced.

## Validation

Permanent V1 fixtures pin request, fixed test bytes, engine/rules/algorithm versions, full internal
execution, public fact projection, byte consumption, and rejection counts. Tests cover exact parsing,
deep freezing, input non-mutation, client-field rejection, all supported sampling bounds, rejection
limits, one/three-card draws, orientation balance, uniqueness, canonical position order, shuffled
source order, exact references, accessor/Proxy snapshot safety, malformed entropy, authenticated
history, damaged execution rejection, idempotent replay, conflict, and internal-field exclusion from
verified public facts. Architecture and build gates prove the pure dependency boundary and compiled
runtime exports.

## Rollout and rollback

There is no runtime consumer or retained production execution. Roll back by removing the draw
module, fixture, tests, and build assertions. Once executions are persisted, retain the V1 parser and
runner; changing new requests to another version must not rewrite historical facts.
