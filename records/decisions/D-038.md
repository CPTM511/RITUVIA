# D-038: Exact published-content retrieval and checksummed prompt artifacts

- Date: 2026-07-18
- Owners: ai_safety, architect, content, qa_security, privacy
- Related tasks: RIT-031, RIT-032, RIT-033, RIT-034, RIT-110
- Evidence references: packages/ai/src/retrieval.ts, packages/ai/src/prompt.ts, packages/ai/test/retrieval-prompt.test.ts, scripts/verify-workspace-build.mjs

## Context

The provider-neutral RIT-030 contract can name approved content and a prompt, but names and
well-formed checksums do not prove that the referenced material came from an approved server-owned
mapping. The Tarot catalog contract can establish structural publication eligibility, exact
references, and rights metadata, but D-031 explicitly does not authenticate an external approval
reference. The AI safety specification also prohibits unpublished or cross-tradition retrieval,
while the general publication assessor treats both `approved` and `published` editorial states as
structurally eligible.

RIT-031 must close those trust gaps without selecting a provider, calling a model, adding a content
service, or preempting RIT-033 persistence and generation orchestration.

## Decision

Keep retrieval and prompt assembly inside the pure `@rituvia/ai` package. It has no file, database,
environment, network, provider SDK, Node built-in, or default cryptographic implementation. A
server composition must inject two independent fail-closed checks: SHA-256 verification of the
canonical parsed JSON snapshot, and authorization against a server-owned exact allowlist. A
checksum calculation alone is not approval. The authority value includes the exact catalog or
prompt registration, locale, tradition, policy/schema references, and approval reference; false,
throwing, or missing verifiers reject the operation.

For Tarot V1 retrieval, parse bounded JSON, verify the exact catalog snapshot, re-run dated
publication eligibility, require AI-retrieval permission, and require `published` status for the
catalog and every selected deck, spread, card-orientation content unit, and source. This resolves
the `approved` versus `published` ambiguity conservatively: unpublished content never enters a
provider prompt. Keep the full publication gate, including rights and artwork prerequisites, until
a separately reviewed AI-only eligibility policy exists. Do not resolve `latest`, fall back across
locales, versions, orientations, themes, or traditions, or merge content from another catalog.

Bind every retrieved excerpt to the public deterministic draw's exact catalog, deck, spread,
position, card, orientation, reading type, locale, stable tradition identifier, and selected theme.
Return only bounded selected excerpts, deterministic content/source references, dated approval and
rights provenance, and the canonical catalog-snapshot checksum scope. The RIT-030 content checksum
therefore means the checksum of the exact catalog snapshot that contains the content unit; multiple
content units from one snapshot can intentionally share it. The provenance records that scope
explicitly rather than implying a per-field digest.

Prompt definitions are bounded, exact-version JSON artifacts with independent reviewer evidence,
evaluation version, locale, tradition, output-schema reference, server-owned allowlist
authorization, and a canonical checksum. Every substantive system and tone instruction, including
the mandatory safety rules, is inside the checksummed definition. Assembly adds no free-form
template language. It accepts only runtime-issued parsed input, retrieved content, and approved
prompt values; requires exact facts/content/prompt/locale/theme/tone/reading-type binding; and puts
instructions in one system message while serializing facts and excerpts as JSON data in one user
message. Curated data is never interpolated into the system message.

Retrieved bundles, approved prompt definitions, and final prompt assemblies use runtime identity
guards so structural casts or clones cannot carry trust. The final assembly contains recursively
immutable, JSON-serializable provenance with the content, deterministic engine, prompt, output
schema, retrieval policy, assembly policy, safety policy, locale, tradition, theme, and tone
versions required for later persistence and replay. RIT-031 produces this persistable evidence;
RIT-033 remains responsible for database persistence, provider-request construction, timeout,
retry, fallback, and redacted telemetry, and it must accept only a runtime-issued prompt artifact.

## Alternatives considered

| Option | Benefits | Costs/risks | Why not selected |
| --- | --- | --- | --- |
| Trust catalog and prompt self-declared approval fields | Smallest interface | Any caller can pair modified bytes with a new checksum and approval string | External allowlist authorization is a separate trust requirement |
| Allow structurally `approved` content in internal prompts | Faster editorial preview | Unpublished material could reach a provider despite the safety specification | RIT-031 uses the safer published-only rule |
| Hash each excerpt independently | Fine-grained integrity | New canonicalization and registry semantics without a current consumer | Exact catalog-snapshot scope is sufficient and explicit |
| Add a vector database or retrieval service | Flexible search | Premature infrastructure, fuzzy matching, and new privacy/operations risks | Exact deterministic lookup satisfies Tarot V1 |
| Concatenate retrieved prose into the system message | Simple prompt text | Curated or compromised content can alter the instruction channel | Keep instructions and JSON data in separate roles |

## Consequences

The placeholder catalog remains mechanically unavailable even when its JSON parses and its digest
is correct. A future production composition must supply exact approved catalog and prompt mappings;
there is no permissive default. Prompt changes to safety or tone text require new checksummed prompt
evidence, while assembly serialization changes require a new assembly-policy version. Provenance
can be persisted without storing excerpts or messages, but no database write occurs in this slice.

The first implementation remains Tarot-only and English-capable by contract; it does not approve
English launch content, another locale, a historical or regional tradition, a provider, a model, or
paid usage. Blacklist checks reject obvious instruction payloads as defense in depth, while the
primary injection boundary is the fixed message-role split plus post-generation verification in
RIT-034.

## Validation

Focused tests cover a test-only published catalog, exact retrieval and prompt assembly, real
SHA-256 verification, external authority denial, the permanently ineligible placeholder, draft
and rights failures, version/approval/locale/tradition/theme/orientation/reading-type drift,
prompt-checksum drift, forged trusted values, injection delimiters, UTF-8 bounds, deterministic
ordering, recursive immutability, provenance round-trip, and private-data canaries. Architecture
and compiled-workspace gates enforce the package's pure provider-neutral boundary and required
artifacts.

## Rollout and rollback

No runtime route, provider, content corpus, database, migration, credential, payment, or deployment
is activated. Rollback removes the unused retrieval/prompt modules and their tests/build evidence;
there is no external side effect or stored data cleanup.
