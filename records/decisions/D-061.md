# D-061: Additive v2 commercial transactions and append-only Credits

- Date: 2026-07-25
- Owners: owner, backend, payments_risk, security
- Related tasks: RIT-062
- Evidence references: packages/payments/src/transaction-domain.ts,
  packages/db/prisma/migrations/202607250007_commercial_transaction_foundation/migration.sql,
  packages/db/scripts/verify-commercial-transactions.ts

## Context

The quarantined local commerce fixture prices permanent ritual objects directly in USD, couples a
payment event to immediate entitlement mutation, uses a money-event ledger rather than the
production Credit ledger, and allows refund/dispute states inside payment attempts. Extending those
records would reinterpret historical replay and could reproduce an invalid state where an order is
fully refunded but a late success grants value.

The approved production pack instead requires exact catalog/policy snapshots, canonical order and
payment-attempt state machines, integer non-transferable Credits, append-only grant/reservation/
consumption/reversal evidence, nonnegative authoritative projections, deterministic source
allocation, and source-specific entitlements.

## Decision

Keep legacy `commerce_order`, `payment_attempt`, `ledger_entry`, and `entitlement` records unchanged
for historical local replay. Add an explicit v2 transaction foundation keyed to immutable catalog
and price versions. Order states own payment, refund, and dispute projection. Payment attempts end
at succeeded/failed/expired/cancelled and never become refund or dispute aggregates.

Use exact versioned key digests plus canonical request digests for every business operation. The
same key and request replays one result; the same key with changed input conflicts. Store Credit
entries as positive-integer append-only facts with grant/reserve/release/consume/reverse/expire
directions. Reservations bind one user, exact product version, amount, and hard expiry; allocations
name exact source grants in subscription, promotional, then purchased order. A mutable projection
may be transactionally maintained for speed but can never be negative and remains rebuildable from
ledger/reservation/allocation evidence.

Represent Plus and permanent-object entitlements separately. Plus must originate from a verified
order lifecycle; a permanent object must originate from a linked Credit consumption. Keep
pending/active/frozen/revoked as projection states while preserving immutable source evidence.

## Alternatives considered

| Option                                   | Benefits           | Costs/risks                                              | Why not selected                   |
| ---------------------------------------- | ------------------ | -------------------------------------------------------- | ---------------------------------- |
| Expand legacy direct-USD tables in place | Fewer tables       | Reinterprets replay and keeps wrong product model        | D-060 quarantines legacy commerce  |
| Store only mutable Credit totals         | Simple reads       | No allocation, reversal, expiry, or audit reconstruction | Credits require append-only truth  |
| Put refunds/disputes on attempts         | One status column  | Conflates payment attempt with later aggregates          | Attempts end at payment outcome    |
| Let clients submit amount/Credit fields  | Less server lookup | Price and entitlement tampering                          | Server snapshots are authoritative |
| Activate sandbox adapter now             | Immediate checkout | OWN-002 and RIT-063 are unmet                            | Provider gate remains explicit     |

## Consequences

RIT-063 can create one hosted checkout against a v2 server-priced order without changing catalog
truth. RIT-064 can attach verified provider events and outbox processing; RIT-065 can fulfill
Credits/entitlements exactly once; RIT-068 can add explicit refund aggregates; and RIT-070 can add
subscription periods. None of those capabilities is implied by this foundation.

The additive schema duplicates only incompatible historical aggregate names; it does not copy
legacy data or expose a second active product source. RLS scopes privacy-deletion reads, ordinary
runtime receives only required inserts and projection-column updates, and Credit ledger/allocation
evidence cannot be updated or deleted.

## Validation

Focused unit/property tests cover every order/attempt state-event combination, exact idempotency,
valid late success, refund/dispute isolation, entitlement non-revival, deterministic Credit source
order, expiry, reservation/release/consume/reversal arithmetic, and generated overspend rejection.
The isolated PostgreSQL gate covers migration replay, exact snapshots, invalid states/provider
shape/source constraints, idempotency conflicts, 20-way concurrency against six Credits,
append-only privileges, entitlement sources, and logical restore.

## Rollout and rollback

Rollout creates empty additive v2 tables and no provider configuration, public route, worker, or
seeded customer value. Rollback disables all new writes and retains evidence; never delete or edit
ledger rows. Production migration, provider activation, country/price/tax/refund/legal approval,
real money/crypto collection, deployment, and public launch remain explicit owner gates.
