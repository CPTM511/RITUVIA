# D-048: Additive ritual lifecycle and durable-pause boundary

- Date: 2026-07-24
- Owners: product, architect, backend, frontend, qa_security, payments_risk
- Related tasks: RIT-043
- Evidence references: records/decisions/D-045.md, records/decisions/D-047.md, docs/codex/rituvia-production-2026-07-23/03_PRODUCTION_ARCHITECTURE.md, docs/codex/rituvia-production-2026-07-23/04_DOMAIN_MODEL_AND_DATABASE.md, docs/codex/rituvia-production-2026-07-23/02_UI_FIDELITY_CONTRACT.md

## Context

Historical `reflection-ritual.v1` and `reflection-journal.v1` tables have strict code, lifecycle,
and daily-uniqueness constraints. Weakening those constraints to admit the production-pack
lifecycle would make old rows ambiguous and violate the repository's immutable, non-destructive
migration policy. The golden Sanctuary also labels visible exit as leaving for now, while the
backend lifecycle separately needs terminal abandonment for explicit policy or expiry handling.

Consumable access creates a second hard boundary: a pass may be spent only when its exact ritual
session is durably created. A pre-check followed by separate writes could double-spend or lose a
pass under races and retries. Journal encryption also needs a stable resource identity before
ciphertext is produced so authenticated context does not depend only on mutable parent links.

## Decision

Keep historical ritual and journal tables and contracts unchanged. Add separate
`ritual_session_v2`, `private_journal_entry`, and `ritual_pass` tables with exact version,
ownership, snapshot, lifecycle, digest, and timestamp constraints. New APIs dispatch by strict
schema version, while owner GET routes can project either exact historical resources or v2
resources without rewriting history.

Resolve the canonical active catalog item on the server. For permanent access, verify the linked
account's exact active entitlement inside the session transaction. For consumable access, lock one
matching available pass, insert the exact session snapshot, and mark that same pass consumed in
one PostgreSQL transaction. Runtime roles may read passes and update only consume fields; pass
issuance, reversal, refund, and production activation remain outside this task.

Treat every visible Sanctuary exit as a durable `pause`. Resume requires an explicit revisioned
mutation. Keep `abandon` as a strict backend terminal transition without exposing an abandonment
control in the current UI. Bind new journal AES-GCM context to both owner subject and preallocated
journal ID; update re-encrypts under the same binding and delete creates an immediately hidden soft
tombstone.

## Alternatives considered

| Option                                  | Benefits                    | Costs/risks                                             | Why not selected                      |
| --------------------------------------- | --------------------------- | ------------------------------------------------------- | ------------------------------------- |
| Relax historical table constraints      | Fewer tables                | Reinterprets v1 rows and requires destructive migration | Historical contracts remain immutable |
| Check a pass before session insert      | Simpler code                | Race, double-spend, and partial-failure risk            | One transaction is mandatory          |
| Refund a pass on pause or completion    | Familiar inventory behavior | Contradicts consumption-at-start contract               | A successful start consumes once      |
| Map visible exit to abandon             | Fewer states                | Conflicts with golden “leave for now” semantics         | Exit is durable pause                 |
| Bind journal encryption only to parents | No preallocated ID          | Weaker replay/substitution boundary                     | Bind the concrete journal resource    |

## Consequences

Historical replay and daily-limit behavior remain exact. New sessions carry immutable access and
content provenance, one owner/intention has at most one open v2 session, and pass rollback is
database-atomic. The Sanctuary can leave and resume without pretending the ritual completed.
Deleted private journal prose is immediately unreadable through the product boundary.

The local AES-GCM keyring remains development evidence, not production KMS/HSM approval. No
production pass inventory exists, and no checkout or Credit path can issue or reverse a pass.
Expired open rows become inaccessible through owner APIs; any future scheduled abandonment or
physical-retention workflow requires its own policy task and owner approval where applicable.

## Validation

Validation requires immutable migration policy, fresh migration and second-deploy checks, exact
least privilege, free/permanent/pass access, concurrent single-pass consumption, failed-start
rollback, same-key replay, optimistic lifecycle transitions, owner isolation, journal
create/update/delete encryption evidence, CSRF, production-artifact browser pause/resume/complete,
offline retry, reduced motion, keyboard, RTL, 320px layout, axe, console/request ledger, and
private-storage canaries.

## Rollout and rollback

Rollout is local-only and activates the v2 UI/API path without production deployment. Rollback
disables v2 dispatch and the Sanctuary lifecycle path while leaving additive tables unused; no
historical row or pass is deleted. Production deployment, KMS configuration, pass issuance,
retention changes, payment activation, and public launch remain human approval gates.
