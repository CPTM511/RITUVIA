# D-103: Use a private offline owner operations dashboard before an admin route

- Date: 2026-08-02
- Owners: owner, operations, qa_security
- Related tasks: RIT-120, RIT-126, RIT-127, RIT-128, RIT-130, OWN-019
- Evidence references: `packages/analytics/src/owner-operations.ts`;
  `scripts/generate-owner-operations-dashboard.ts`;
  `docs/runbooks/RIT-120_OWNER_OPERATIONS_DASHBOARD.md`

## Context

RIT-120 needs one daily Owner surface for health, revenue, core-loop, AI, queue, support, cost, and
approval state. The repository has reusable local SLO, AI operations, core-loop projection,
commerce inspection, operational-case, backup, and governance evidence, but it does not have a
standing production metrics source, durable consented core-loop analytics, a revenue aggregate,
approved cross-provider budgets, protected staging, or a fully composed admin authentication and
read-audit route.

Creating a visible Web dashboard now would either show invented values, expose an unreviewed admin
entry point, or require a broad authentication/audit/UI slice beyond the smallest RIT-120 outcome.
Treating absent values as zero would be materially misleading.

## Decision

Implement `owner-operations.v1` as a private, read-only, digest-bound offline dashboard. It accepts
one strict source manifest and renders exactly eight sections in canonical order. Every section
shows environment, source kind, observed-through time, maximum age, freshness, data quality,
window, approval reference, evidence path, runbook, current state, and a fixed known gap.

Unavailable, stale, future, or synthetic evidence is forced to `unknown`; it is never displayed as
zero, healthy, nominal, or production-complete. The dashboard also shows the protected English
anonymous free-Beta candidate, OWN-019, the RIT-127 -> RIT-128 -> RIT-130 sequence, standing staging,
Gate H, and independent-security status. Even `evidence_ready` always retains
`owner_deployment_approval_required` and cannot authorize deployment, DNS, provider activation,
data mutation, or launch.

The first surface is generated with `pnpm report:owner-operations` into exclusive mode-0600 JSON
and Markdown files. It has no product, Support, or Admin Dashboard button and no HTTP route. A
future protected Web route may consume the same projection only after its authentication,
role/passkey step-up, read-audit, CSRF/origin, no-store/noindex, privacy, accessibility, browser,
and standing-environment evidence is separately complete.

## Alternatives considered

| Option | Benefits | Costs/risks | Decision |
| --- | --- | --- | --- |
| New `apps/admin` application | Strong isolation | Empty new deployment and duplicated composition before evidence exists | Rejected |
| Protected route in `apps/web` now | Browser-accessible daily view | Requires broader auth/read-audit/UI/E2E work and creates a new attack surface | Deferred |
| Static tracked status page | Easy to open | Goes stale and can be mistaken for live production state | Rejected |
| Private digest-bound offline dashboard | Small, reversible, source-explicit | Manual generation until RIT-126; no browser button | Selected |

## Consequences

The Owner receives one truthful release and operations overview without adding production readers,
provider calls, private data, arbitrary labels, or a new admin route. Existing detailed reports and
source systems remain authoritative; the dashboard is a summary and link surface, not a replacement.

RIT-127 becomes the sole next Ready item and must populate approved cost/budget policy rather than
inventing budget compliance. RIT-128 remains Planned for the incident/provider game day. OWN-019
remains Blocked until the Owner explicitly approves its exact ingress dossier. Standing staging,
provider-level restore, DAST/penetration testing, and Gate H remain incomplete.

## Validation

RIT-120 must pass strict-contract, canonical-section, stale/future/synthetic/unavailable suppression,
private-field/accessor rejection, release-gate consistency, deterministic rendering, digest binding,
mode-0600 output, symlink rejection, no-overwrite, analytics typecheck, formatting, evidence, and
affected workspace gates.

## Rollout and rollback

Use only local, CI, or separately approved protected inputs. Do not put private source data in the
manifest or generated report. Rollback removes the additive analytics export, CLI, tests, and docs;
it does not mutate databases, providers, deployments, or historical evidence.
