# D-074: Checksummed ICU localization publication boundary

- Date: 2026-07-27
- Owners: owner, product, localization, engineering, qa_security
- Related tasks: RIT-100, RIT-103
- Evidence references: `content/localization/manifest.v1.json`;
  `packages/i18n/test/i18n.test.ts`

## Context

RITUVIA previously had an English-only locale-prefixed shell and browser pseudolocale checks, but
parameterized copy still depended on manual string replacement and fixed English formatters. The
repository had no strict source-catalog schema, checksum binding, translation review state,
glossary publication gate, exact missing-key check, or observable runtime fallback contract.

RIT-100 must establish those foundations without activating an unreviewed locale. Legal, payment,
safety, spiritual, and culturally sensitive copy cannot become publishable merely because an ICU
message parses or machine translation exists.

## Decision

Adopt pinned FormatJS ICU parsing and formatting in `@rituvia/i18n`. English remains the only
active locale. The versioned English source catalog and source glossary are RITUVIA-owned records
with editorial, rights, context, risk, placeholder, markup, link, and maximum-length metadata.
Their exact bytes are bound by SHA-256 in a finite manifest.

Translation publication requires all of the following:

- strict catalog, locale, source version, and source checksum binding;
- exact key, ICU placeholder, markup, and link inventories;
- approved status plus human review, with a qualified or owner reviewer for legal, payment,
  safety, and spiritual messages;
- approved locale glossary binding, forbidden-term checks, expansion limits, and no silent
  identical-source fallback; and
- successful process-owned authorization before a catalog can enter runtime resolution.

Runtime locale fallback is finite, explicit, deduplicated, and observable through a structured
fallback event. Currency and time zone remain explicit inputs rather than inferred from language.
No non-English catalog, route, support promise, or public locale is approved by this decision.

## Alternatives considered

| Option                                        | Benefits                                                 | Costs/risks                                                 | Decision |
| --------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------- | -------- |
| Manual templates and native `Intl` only       | No new dependencies                                      | Weak plural/select grammar and easy placeholder drift       | Rejected |
| Load any schema-valid translation             | Simple runtime                                           | Draft, stale, or unqualified content can leak into UI       | Rejected |
| Activate a first translated locale now        | Immediate visible localization                           | OWN-004 and reviewed content/support path remain unresolved | Rejected |
| Checksummed ICU workflow, English active only | Complete engineering boundary without false launch claim | Requires later reviewed locale work                         | Selected |

## Consequences

Core shell, ritual, Tarot, account, commerce, and astrology formatting now receive an explicit
locale. Manual parameter replacement and fixed-English formatters in the reviewed Web surfaces are
blocked by a repository evidence gate. Translation catalogs can be prepared and tested, but only
an exact validated object authorized in the current process is eligible for runtime use.

RIT-101 can now complete RTL architecture and Arabic pseudotranslation QA. RIT-103 and RIT-104 can
build localized route and notification delivery on the same contracts. RIT-105 remains blocked on
OWN-004; RIT-106 remains responsible for the first reviewed non-English beta content.

## Validation

Focused tests cover strict source/glossary parsing, manifest digests, BCP 47 and IANA
canonicalization, number/currency/percentage/unit/date/time/relative/list/display-name formatting,
nested plural/select ICU messages, exact arguments, valid authorization, unauthorized runtime
fallback, fallback telemetry, missing and unexpected keys, stale binding, invalid ICU,
placeholder, markup, link, expansion, glossary, forbidden-term, identical-source, status, and
review failures.

The architecture gate must keep the package client-safe. The localization evidence gate must
verify manifest hashes and reject manual placeholder replacement or fixed-English formatter
regressions in the reviewed Web files.

## Rollout and rollback

Repository rollout keeps `en` as the only active locale and changes no production deployment,
country policy, legal text, payment behavior, data, migration, or external service. Rollback
removes the new package, catalog bridge, manifest, workflow gate, and locale-aware call sites and
restores the prior English-only behavior. A translation launch requires a successor reviewed
catalog, owner gates, route/support readiness, and the RIT-101 through RIT-106 evidence applicable
to that locale.
