# D-031: Git-authored tarot snapshot and structural publication eligibility

- Date: 2026-07-17
- Owners: product, architect, content, ai_safety, qa_security
- Related tasks: RIT-022, RIT-023, RIT-024, RIT-031, RIT-111
- Evidence references: packages/divination/src/tarot-content.ts, packages/divination/src/tarot-publication.ts, content/traditions/tarot/rituvia-placeholder.v1.json, packages/divination/test/tarot-content.test.ts

## Context

RIT-022 must define deck, spread, source, rights, orientation content, and version contracts before
the deterministic draw engine exists. Canonical specifications require traceable sources, separate
text and artwork rights, explicit editorial and translation states, precise versions, and no silent
cross-tradition mixing. No reading service, editorial application, content publication service, or
production content corpus exists. Building those systems here would preempt later backlog slices.

The repository also contains reference artifacts whose content is inspiration only and has no
recorded production license. Copying that deck or applying a generic `public_domain` label would not
prove commercial, display, translation, derivative, or retrieval rights across jurisdictions.

## Decision

Activate `@rituvia/divination` as a pure TypeScript package that may depend only on
`@rituvia/domain`. It owns strict unknown-input parsing, immutable deck/card/spread/content/source
contracts, cross-reference validation, and a pure structural publication-eligibility assessment. It
must not read files, databases, environment variables, clocks, networks, UI, analytics, AI
providers, or randomness. Draw rules, entropy, idempotency, and engine versions remain RIT-023.

Keep canonical authored tarot snapshots under `content/**`. Every snapshot uses exact independent
schema, catalog, source, rights, deck, spread, artwork, and card-orientation content versions. Every
reference is an exact `{id, version}` pair; there is no `latest` resolution. A snapshot contains at
most one active version of a stable entity ID. `supersedes`, when present, is an exact same-ID lower
version reference outside the current snapshot and cannot self-reference or point forward. A future
registry/import workflow must verify that the referenced historical version exists and that the
cross-snapshot graph is acyclic.

Model source provenance, claims, known disagreement notes, editorial dates, actor/role evidence,
locale, tradition, risk, translation state, and rights evidence explicitly. Rights state and
version are independent from source version. Rights permissions distinguish internal validation,
public display, commercial use, derivatives, translation, and AI retrieval; material types
distinguish structural data, spread definitions, interpretation text, artwork, and cultural
references. Pending, not-cleared, revoked, expired, missing-evidence, missing-permission, stale, or
non-worldwide rights fail closed for this global V1 eligibility assessment. Text and artwork
references are separate. Assigned artwork requires per-card asset identity, version, credit, alt
text, localization notes, and one exact artwork source.

Structural publication eligibility is a deterministic assessment for an explicit `asOf` date. It
requires explicit publication permission, independent required-role review with reviewer identity
and approval reference, effective/review dates, evidence-backed public/commercial rights,
translation rights when source and catalog locales differ, AI-retrieval rights when retrieval is
requested, artwork, one-card and ordered Situation/Action/Possibility spreads, all ten intake
themes, reviewed source/localized text, and no prohibited claims. The assessment cannot verify the
external approval reference's authenticity and cannot publish, index, retrieve, activate, or
deploy; the future publishing workflow must do both. `approved` and `published` remain distinct
editorial states even though both can be structurally revalidated.

Use one English synthetic fixture with three original neutral cards, both orientations, one-card and
three-card spreads, and complete content for its declared `open_reflection` test scope. It is marked
AI-assisted, draft, internal-validation-only, artwork-free, non-indexable, non-retrievable, and
publication-disallowed. It is not a historical tradition, production deck, expert-reviewed corpus,
or launch approval. The small fixture proves three-card capacity and every schema branch without
manufacturing a large body of placeholder content.

Do not add a database migration in RIT-022. Git remains the reviewable authored-input system for
this slice. PostgreSQL remains the future system of record for operational readings and immutable
draw facts when those tasks are implemented.

## Alternatives considered

| Option | Benefits | Costs/risks | Why not selected |
| --- | --- | --- | --- |
| Copy the reference prototype deck | Fast and familiar | No production rights evidence; unreviewed claims | Violates repository policy |
| Declare a traditional deck public domain | Realistic titles and meanings | Edition, translation, artwork, jurisdiction, and use rights differ | A label is not evidence |
| Create a 78-card structural-only fixture | Realistic cardinality | Leaves orientation content unproven and creates low-value data | Three complete cards prove current contracts |
| Add content tables and editorial APIs | Runtime querying and admin flexibility | Premature migration, authorization, audit, UI, and operations | Later tasks own these concerns |
| Embed canonical content in package code | Easy runtime import | Couples authored data to executable releases | `content/**` preserves editorial diffs |
| Treat structural eligibility as publication | Fewer gates | External evidence could be forged or missing | Publishing remains a separate audited action |

## Consequences

The repository gains a compiled, runtime-validated content boundary without a provider, database,
UI, or public surface. Drafts can be structurally tested while remaining mechanically ineligible.
Exact source and rights versions support future retrieval and historical reading explanation without
in-place rewrites.

The fixture is intentionally not useful user-facing content. A real rights-cleared deck, complete
ten-theme content, reviewed artwork, and qualified editorial evidence remain required before a
production consumer exists. Git-authored snapshots will eventually need an authorized import and
publication workflow once runtime consumers and correction requirements exist.

No private data, analytics event, payment behavior, locale launch, regional tradition, database
object, production activation, or deployment is introduced.

## Validation

Tests must parse the canonical fixture without mutation, deep-freeze every returned branch, preserve
serialization, and reject extra/unsafe fields, duplicate IDs/orders/tuples, missing exact versions,
cross-tradition references, spread/deck mismatches, missing orientations/themes, forward/invalid
supersession, and merged or missing rights. Eligibility tests must prove deterministic reason order,
the fixture's ineligibility, a structurally complete positive path, and fail-closed revoked,
expired, future, stale, translation, retrieval, territory, missing-permission, and prohibited-claim
states. Architecture and build gates verify the package boundary and compiled exports.

Reconsider authored-input storage when RIT-110 needs concurrent editors, authorization, publication
audit, corrections, and localized dependency propagation, or when measured size and release
frequency make Git operationally inadequate. Do not weaken exact version or rights requirements.

## Rollout and rollback

The placeholder stays unavailable because its use policy disallows publication, indexing, and AI
retrieval. There is no runtime flag, route, migration, retained data, or deployment. Roll back by
removing the package/content snapshot and restoring the workspace/build verifier. Future corrections
create new exact versions; historical facts retain recorded version references.
