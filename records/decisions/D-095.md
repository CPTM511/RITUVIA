## Context

The repository has broad local and test-mode capability, but engineering completion counts no
longer communicate whether a user can understand and complete the product. The combined Chinese
guide mixes user instructions with route, API, database, test, and activation detail. The queue
also advances payment-support internals while customer-facing commerce and several other visible
journeys remain incomplete.

The anonymous reflection loop already has browser evidence. Continuing breadth-first feature work
before owner acceptance would add cost and compatibility surface without resolving product clarity.

## Decision

Effective 2026-07-31, make the current product stage one owner-verifiable journey:

`Question or theme -> Interpretation -> Intention -> Small action -> Free ritual -> Private reflection -> Revisit`

Keep this journey anonymous-first and useful without payment. Account creation, AI enhancement,
commerce, astrology, growth content, additional locales, administration, and production provider
activation are not deleted or repudiated; they are frozen as current-stage expansion unless they
are required to preserve, recover, secure, or verify the retained journey.

Separate communication into three audiences: a plain-language user guide, an owner capability map,
and an engineering runbook. Owner progress reports lead with user outcome, acceptance path, visible
gap, risk, approval, and one next result. Task IDs and implementation evidence belong in the owner
or engineering layers, never the user guide.

RIT-161 becomes the sole active reset task. RIT-074 returns to Planned. RIT-162 may remove exact
code only after dependency, rollback, and browser evidence identify safe candidates. This decision
changes execution sequence and communication, not the production pack's safety/security
precedence, product truth, legal gates, or eventual owner-approved scope.

## Alternatives considered

| Option | Benefits | Costs/risks | Why not selected |
| --- | --- | --- | --- |
| Continue the current backlog order | Preserves prior sequencing | Adds support and platform depth before product clarity | Rejected |
| Delete all non-core code immediately | Rapid line-count reduction | High regression, evidence, privacy, and migration risk | Rejected |
| Rewrite the application from scratch | Clean conceptual surface | Duplicates proven behavior and discards security evidence | Rejected |
| Freeze breadth, separate communication, then remove exact dead code | Preserves value while restoring product focus | Requires a deliberate two-step reset | Selected |

## Consequences

The current stage has a single acceptance journey and a smaller communication surface. Existing
safe-off modules remain maintained only enough to avoid security or repository breakage. No frozen
module may become user-facing or production-active without a later owner decision and restored
queue priority.

This reset does not weaken private-data handling, deterministic calculations, accessibility,
localization architecture, payment integrity, AI safety, auditability, or release approval gates.
It may defer revenue, growth, and modality breadth while owner acceptance evidence is collected.

## Validation

The split documents must agree on the core loop while keeping audience-specific detail separate.
The production build and core-loop browser gate must pass without payment requests, serious or
critical accessibility violations, or private-data leakage. Record and generated-evidence checks
must accept the new task and decision.

Reconsider the freeze only after the owner accepts the retained journey and an exact follow-up task
states the user outcome, evidence, risk, and rollback for restored scope.

## Rollout and rollback

Roll out through documentation and queue state only. Keep feature flags and production providers in
their existing safe-off states. Do not migrate or delete data and do not update golden screenshots.

Rollback restores the prior queue order and combined-document references. Existing implementation,
history, decisions, and safety gates remain available because this task performs no destructive
code or schema change.
