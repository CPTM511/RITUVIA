# D-036: Tab-scoped UUID-only tarot result resume boundary

- Date: 2026-07-18
- Owners: frontend, backend, qa_security, privacy, product
- Related tasks: RIT-029, RIT-028, RIT-052
- Evidence references: apps/web/app/_components/tarot-reading-resume-storage.ts, apps/web/app/_components/tarot-one-card-flow.tsx, apps/web/app/_components/tarot-one-card-machine.ts, apps/web/app/_components/tarot-one-card-transport.ts, apps/web/app/api/v1/readings/[readingId]/route.ts, packages/db/src/tarot-reading-persistence.ts

## Context

RIT-025 and RIT-026 keep a fixed tarot result only in React state. A refresh therefore discards a
useful result even though the owner-scoped read API can return the same immutable reading. Resume
must not become durable browser tracking, cross-tab disclosure, private-text storage, an automatic
redraw, or a second server-retention policy.

The exact RIT-029 acceptance boundary is same-session recovery using only a bounded reading ID.
The product requirement's broader same-device persistence is not exercised by this slice because
it would require a different privacy and consent decision.

## Decision

Store one strict lowercase UUID V4 per reading type in `sessionStorage`, using the fixed keys
`rituvia.tarot.resume.v1.one_card` and `rituvia.tarot.resume.v1.three_card`. Store the ID only after
the complete fixed response passes strict schema, reading-type, ID, position, and presentation
validation. Do not store the selected theme, result, question, card content, report, owner/session
identifier, timestamps, or analytics data. Do not use `localStorage`, IndexedDB, Cache Storage, a
service worker, cookies, URL state, or cross-tab broadcast for resume.

Because a same-origin tab created with a live `window.opener` can receive a cloned snapshot of its
opener's `sessionStorage`, clear the current reading-type resume key before reading whenever an
opener is present. An opener-created tab therefore cannot turn tab-scoped recovery into cross-tab
disclosure or issue the owner GET from inherited state.

On hydration, validate the stored value before any request. Invalid values are removed. A valid ID
causes one exact same-origin credentialed, no-store `GET /api/v1/readings/{uuid}`. The returned ID
and reading type must match the request before the result can enter the state machine. A restored
result returns to an explicit ready-to-reveal state; reveal remains presentation-only and makes no
request. A definitive private `404` removes the ID. Offline, dependency-unavailable, and unexpected
transport failures keep the ID and require an explicit manual retry. No retry or redraw is
automatic.

Starting a new reflection does not erase the previous resume ID. A newly validated fixed result
replaces it, so failed or limited attempts do not destroy the last recoverable result. Storage
denial never blocks the in-page result and is disclosed truthfully. One-card and three-card keys
remain isolated.

Owner retrieval must also enforce `reading.expires_at > CURRENT_TIMESTAMP`; expired readings share
the same private `404` as unknown, cross-owner, or unavailable readings. Framework-prefetch/RSC and
cross-origin representations are rejected before the private read. The existing shared safe-off
tarot gate remains unchanged.

Increase the compressed Web JavaScript budget from 220 KiB to 224 KiB for this complete bounded
resume slice. The measured maximum is 225,894 B gzip, leaving 3,482 B within the new budget. This
is an explicit feature-cost adjustment, not removal of the build budget.

## Alternatives considered

| Option | Benefits | Costs/risks | Why not selected |
| --- | --- | --- | --- |
| Persist the full response | Instant restore without a read | Stores private reflection content and stale policy data in browser storage | Owner-scoped GET is the authority |
| Use `localStorage` | Survives browser restarts and works across tabs | Broader tracking/disclosure and exceeds same-session acceptance | Requires a separate owner/privacy decision |
| Clear the ID when starting over | Simple replacement logic | A failed new attempt destroys the last recoverable result | Replace only after a new fixed response validates |
| Auto-reveal restored results | One less interaction | Hides the restore boundary and changes the existing reveal contract | Preserve explicit user-controlled reveal |
| Retry automatically | Faster transient recovery | Creates hidden traffic and confusing redraw expectations | Retry is explicit and idempotent |

## Consequences

A refresh in the same tab can restore the same owner-bound immutable one-card or three-card result
without creating a new anonymous session or draw. Browser persistence is bounded to a non-secret
opaque identifier and disappears with the tab session. Storage failures degrade to a useful
in-page result instead of blocking the reading.

The identifier still appears in the private GET path and browser history-free network metadata, so
future production proxy/log configuration must retain private-route redaction. Closing the tab,
expiry, revocation, or a private `404` ends recovery. Cross-device/account history remains RIT-052;
offline result caching is not claimed.

## Validation

Client tests cover exact per-type keys, opener-clone rejection, UUID validation and clearing,
denied storage, store timing, replacement timing, all restore transitions, manual retry, strict
response/ID/type binding, and GET-only transport. HTTP, proxy, server, and database tests cover
private equal-shape `404`, RSC and cross-origin rejection, safe `503`, key rotation, owner isolation,
and individual reading expiry.
Production-browser acceptance covers one-card and three-card refresh restoration, explicit reveal,
no reveal-time API request, stale-ID clearing, exact ordered card content, and 320px reflow.

## Rollout and rollback

No migration, server-retention change, content publication, runtime activation, deployment, or
public launch is authorized. Rollback may remove the storage adapter and restore transitions while
retaining the owner GET and its expiry check. If the feature has been used, removing it merely
leaves inert tab-scoped UUID values that disappear when tabs close; no destructive cleanup is
required. Keep the safe-off gate until catalog approval and production activation are separately
authorized.
