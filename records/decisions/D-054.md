# D-054: Read-time private history with timestamp-only session controls

- Date: 2026-07-24
- Owners: owner, frontend, backend, privacy, qa_security
- Related tasks: RIT-052
- Evidence references: docs/02_USER_EXPERIENCE.md, docs/05_DATA_MODEL.md,
  docs/10_SECURITY_PRIVACY_RELIABILITY.md, docs/13_API_CONTRACTS.md,
  docs/14_TEST_STRATEGY.md, records/tasks/RIT-052.md

## Context

RIT-051 preserves private resources under immutable anonymous subjects and authorizes an account
through append-only links. RIT-052 needs a useful account surface without copying private rows,
turning list responses into a prose index, extending retention, or introducing device
fingerprinting. The existing account profile already has optimistic revision protection and the
session table already has sufficient lifecycle timestamps.

## Decision

Build account history as a bounded read-time union over currently retained readings, intentions,
legacy/v2 ritual sessions, legacy/v2 journals, and Revisits reachable through the active account's
immutable subject links. Select only opaque resource identifier, resource type, coarse status,
occurrence time, and optional approved reading type/theme. Use a stable descending tuple of
occurrence time, internal source discriminator, and UUID for the opaque cursor. Accept no
client-selected user or subject identifier.

Keep account profile updates on the existing strict schema and `profileVersion` compare-and-swap.
Expose active sessions as current/other with created, last-seen, and expiry timestamps only.
Collect no device name, location, IP address, user agent, fingerprint, or inferred trust. Targeted
revocation is owner-scoped and cannot revoke the current session; current and all-session logout
remain separate session-CSRF-protected actions.

Permit a linked account session to restore an exact reading detail through the existing private
reading route, while preserving the same missing/cross-owner `404`. Store only that reading UUID in
tab-scoped browser storage for the handoff.

## Alternatives considered

| Option                                    | Benefits               | Costs/risks                                                       | Why not selected                            |
| ----------------------------------------- | ---------------------- | ----------------------------------------------------------------- | ------------------------------------------- |
| Copy history rows to `user_id`            | Simple account queries | Duplicates private data, migration and race risk, retention drift | Preserve immutable source ownership         |
| Include decrypted snippets in history     | Richer previews        | Creates a sensitive prose index and wider leak surface            | Minimal metadata is sufficient              |
| Store device/IP/fingerprint details       | Familiar device labels | New tracking, retention, accuracy, and abuse risks                | Timestamps provide adequate control         |
| Allow targeted current-session revocation | One generic endpoint   | Ambiguous UX and accidental self-lockout                          | Keep explicit current/all logout            |
| Add a durable history table               | Fast reads             | New synchronization and deletion obligations                      | Read-time projection is bounded and correct |

## Consequences

Account history remains consistent with source expiry and deletion without a migration or new
retention period. The UI cannot search private prose and non-reading resources remain summaries
until dedicated restoration flows exist. Session labels are less descriptive than fingerprinted
device lists but avoid collecting unnecessary tracking data. Existing commerce resources remain
on their owner-scoped endpoints and are covered by the authorization test matrix rather than mixed
into reflection history.

## Rollout and rollback

The change is application-only and expand-free. Rollback can remove the account history route and
account control panels while retaining profiles, links, sessions, and private resources. Do not
delete links, change retention, collect device metadata, or mutate production data as part of
rollback.

## Validation

Focused parser, route, service, proxy, and UI tests cover strict response shapes, bounded queries,
profile conflict, session-CSRF, current-session protection, account-linked reading restoration,
and equal-shape cross-owner denial. A dedicated PostgreSQL gate covers pagination, all reflection
resource types, retention/deletion filtering, owner isolation, private-canary exclusion, profile
conflicts, revocation, and logout-all. A production-artifact Chromium gate covers mobile layout,
keyboard flow, accessibility, privacy, profile conflict, current/other sessions, targeted
revocation, and all-session logout.

## Sources and approvals

The owner approved continued autonomous RIT-052 implementation and local unrestricted validation.
This decision does not approve retention changes, device fingerprinting, export/deletion,
production identity providers, deployment, public launch, or golden screenshot updates.
