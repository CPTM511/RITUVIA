# D-053: Immutable subject bridge with recoverable account-session rotation

- Date: 2026-07-24
- Owners: owner, backend, privacy, qa_security
- Related tasks: RIT-051
- Evidence references: docs/05_DATA_MODEL.md, docs/10_SECURITY_PRIVACY_RELIABILITY.md,
  docs/13_API_CONTRACTS.md, docs/14_TEST_STRATEGY.md, records/tasks/RIT-051.md

## Context

RITUVIA private history is currently owned by immutable anonymous subjects. Existing account
authorization resolves that history through `account_subject_link`, but authentication completion
previously consumed the challenge and created an account session before a separate merge
transaction. Explicit merge returned only a status, did not rotate the account session, accepted a
different idempotency key as replay, and had no database-bound account-session provenance.
Opportunistic reflection-route merge could commit rotation and then discard the replacement
bearer. A dropped successful response could therefore strand a user or cause repeated session
side effects.

## Decision

Preserve existing private rows and their immutable `anonymous_subject_id`; do not copy or rewrite
history into account-owned duplicates. Authorize the account through one append-only,
subject-unique `account_subject_link`.

Authentication completion performs challenge consumption, account/identity/session creation,
optional link insertion, and anonymous-session revocation in one PostgreSQL transaction. Any merge
failure rolls back the challenge, account, identity, session, link, and revocation together.

Explicit post-login merge is available only through the dedicated same-origin, empty-body,
session-CSRF-protected endpoint. Bind its evidence to the target user, anonymous subject, source
anonymous session, source account session, exact keyed idempotency digest, and canonical subject
digest. Composite foreign keys prove that each source session belongs to its represented owner.
The runtime role may select and insert link rows but cannot update or delete them.

Derive the successor account bearer from a server-held HMAC key and the exact source account
bearer, anonymous bearer, and idempotency key. Store only the successor digest. Concurrent or
dropped-response retries with the same source and key return the same successor and one link;
different source sessions, keys, or accounts conflict without partial revocation. A successful
explicit merge revokes the source account session and all anonymous sessions, sets the successor
host-only cookie, and returns successor-bound CSRF. Reflection routes never perform hidden merge or
credential rotation.

## Alternatives considered

| Option | Benefits | Costs/risks | Why not selected |
| --- | --- | --- | --- |
| Rewrite every private row to `user_id` | Direct account ownership | Broad destructive migration, duplicate/history races, rollback complexity | Preserve immutable subject ownership and bridge it once |
| Random successor on every retry | Simple generation | Dropped response cannot recover; concurrent replays create extra sessions | Deterministically recover one successor |
| Keep the source account session active | Easy retry | Violates merge rotation and leaves stale authority | Rotate atomically and support exact replay |
| Merge inside reflection mutations | Seamless legacy behavior | Commits credentials separately from resource mutation and can discard the bearer | Centralize in authentication and the dedicated endpoint |
| Store successor bearer in audit | Straightforward replay | Persisted credential compromise | Store only keyed/digest material |

## Consequences

Account conversion preserves exact history without row copying, and concurrency produces one
auditable ownership transition. Exact retries recover from response loss while cross-account,
cross-source, and different-key attempts fail closed. Existing pre-RIT-051 links remain readable;
the new not-valid constraints enforce complete provenance on new rows without rewriting legacy
rows. Account history/settings UI, export/deletion, analytics stitching, production providers, and
deployment remain later tasks or approval gates.

## Rollout and rollback

The migration is expand-only: it adds source-account-session provenance, composite owner/session
keys, foreign keys, a future-row non-null check, and an index. Rollback can stop application use of
the new explicit merge path while retaining all link and audit rows. Do not delete links, rewrite
private ownership, alter retention, or mutate production data without separate owner approval.

## Validation

Focused unit and route tests cover atomic callback composition, preview retry, exact idempotency,
CSRF/cookie rotation, and rejection of opportunistic reflection merge. The dedicated PostgreSQL
gate covers eight-way same-request concurrency, response-loss replay, different-key and
cross-account conflict, preserved reading history, post-link failure rollback, challenge/account
rollback, composite provenance, digest-only evidence, and append-only privileges. The
production-artifact browser gate covers the real explicit merge and retry path.
