# D-107: Bind recurring reviews to local prompt-enforced read-only Codex automations

- Date: 2026-08-02
- Owners: owner, operations, qa_security
- Related tasks: RIT-126, OWN-020
- Evidence references: `automation/rituvia-recurring-reviews.json`;
  `automation/scheduled-read-only-runner.md`; `docs/runbooks/RIT-126_CODEX_AUTOMATIONS.md`;
  `docs/reports/RITUVIA_RIT_126_AUTOMATION_ACTIVATION_DECISION_REQUEST_2026-08-02.md`

## Context

RITUVIA already had versioned daily, weekly, and monthly review prompts plus a bounded structured
result contract, but no bound project schedules. Codex Desktop project cron jobs currently support
local project execution, not a hard read-only worktree execution mode. Creating unrestricted local
jobs would risk colliding with human work or silently changing project state.

The Owner instructed Codex to continue with RIT-126 after it became the sole Ready item. This
authorizes preparation of the reversible development-tool schedules below, but D-106 Option A does
not provide recurring model-use authority and does not accept local prompt-only isolation risk.

## Decision

Create exactly three paused Codex Desktop project automations in `Asia/Shanghai`:

- daily maintenance every day at 08:30;
- weekly product review every Monday at 09:30;
- monthly risk audit on day 1 at 10:30.

Configure `gpt-5.6-terra` with `high` reasoning and failed-run-only notifications. Because the available
project execution environment is local, every automation must first apply the fixed scheduled
read-only runner. A dirty checkout stops as unavailable. A clean checkout may read tracked and
already-available aggregate evidence only and must return the bounded task-result JSON after its
human-readable review.

Keep every card paused until OWN-020 chooses the activation posture and live outputs are validated.
The automations cannot update project state, create PRs, satisfy Owner gates, access production or
private product content, contact providers/users, spend money, or perform a release action.

## Alternatives considered

| Option | Benefits | Costs/risks | Decision |
| --- | --- | --- | --- |
| Keep configured cards paused | No scheduled model use or checkout collision; reversible | RIT-126 remains Blocked | Selected |
| Run unrestricted local automations | Immediate reports | Can collide with dirty work and cross human gates | Rejected |
| Activate local jobs with dirty-checkout stop and fixed read-only runner | Works with current Codex capability | Prompt-enforced rather than hard filesystem read-only; recurring model use | Owner decision required |
| Activate inert GitHub Codex workflows | CI-hosted isolation | Requires API secret, action review, branch protection, and budget authority | Deferred |

## Consequences

The Owner receives three prepared automation cards without a new product/Admin surface or scheduled
model call. Manual prompts remain available. Activation requires the exact OWN-020 response plus
three clean-checkout observed runs whose output and unchanged Git state pass validation.

This does not satisfy RIT-127, standing staging, external monitoring/paging, independent security,
Gate H, deployment approval, or any product/provider activation.

## Validation

- The Git-indexed manifest fixes the three IDs, schedules, runner/prompt/schema paths, model,
  reasoning, execution truth, and notification policy.
- Record-policy tests reject execution, notification, reference, and runner-boundary drift.
- Codex automation state is reviewed after creation and pause against the manifest.
- RIT-126 does not close until Owner activation posture and three clean-run outputs are evidenced.

## Rollout and rollback

There is no rollout: the schedules are paused. Rollback retains pause or deletes the cards only after
review. No product, provider, database, deployment, DNS, payment, or customer state is changed.
