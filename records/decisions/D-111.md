# D-111: Derive dispute support records from matched commerce facts only

- Date: 2026-08-03
- Owners: payments_risk, operations, qa_security
- Related tasks: RIT-074
- Evidence references: `docs/runbooks/RIT-074_DISPUTE_SUPPORT.md`;
  `tests/verify-commercial-fulfillment.ts`; D-092; D-094; D-102

## Context

The signed payment-event path could already project an order to `disputed`, emit a transactional
outbox row, and freeze only unspent purchased Credits. The operational-case kernel could already
triage its original finite source set, but its immutable database constraint could not accept a new
source without a forbidden drop/replacement migration. There was no durable binding from a current
fulfilled provider dispute to one privacy-minimal support work item even though the financial
restriction was correct.

## Decision

Treat the existing immutable, matched `commercial_payment_event_v2` row as the dispute fact; do not
copy it into a second dispute aggregate. Only an applied signed-webhook dispute whose exact outbox is
completed, whose order remains currently disputed, and whose Credit Pack fulfillment has reached
the same payment-state version may become a current support work item. Ignored-out-of-order and
already-refunded dispute observations remain payment history and do not open a current work item.

Run support-work-item projection in an independent retrying Worker loop after payment ingestion and
fulfillment. Support failure must never roll back a signed payment fact, order transition, outbox
completion, Credit hold, or review shortfall. The projector creates exactly one high-priority,
immutable `commercial_dispute_support_projection_v1` row with fixed local SLA metadata and the
draft-only `support_dispute_ack` template. This is not a second mutable case state machine and does
not add `triage`, `escalate`, or `resolve` actions.

The payment-fulfillment role receives only the exact payment-event and support-projection columns
needed to identify/project the work item. It cannot read provider object IDs, amounts, currency,
payloads, or private journals; mutate the projection; send a response; contact a provider; or decide
a chargeback outcome.

## Alternatives considered

Using journal or reading content as evidence, letting support staff create free-form dispute facts,
putting dispute state on payment attempts, auto-reversing all purchased value, and sending an
automatic provider/customer response were rejected. They breach privacy, conflate aggregates,
misstate refund truth, create negative-balance risk, or cross an Owner/provider approval gate.
Dropping and recreating the historical RIT-125 case constraint or adding a second mutable case
kernel was also rejected because it violates immutable migration policy or duplicates workflow
state.

## Consequences

Every matched dispute observation remains in the existing payment timeline. Every current applied
Credit Pack dispute has at most one support work item after fulfillment; duplicate/projector replay
is idempotent, and out-of-order/refunded observations do not create stale current work items.
Credit freeze/refund conversion behavior remains in the existing fulfillment path. Operator
transition state remains absent until a future additive schema version is separately reviewed.

Chargeback evidence assembly, provider submission, win/loss outcomes, customer messaging, paid UI,
pricing, Live provider activation, production migration, and deployment remain outside this
decision and separately gated.

## Validation

The isolated PostgreSQL gate applies all migrations and proves current applied dispute projection,
refund-before-projection exclusion, exact one-to-one work-item creation, fixed SLA/template
classification, immutable/RLS boundaries, narrow payment-event columns, and no private-journal
access. Worker tests prove support persistence failure is contained and retried independently.

## Sources and approvals

- Root `AGENTS.md` privacy, payment, audit, least-privilege, and human-approval rules.
- Canonical payment/data/operations/test specifications and the 2026-07-23 production pack.
- D-092 dispute-hold semantics, D-094 provider-execution separation, and D-102 metadata-only case
  queues.
- No chargeback response, provider action, legal position, production migration, deployment, or
  payment activation is approved.

## Rollout and rollback

This is an additive repository-local migration. Rollout requires the normal migration, role/RLS,
backup/restore, staging, and Owner production gates. Rollback stops the projector and retains
immutable payment, projection, ledger, and restriction evidence. Deleting or rewriting records
requires a separately reviewed forward migration and explicit Owner approval.
