## Context

The approved protected Beta exposes an anonymous intake-first reflection loop. Existing controls
already bound anonymous-session issuance, Tarot draws, authentication starts, privacy operations,
request bodies, ownership, CSRF, revisions, and idempotent domain mutations. Intake and the wider
anonymous reflection mutation surface still allowed one valid session to send an unbounded number
of distinct requests, while IP, user-agent, device, fingerprint, or private-text profiling would
violate the product's privacy-minimal launch profile.

## Decision

Use one PostgreSQL-backed fixed-row request budget keyed only by the hash-resolved active anonymous
session and one of two closed scopes: `question_intake` or `protected_beta_mutation`. Store only the
session foreign key, closed scope, window start, request count, and policy version. Do not store or
derive question text, journal text, intention text, email, IP address, user agent, device identifier,
fingerprint, or arbitrary risk attribute.

Admission occurs after same-origin/session checks and before the private request body or expensive
domain work. Missing configuration, unavailable storage, privilege drift, invalid session, and
malformed policy fail closed. Concurrent requests use one database-atomic cap and return only a
bounded `429` plus `Retry-After`; the browser presents a calm pause state and never retries
automatically.

The local acceptance profile is `12` intake checks per `60` seconds and `120` protected-Beta
mutations per `86,400` seconds under `local.protected-beta-abuse.v1`. These numbers are local test
defaults, not production authorization. A production policy must carry an `own-019.` reference;
OWN-019 must approve the exact thresholds, invite/cohort assumptions, and complementary protected
ingress/edge controls before RIT-130 can produce a Beta candidate.

The shared budget counts HTTP admission attempts, including exact idempotent retries. Domain
idempotency still prevents duplicate state and existing endpoint-specific quotas retain their own
replay semantics. This trade-off bounds request work before reading private bodies; it must be
revisited if protected-Beta evidence shows legitimate dropped-response retries are being blocked.

## Alternatives considered

| Option                                       | Benefits                                      | Costs/risks                                                   | Decision                       |
| -------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------- | ------------------------------ |
| IP/device/fingerprint scoring                | Better aggregate bot attribution              | Adds sensitive profiling and legal/operational burden         | Rejected                       |
| Redis/WAF-only limiter                       | Edge-scale control                            | Adds infrastructure and cannot provide local durable evidence | Deferred to RIT-130 complement |
| Per-endpoint tables and middleware           | Tailored thresholds                           | Duplicates logic and expands schema/change surface            | Rejected                       |
| One fixed-row session budget with two scopes | Durable, bounded, privacy-minimal, reversible | Session farming still needs invite/edge controls              | Selected                       |

## Consequences

The approved anonymous core loop gains one shared, fail-closed admission boundary without enabling
payments, AI, astrology, accounts, public access, or a new data category. Database row growth is
bounded to at most two rate-limit rows per anonymous session. Session farming remains an aggregate
risk, addressed by the existing global issuance cap and the future OWN-019/RIT-130 invite and
protected-ingress profile rather than covert browser profiling.

## Validation

RIT-122 must prove exact concurrent caps, scope isolation, least privilege, restore continuity,
bounded headers, pre-body rejection, no private canary disclosure, no immediate browser retry,
normal-flow recovery, exact proxy methods, configuration failure, production policy-reference
enforcement, migration policy, architecture, generated evidence, and the production-artifact core
loop under exact Node `26.5.1` and pnpm `11.13.1`.

## Rollout and rollback

Roll out only through the expand-only table, least-privilege grants, typed configuration, route
admission calls, and user-facing degraded states. No deployment or provider action is authorized.

Rollback removes the application admission calls and policy configuration while retaining the
expand-only table for a forward fix. Do not drop evidence rows, weaken existing issuance/Tarot/auth/
privacy controls, or activate an excluded provider.
