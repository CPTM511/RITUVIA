# D-035: Unified tarot limit, explicit new-reflection, and categorical report boundary

- Date: 2026-07-17
- Owners: ai_safety, backend, frontend, qa_security, product
- Related tasks: OWN-010, RIT-027, RIT-028, RIT-037, RIT-122, RIT-125
- Evidence references: packages/domain/src/tarot-reading-report.ts, packages/db/src/tarot-reading-persistence.ts, packages/db/prisma/migrations/202607170004_tarot_reading_report/migration.sql, apps/web/server/tarot-reading.ts, apps/web/app/api/v1/readings/[readingId]/report/route.ts, apps/web/app/_components/tarot-one-card-machine.ts, apps/web/app/_components/tarot-one-card-flow.tsx, apps/web/app/_components/tarot-reading-report.tsx, apps/web/proxy.ts

## Context

The reading persistence created in RIT-024 already applies an atomic database-clock quota after
idempotent replay, but the application and persistence layers accepted independently shaped limit
configuration. The one-card and three-card flows also had only transport retry behavior: they did
not yet distinguish retrying the same request from deliberately beginning another reflection, and
they exposed no durable user report control.

A retry must never silently consume another draw. A new reflection must remain an explicit choice
that does not imply greater certainty. A report cannot be a toast or free-text analytics event: it
must be owner-bound, private, idempotent, append-only, minimally retained, and useful to later
content-governance operations without collecting the private question or journal.

## Decision

Treat the persistence limit as the single server-owned authority. Persistence exposes only its
parsed maximum, window, and policy version to the application composition root; application
construction fails closed unless all three exactly match the reading policy. The database clock
and locked anonymous subject remain authoritative. Idempotent replay is resolved before quota or
entropy use. A new request over quota returns a strictly bounded `Retry-After`; the client may
display that server duration but never treats a local clock as authority and offers no immediate
same-request retry from the limit state.

Keep transport retry and new reflection as different state transitions. Manual retry reuses the
same session and reading idempotency keys. Reveal remains presentation-only. Only the explicit
post-result “Start a new reflection” action can clear the completed operation and return to theme
selection. While that separate operation is unfinished or fails, the prior revealed result remains
available; revealing the new fixed result replaces it. Copy states that another draw does not make
the reflection more certain and preserves a clear stop point.

Accept exactly `tarot-reading-report.v1` at
`POST /api/v1/readings/{uuid}/report`. The body contains one of `factual`, `cultural`, `safety`,
`translation`, `rights`, or `accessibility`, plus either the whole-reading target or one canonical
position identifier that exists in the stored verified draw. There is no free-text field. Require
same-origin exact JSON, the private session cookie, and an independent high-entropy idempotency
key. Created and matching replay both return an empty private `204`; changed reuse returns `409`;
invalid, missing, expired, or cross-owner readings share the same `404`; dependency failure is
redacted as `503`.

Persist one immutable `reading_report` row with reading and anonymous-owner foreign keys, category,
validated target, schema and report-policy versions, keyed idempotency and canonical-request
digests, created time, and expiry. Runtime has only exact `SELECT` and `INSERT`; it has no report
update, delete, DDL, or ownership capability. Report expiry exactly inherits the fixed reading
expiry, so RIT-027 introduces no independent retention period. Reports do not consume reading
quota and emit no private analytics. Triage, severity, reviewer workflow, notifications, admin UI,
and deletion/export orchestration remain RIT-125 and later privacy tasks.

Keep the report route and UI behind the same safe-off tarot availability boundary while no
publication-eligible catalog exists. This repository change does not activate the synthetic
catalog, apply a production migration, deploy, or publish a page. A later operational task must
separate “disable new reading creation” from “preserve historical read/report access” before an
environment contains retained customer readings.

## Alternatives considered

| Option | Benefits | Costs/risks | Why not selected |
| --- | --- | --- | --- |
| Let Web and DB configure limits independently | Flexible tests | Silent drift produces inconsistent policy and wait behavior | Composition now requires exact equality |
| Redraw on reveal or retry | Fewer UI states | Network recovery changes facts and encourages rerolls | Reveal and retry must preserve the fixed result |
| Clear the old result before a new attempt | Simpler state | A quota/offline failure destroys the only useful result | Preserve it until the next result is revealed |
| Send a free-text report | More detail | Collects sensitive content and expands moderation/retention scope | Six categories and canonical targets are sufficient for MVP |
| Store reports in analytics or logs | No migration | Not owner-bound, idempotent, private, or auditable | Use a constrained append-only domain record |
| Give reports a separate fixed TTL | Independent operations | Invents a new legal retention promise | Inherit the already fixed reading expiry |

## Consequences

One-card and three-card flows now distinguish recovery from a deliberate new reflection, retain the
previous useful result through failure, expose a calm server-authoritative wait, and offer a private
structured report. Report retries are safe and quota-independent; the browser cannot add free text
or target a nonexistent position; and report persistence cannot mutate reading facts.

The initial local acceptance baseline approved by OWN-010 is three new readings per anonymous
subject per rolling hour. The code remains configuration-driven and safe-off, and no production
limit/window is selected or activated here. Broad denial-of-wallet, network-signal abuse control,
support triage, privacy-rights deletion, and historical-access kill-switch separation remain future
work.

## Validation

Domain tests cover all six categories, exact nested targets, extras, bounds, and non-reflection.
Application, cryptographic, HTTP, proxy, client state/transport, and component tests cover exact
policy matching, same-key replay, conflict, owner isolation, canonical positions, strict methods
and bodies, private errors, bounded `Retry-After`, offline/manual retry, old-result preservation,
and both spreads. Real PostgreSQL tests cover migration, constraints, grants, idempotency, target
validation, quota independence, immutability, expiry inheritance, and logical restore. Full type,
lint, format, architecture, build, accessibility, browser, record, checksum, and secret gates remain
required.

## Rollout and rollback

Apply the expand-only migration before compatible application code in any future environment. Keep
the runtime gate off until an approved catalog and activation record exist. Before retained reports
exist, rollback may remove the new route, UI, persistence method, and table. After reports exist,
disable new reporting through the gate, retain the V1 parser/digest verification and records for
their approved inherited lifetime, and use a separately reviewed forward migration rather than
destructive rollback.
