# D-093: Hold unused Credits before a Stripe sandbox refund

- Date: 2026-07-30
- Owners: owner, payments_risk, security, backend
- Related tasks: RIT-068, RIT-069, RIT-073, RIT-125
- Evidence references: `packages/db/src/commercial-refund-persistence.ts`;
  `packages/db/prisma/migrations/202607300005_commercial_refund_request/migration.sql`;
  `tests/verify-commercial-refund.ts`

## Context

A Stripe refund API response proves that Stripe accepted an idempotent request, but it does not
replace provider confirmation. The user may also spend purchased Credits while a refund request is
in flight, and a network timeout may occur after Stripe accepted the request.

The first safe slice must remain lean, Test Mode only, and compatible with the existing payment
adapter, signed webhook timeline, transactional outbox, and source-linked Credit fulfillment.

## Decision

Allow one authenticated full refund request only for the exact synthetic US/USD Stripe sandbox
Credit-pack and `local.refund.v1` policy when every source Credit remains unused, unreserved,
unheld, unreversed, and active.

Before calling Stripe, create an owner-scoped append-only request and move the exact source Credits
from purchased availability into a nonspendable refund hold under a serializable transaction.
Use a deterministic Stripe idempotency key. A definitive provider rejection releases the hold; an
ambiguous timeout keeps it and allows exact replay to retry safely.

Treat the Stripe API response as `submitted`, never as completion. Only the existing matched
`charge.refunded` payment event and fulfillment outbox may mark the request `confirmed`, link the
confirming payment event, convert the hold, and append one source-linked reversal. Preserve the
internal `refund_requested` overlay when duplicate success events replay the provider timeline.

Do not add a second refund service, runtime dependency, or separate submission queue for this
bounded Test slice. Exact client retry uses the same durable request and Stripe idempotency key;
later admin/support work may surface stale prepared requests without changing refund authority.

## Alternatives considered

| Option | Benefit | Risk | Decision |
| --- | --- | --- | --- |
| Refund before holding Credits | Short request path | Refund-versus-spend race | Rejected |
| Mark refunded from the API response | Simple state model | Claims completion before confirmation | Rejected |
| Add a dedicated refund microservice and queue | Autonomous retries | Extra runtime, DSN and operations surface before measured need | Rejected |
| Durable request, hold, exact retry and existing outbox | Smallest complete vertical slice | Stale ambiguous requests need later support visibility | Selected |

## Consequences

The Web application cannot choose amount, reason, currency, policy, user, provider object, or
Credit quantity. Refund acceptance cannot race a successful Credit reservation into a negative
projection. Duplicate requests and Stripe retries converge on one request, one hold, one provider
refund identifier, one confirming event, and one linked reversal.

Ambiguous provider failure intentionally leaves Credits held rather than guessing whether the
refund occurred. RIT-073 and RIT-125 remain responsible for operator visibility and support
workflow. This decision does not finalize consumer refund law or copy, activate Stripe Live Mode,
run a production migration, deploy, or launch.

## Validation

Focused domain, provider, service, route, payment-timeline, fulfillment, privacy-export and real
PostgreSQL gates must prove owner scope, exact idempotency, changed-request rejection, definitive
rejection release, ambiguous-failure hold retention, duplicate success preservation, webhook-first
confirmation, source-linked reversal, refund-versus-reservation serialization, composite
ownership, least privilege, and nonnegative projections.

## Rollout and rollback

Rollout is limited to an approved non-production Stripe Test environment after the additive
migration and focused gates pass. Rollback disables the refund route/provider method. Existing
requests, holds, confirming events, and reversals remain auditable; no destructive rollback or
balance rewrite is permitted.
