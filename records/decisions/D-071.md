# D-071: Canonicalize the astrology kill-switch persistence key

- Date: 2026-07-26
- Owners: backend, operations, qa_security
- Related tasks: RIT-007, RIT-093
- Evidence references: migration `202607260003_astrology_feature_flag`; RIT-093 kill-switch drill

## Context

The approved production pack and earlier astrology records use `astrology_enabled` as a semantic
kill-switch label. The immutable PostgreSQL feature-flag contract requires hierarchical keys with
at least one dot, so that label cannot be persisted and cannot support a real staging exercise.
Changing the historical migration or weakening its key constraint would damage migration
auditability.

## Decision

Use `experience.astrology` as the canonical registry and PostgreSQL key. Treat
`astrology_enabled` in the frozen production pack and historical D-066/D-069 records as the
superseded semantic label for the same control.

The flag remains default-off. An enabled immutable version requires an `OWN-015:` approval
reference, no country or locale scope, and the existing owner deployment gate before production
activation. The new migration only adds an RLS insert policy; it inserts no version and enables no
environment.

## Alternatives considered

| Option                                 | Benefits                               | Costs/risks                                   | Decision |
| -------------------------------------- | -------------------------------------- | --------------------------------------------- | -------- |
| Use `experience.astrology`             | Satisfies the immutable dotted-key API | Requires historical-label reconciliation      | Selected |
| Weaken the dotted-key constraint       | Preserves the old label                | Damages registry consistency and auditability | Rejected |
| Rewrite the historical migration       | Makes the old label insertable         | Breaks immutable migration evidence           | Rejected |
| Keep the switch only in process config | Avoids a database change               | Cannot support audited emergency-off history  | Rejected |

## Consequences

Active Selection V2, configuration, runtime composition, tests, and new operational evidence use
`experience.astrology`. Historical selection V1 and frozen source-pack text remain unchanged.

A staging drill may append on and emergency-off versions without redeploying. Production remains
disabled until the RIT-142 release evidence and RIT-143 explicit deployment approval pass.

## Validation

Focused tests must prove default-off behavior, approval-reference rejection, database insertion
constraints, latest-version evaluation, and off-before-native execution.

## Rollout and rollback

Rollout applies the additive policy migration and keeps the latest version off. Rollback stops
writers and appends an off version; it does not delete immutable flag history or rewrite the
historical migration.
