# D-029: Privacy-minimal anonymous identity and per-purpose consent ledger

- Date: 2026-07-17
- Owners: backend, security, privacy, product, qa_security
- Related tasks: RIT-020, RIT-021, RIT-024, RIT-050, RIT-051, RIT-054, RIT-055
- Evidence references: packages/domain/src/identity.ts, packages/db/src/anonymous-identity.ts, packages/db/prisma/migrations/202607170002_anonymous_identity_baseline/migration.sql, apps/web/app/api/v1/anonymous/session/route.ts, packages/db/scripts/verify-anonymous-identity.ts

## Context

The product requires meaningful anonymous-first value and same-device continuity before account
creation. That continuity needs a bearer credential, database ownership, expiration, idempotency,
and optional-consent provenance without collecting email, IP address, user-agent, fingerprint, or
private reflection content. The product sources require defined expiry but do not contain an
owner/legal-approved production retention duration or legal consent notice. A singular mutable
consent pointer also cannot represent independent purposes, notice versions, denial, and withdrawal
without losing history or creating cross-purpose ambiguity.

## Decision

Generate 32 random bytes for each created anonymous session, return the raw base64url token only in
the host-only `__Host-rituvia-anonymous-session` cookie, and persist only the versioned SHA-256
digest. The cookie is `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, has no `Domain`, and uses the
database-authoritative fixed absolute expiry; last-seen updates never extend it. Issuance requires a
complete bounded policy configuration, and missing configuration is safe-off. A production policy
version must reference the still-gated OWN-004 decision; this record does not choose a legal
retention period.

Keep optional consent as an append-only per-subject, per-purpose sequence containing a bounded
purpose, notice version, locale, decision, source, timestamp, and request digests. A withdrawal must
reference a prior record for the same subject and purpose. Current consent is derived by replaying
an ordered, contiguous, time-valid history up to a strict 256-record bound and then checking the
exact required notice version; absence, denial, withdrawal, stale notice, oversized/malformed
history, or an inactive session fails closed. The strictly necessary anonymous-session
cookie is not optional consent, and this baseline contains no legal notice copy or consent UI.
Append-only writes remain available at the evaluation bound so a 257th withdrawal can be recorded;
an oversized history evaluates to false and cannot preserve a grant.

Expose only exact `POST /api/v1/anonymous/session`: same canonical origin, same-site fetch metadata
when present, empty body, no query or alternate framework representation, and a high-entropy
idempotency key. Return `204` with no identifiers or token in the body. Same-key concurrent creates
produce one session; a replay without the original cookie conflicts rather than issuing another
secret. One database-atomic singleton limits global issuance without storing network/device
attributes; it is a baseline capacity guard, not a complete production abuse system.

Give the application identity exact reads/inserts and only reviewed last-seen, token-authenticated
revocation, and issuance-gate column updates. D-021's read-only runtime statement is specific to
`feature_flag_version`; this identity capability is separately bounded. Attest the live PostgreSQL identity before every operation and reject
owners, privileged roles, role switching, reachable privilege escalation, DDL, deletes, consent
updates, and expiry/hash/ownership updates.

## Alternatives considered

| Option                                         | Benefits                       | Costs/risks                                                                          | Why not selected                                     |
| ---------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| Plain token or reversible token storage        | Simple lookup                  | Database compromise immediately yields live bearer credentials                       | Violates credential-minimization requirements        |
| Sliding session expiry                         | Longer continuity              | Activity creates indefinite retention and changes the promised policy after issuance | Fixed expiry is clearer and auditable                |
| IP/user-agent/device fingerprint rate keys     | Stronger per-client throttling | Collects linkable attributes before necessity and policy review                      | Global aggregate is the smallest safe baseline       |
| Mutable current consent row or subject pointer | Fast current lookup            | Loses provenance and conflates purposes/notices                                      | Append-only per-purpose derivation preserves history |
| Hardcode a default production TTL or notice    | Faster activation              | Invents legal/retention decisions outside an owner gate                              | Required configuration keeps production safe-off     |

## Consequences

Anonymous same-device continuity is available without email or fingerprinting, and future private
records can bind to one pseudonymous owner. Session compromise remains possible until fixed expiry
or revocation, so every future private-resource endpoint must enforce subject ownership and must
not expose the cookie. Global throttling cannot distinguish attackers from normal traffic and may
temporarily reject all new issuance; production abuse controls require a separate reviewed design.
Feature-flag and anonymous-identity access share one bounded process-level Web database pool, but
every operation intentionally re-attests live catalog privileges before the database-atomic global gate. A request burst can therefore
saturate that bounded pool before the gate; production admission control and load evidence remain a
release requirement.

Consent history adds storage and sequence-lock contention but provides explicit purpose, version,
locale, denial, and withdrawal provenance. No legal copy, optional analytics activation, account
merge, user deletion workflow, or production retention approval is created by this decision.

## Validation

Domain tests cover strict branded parsing, serialization, expiry/revocation, transitions, and
fail-closed consent. Web tests cover exact routing, same-origin/body/idempotency validation,
cookie attributes, no-body success, safe errors, safe-off feature gating, and response privacy.
Real PostgreSQL tests cover token hashing, no plaintext persistence/logging, fixed expiry, runtime
revocation, bounded full-history consent replay, gap/future-history denial, withdrawal,
stale-notice denial, eight-way idempotency races, global capacity, injected privilege-drift denial,
the 256-grant/257th-withdrawal boundary, cross-path process-level pool reuse, constraints, and exact-field
non-empty logical restore with post-restore behavior. Production-artifact
and browser tests must confirm the HTTP/cookie behavior without external requests.

Reconsider the capacity strategy before production traffic, the TTL only through OWN-004 and legal
review, and the schema when RIT-051 adds exactly-once account merge or RIT-054 implements deletion.

## Rollout and rollback

The migration is additive and seeds no identity or consent. The endpoint remains behind the
existing server-side safe-off public-shell gate and required runtime policy configuration. Roll
back by disabling configuration/route use and reverting application/grant changes; leave the
tables intact. Dropping tables or deleting records is destructive and requires backup evidence,
retention review, and explicit owner approval through a later forward migration.
