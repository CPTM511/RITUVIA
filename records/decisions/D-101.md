# D-101: Use fixed privacy-safe Beta SLOs and one global read-only containment mode

- Date: 2026-08-01
- Owners: operations, platform, qa_security, commerce, identity, product_ai
- Related tasks: RIT-075, RIT-120, RIT-124, RIT-125, RIT-128, RIT-130
- Evidence references: `packages/observability/src/beta-operations.ts`; `apps/web/proxy.ts`;
  `packages/config/src/server.ts`; `docs/runbooks/RIT-124_BETA_OPERATIONS.md`

## Context

RITUVIA already emitted bounded structured Web/worker traces and carried correlation IDs, while the
database feature-flag foundation could rehearse an append-only astrology `off -> on -> off` cycle.
The repository had no executable protected-Beta SLO/alert contract and no global Web containment
mode. Building a new monitoring platform, public status service, or duplicated feature-control
system would add the code and operating burden the Owner explicitly asked us to reduce.

## Decision

Adopt the six owner-approved Beta SLO candidates as one fixed numeric evaluator. Missing, stale,
future, and invalid evidence is `unknown`, not healthy. Every non-healthy evaluation carries only a
fixed alert ID, owner, severity, runbook path, and correlation requirement; the contract accepts no
arbitrary labels or private product content.

Add one typed server-only `RITUVIA_OPERATION_MODE` with `normal` and `read_only`. Read-only mode
blocks reviewed business mutations at the existing proxy and returns one bounded private `503`
response with `Retry-After` and the request correlation ID. It continues reviewed reads, signed
payment webhooks, logout, and explicit session revocation so containment does not silently discard
provider settlement truth or remove immediate account-safety controls. Unknown routes remain `404`.

Reuse the existing database-backed astrology Feature Flag as the dynamic kill-switch rehearsal. Do
not duplicate a control service or infer that payment/country/provider controls in RIT-075 exist.
The global mode is environment-backed and currently requires a Web restart; a production metrics
exporter, paging/status provider, no-redeploy global control plane, and Gate H completion are not
claimed.

## Alternatives considered

| Option | Benefits | Costs/risks | Decision |
| --- | --- | --- | --- |
| New monitoring/control platform | Integrated dashboards and controls | Large new code/operations surface; no approved provider | Rejected |
| Public status API/page now | Visible incident state | New public contract, disclosure and hosting work | Deferred |
| Block every write including webhooks/logout | Simple rule | Can lose settlement truth and remove safety controls | Rejected |
| Fixed evaluator plus proxy containment | Small, testable, reversible | External bindings and restart remain | Selected |

## Consequences

The repository can now distinguish healthy, breached, and unknown Beta evidence consistently and
can rehearse correlated read-only containment without a deployment or provider. Production use of
the mode, alerting provider, status communication, or feature flag remains behind existing Owner
gates. RIT-125, RIT-075, RIT-128, and RIT-130 retain their separate responsibilities.

## Validation

RIT-124 must prove exact objectives and freshness, stale/missing fail-safe behavior, fixed runbook
and owner routing, no private canary reflection, valid/invalid operation-mode parsing, read-only GET,
503, webhook, logout, revocation and unknown-route behavior, exact `x-request-id`, existing
`off -> on -> off` database kill-switch behavior, architecture, configuration, record, type, build,
and focused tests under the pinned Node and pnpm versions.

## Rollout and rollback

Use local or separately approved staging evidence first. Production activation, restart, rollback,
deployment, status publication, and customer communication require their applicable approvals.
Rollback removes the evaluator and operation-mode branch; there is no migration or persisted user
state to reverse. Preserve existing observability and feature-flag evidence.
