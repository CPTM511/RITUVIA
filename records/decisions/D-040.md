# D-040: Provider-neutral generation, authorized fallback, and fenced persistence

- Date: 2026-07-18
- Owners: backend, architect, ai_safety, qa_security, privacy, operations
- Related tasks: RIT-033, RIT-034, RIT-035, RIT-036, RIT-038, RIT-083, RIT-122
- Evidence references: packages/ai/src/generation.ts, packages/ai/src/prompt.ts, packages/db/src/interpretation-generation-persistence.ts, packages/db/prisma/schema.prisma, packages/db/prisma/migrations/202607180001_interpretation_generation/migration.sql, apps/web/server/interpretation-generation.ts

## Context

D-037 defines strict public-fact-only interpretation contracts, D-038 produces exact
checksum-verified published-content and prompt artifacts, and D-039 permits continuation only
after exact pre-generation policy evaluation issues an opaque request-bound authorization. None of
those decisions constructs a provider request, enforces a real deadline, validates a provider
result, supplies a deterministic degraded result, or atomically records generation state.

RIT-033 adds those capabilities without treating a TypeScript type, caller-supplied
configuration, structurally cloned trust value, provider claim, or application timer as authority.
It does not make structurally valid provider prose displayable before RIT-034 verifies
semantic safety and fabrication, and must not invent an interpretation-retention duration while
the relevant owner policy remains gated.

## Decision

Keep the generation state machine pure and provider-neutral in `@rituvia/ai`, with Web/server
composition supplying host capabilities and PostgreSQL persistence through narrow adapters. The
entry boundary accepts only the exact runtime-issued parsed input, exact prompt assembly, and
opaque allowed authorization for the same request. It rechecks their complete binding and requires
an exact server-owned provider/model registration plus independent authority. Registration,
authority, prompt, authorization, fallback-template, or persistence ambiguity fails closed; a
fallback must never disguise a broken trust boundary.

Construct one immutable structured request from those trusted artifacts. Provider adapters receive
only that bounded request and a package-owned cancellation capability, and return only a normalized
categorical failure or structured result. Validate normalized values again at runtime: exact keys,
bounded text/usage/cost, the expected provider/model/configuration, and a successful `stop`
completion are mandatory. Parse successful output through the D-037 runtime contract so every
schema field and fact, source, and approved-ritual reference remains bound to deterministic input.
Raw provider objects and exception text never leave the adapter.

Use a host-enforced per-attempt deadline measured by a monotonic clock, with cancellation and
explicit late-settlement/rejection consumption. A timed-out or cancelled attempt cannot later
replace a terminal fallback. Permit at most one retry, using the same request identity and bytes,
only after a strictly normalized settled `rate_limited` or `unavailable` result, or after a
malformed/schema-invalid structured success that explicitly reports zero estimated cost. Do not
trust a provider's arbitrary `retryable` flag, and do not retry timeout, aborted, content-filtered,
quota, unknown, configuration, invalid-request, or policy failures. A future timeout retry would
require a separately reviewed adapter that proves cancellation acknowledgement and stable external
idempotency.

Only the explicit `aborted`, `content_filtered`, `invalid_response`, `quota_exceeded`,
`rate_limited`, `timeout`, and `unavailable` outcomes may enter deterministic fallback. The exact
template must be a runtime-issued, checksum-verified, independently authorized artifact. Render
only from the exact branded deterministic facts and retrieved published content, then pass the
result through the same strict output parser. No permissive default, provider-written fallback, or
hardcoded production copy exists. Missing, mismatched, unauthorized, or invalid fallback material
fails closed. Trust or execution-context ambiguity and the exact `configuration`, `invalid_request`,
and `unknown` outcomes instead become durable no-output `failed` terminal states with no retry,
fallback, usage, or cost.

Treat a valid provider result as an unverified, non-displayable in-memory candidate for RIT-034.
Before that verifier runs, durable storage may contain only its categorical
`pending_verification` status, versioned provenance, and fixed operational fields, never the
candidate prose. An independently authorized deterministic fallback is already non-model output
and may persist its strictly validated structured result. RIT-035 remains responsible for API/UI
delivery and provisional/final/fallback presentation; this decision creates neither route nor UI.

Operational metadata is a recursively immutable closed allowlist: schema/result/failure/retry
codes, attempt count, bounded latency, locale, modality/theme, provider/model/prompt/schema/safety
and content versions, plus validated nullable usage/cost values. Exclude questions, messages,
retrieved excerpts, candidate or fallback prose, raw provider responses/errors, moderation
categories, owner/session/reading/request identifiers, and arbitrary labels. RIT-038 may later map
this contract to approved metrics without broadening it.

Persist generation state through one owner-scoped PostgreSQL interpretation claim before any
provider work. Bind a canonical request/idempotency hash, immutable provenance, anonymous subject,
parent reading, and inherited parent expiry. An exact duplicate replays terminal state or reports
in-progress with zero additional provider calls; a mismatched hash conflicts. Provider work occurs
outside the database transaction. PostgreSQL computes leases from `clock_timestamp()` rather than
an application wall clock and adds a fixed 30-second buffer to the configured total execution
budget. Finalization uses lease version, secret claim material, and a compare-and-set fence so a
stale or late writer cannot overwrite the winner. A reclaimed expired claim is fallback-only while
no approved adapter proves stable external idempotency. Database constraints and least-privilege
roles enforce ownership, legal failed/fallback states, immutable terminal fields, retention
inheritance, and denial of broad update, delete, DDL, ownership, or role escalation.

Keep the entire slice safe-off. It selects no provider or model, reads or creates no API key,
installs no provider SDK, makes no network call, authorizes no paid inference, publishes no prompt,
content, or fallback template, and exposes no API/UI/runtime activation path.

## Alternatives considered

| Option                                        | Benefits                     | Costs/risks                                                                               | Why not selected                                                                |
| --------------------------------------------- | ---------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Activate one provider and SDK now             | Fast visible model output    | Crosses provider/model/key/budget/retention gates and couples orchestration to one vendor | Keep adapters capability-shaped and safe-off                                    |
| Persist provider prose before semantic review | Easier async handoff         | Unverified unsafe or fabricated text becomes durable and may be displayed accidentally    | Persist categorical pending status only until RIT-034                           |
| Use a timeout race without cancellation       | Small implementation         | The expensive request continues and a late result can race fallback/finalization          | Enforce a host deadline, cancellation, late-settlement consumption, and fencing |
| Retry every provider failure                  | Higher apparent success rate | Duplicate cost, retry storms, policy bypass, and denial-of-wallet risk                    | Retry once only for a finite settled allowlist                                  |
| Embed a convenient English fallback in code   | Always returns text          | Bypasses content/copy approval, provenance, localization, and checksum authority          | Require an exact authorized runtime template or fail closed                     |
| Keep idempotency in process memory            | Simple local tests           | Breaks across workers/restarts and permits duplicate paid inference                       | Claim and fence durably in PostgreSQL                                           |
| Give interpretations a new fixed expiry       | Straightforward cleanup      | Invents an unapproved legal/product retention policy                                      | Inherit the parent reading expiry only                                          |

## Consequences

The future runtime can swap providers without changing domain contracts, and an explicitly
fallback-eligible provider outcome can degrade to reviewed deterministic content without allowing
untrusted prose or duplicate inference. Broken trust/configuration cannot be disguised as a
degraded success. Exact request identity, database-clock leases, claim fencing, durable failure,
and immutable provenance make retries, races, historical explanation, and later reconciliation
auditable while metadata remains privacy-minimal.

The boundary intentionally does not make AI output usable end to end. RIT-034 must approve or
replace the in-memory candidate before any final provider prose can be persisted or displayed;
RIT-035 must add the user-facing transport and states; RIT-036 must enforce the release eval set;
RIT-038 owns approved dashboards; and RIT-122 owns production denial-of-wallet controls. Provider
and model choice, credentials, data region/retention/training settings, cost limits, production
content/template activation, and deployment remain explicit later gates.

Generation retention duration is not decided here. Linking the interpretation expiry to its parent
reading prevents an orphan from outliving that parent, but does not approve the parent's duration
or any distinct retention policy. A future owner-approved retention decision may require an
additive migration and deletion/export/backup-expiry review.

## Validation

RIT-033 validation passes 34 focused AI/Web tests for runtime identity binding,
registration/authority denial, exact request construction, strict normalized-result/output
parsing, retry limits, monotonic timeout/cancellation, consumed late settlement, exact fallback
allowlisting and authorization, durable no-output failures, immutable redacted metadata, and zero
provider work on replay/in-progress claims. Full local gates pass formatting, lint, strict type
checking, 1,048 unit/contract tests in 67 files, configuration-boundary integration, the
177-file/nine-module architecture check, seven immutable migrations, a 406-file secret scan, and a
75-artifact production build.

An isolated real PostgreSQL 17 run on port 55434 applied all six current migrations and passed the
eight-way claim race, exact replay/conflict, database-clock reclaim, fallback-only recovery,
lease-version fencing, stale-writer rejection, failed-state and illegal-fallback constraints,
token-overflow rejection, exact least privilege, inherited expiry, and non-empty dump/restore. A
temporary uncommitted loader changed only the local test root and port, not repository guards. The
unrelated PostgreSQL service on fixed port 55432 was not connected to, stopped, or modified. No
provider, key, network request, or paid inference was used for this evidence.

## Rollout and rollback

No provider, model, SDK, key, network request, paid inference, production content/template, API,
UI, runtime activation, deployment, public launch, or production migration is changed. The
migration is additive and remains unapplied by this decision. Before activation, rollback removes
the unused generation/composition/persistence modules and unapplied migration. If a production
migration is later applied or interpretation rows exist, destructive rollback requires separate
owner approval and a forward-fix/data-preservation plan; stale claims remain safe-off and bounded by
their parent expiry.
