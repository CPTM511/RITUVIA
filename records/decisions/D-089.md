## Context

`experience.public_shell` was introduced as a temporary rollout flag while the first English shell
and accessibility evidence were incomplete. RIT-016 requires two distinct phases: retire the flag
safe-off for one registry compatibility window, then remove it after rollback compatibility is
proved. Deleting the key in the retirement version would skip that window, while coupling whole-site
availability to SEO inventory freshness would let editorial drift disable private product routes.

The owner approved a protected staging compatibility window and registry v3 removal on 2026-07-29.
The repository had no configured external hosting project, so the window used an isolated,
loopback-only staging topology rather than inventing a public or production deployment claim.

## Decision

Advance the current feature-flag registry from version 1 to version 2.

- Keep `experience.public_shell` in registry v2 as a `retired` definition with literal safe-off
  behavior. A v2 `on` version is invalid in typed configuration and denied by PostgreSQL policy.
- Stop using the retired flag as a Web request dependency. During the compatibility window the
  existing state adapter returns the completed rollout branch, `enabled`, without reading the
  database, process environment, request, cookie, header, or query.
- Preserve immutable v1 history already present in an upgraded database, but stop creating the
  obsolete local activation seed. New v1 activations are denied; exact v1 keys may append only
  `off`.
- Permit v2 `on` versions only for the remaining active keys with their existing owner gates and
  country/locale scope rules.
- Keep page/API availability independent from SEO inventory freshness. Robots, sitemap, and
  indexability continue to require production plus the current approved public-page inventory.
- After at least one verified deployment/rollback compatibility window, create registry v3,
  remove the retired key and compatibility adapter/branches, and ignore v1/v2 history by reading
  registry v3 only.

The protected window passed, so the final bullet is executed: registry v3 is current and the
retired key and adapter are removed.

## Alternatives considered

| Option                           | Benefits                                     | Costs/risks                                        | Decision |
| -------------------------------- | -------------------------------------------- | -------------------------------------------------- | -------- |
| Delete the key directly in v2    | Fast cleanup                                 | Skips the required compatibility window            | Rejected |
| Use SEO freshness as site state  | Reuses evidence                              | Editorial drift can close unrelated private routes | Rejected |
| Keep the active rollout flag     | No migration                                 | Obsolete runtime database dependency remains       | Rejected |
| v2 retired tombstone, v3 removal | Safe rollback boundary and explicit evidence | Requires a later gated phase                       | Selected |

## Consequences

Current application nodes no longer depend on a public-shell feature flag or compatibility adapter
to serve the reviewed shell. Remaining feature flags default off until an exact approved registry
v3 version exists. Immutable v1/v2 rows remain available for audit and rollback but are ignored by
v3 readers and may not be newly activated.

RIT-016 is Done. Production migration, deployment, rollback, DNS, indexing, and public launch
remain separately owner-gated.

## Validation

Focused tests cover the exact v3 registry, removed-key rejection, direct completed-rollout Web
delivery, exact composition version, legacy no-reactivation, current owner-gated activation, and
immutable migration policy. PostgreSQL verification proves policy roles, v1/v2 on denial, v3
removed-key denial, v3 approvals, repeat migration safety, and runtime read-only privileges.

## Rollout and rollback

The protected window applied the additive v2 policy migration before v2 nodes, observed v1 rollback,
and restored v2 without deleting history. It then applied the v3 policy migration, observed v2
rollback, and restored v3. A rollback reader continues to query only its exact registry version;
legacy writers may append emergency `off` versions but cannot activate legacy rows.
