# D-055: Recently authenticated encrypted privacy export boundary

- Date: 2026-07-25
- Owners: owner, backend, privacy, security, qa_security
- Related tasks: RIT-053
- Evidence references: docs/05_DATA_MODEL.md, docs/10_SECURITY_PRIVACY_RELIABILITY.md,
  docs/13_API_CONTRACTS.md, docs/14_TEST_STRATEGY.md, records/tasks/RIT-053.md

## Context

RIT-053 must export all currently implemented account-linked data without copying source rows,
turning ordinary history endpoints into private-content indexes, exposing bearer/hash material, or
inventing a final legal retention period. Existing account-session creation time is not reliable
recent-authentication evidence because anonymous merge rotates a session without reauth, and an
identity-level last-sign-in time can be refreshed by another device. The repository does not yet
have the transactional outbox/worker and provider-neutral private object-storage boundary required
for asynchronous production delivery.

## Decision

Persist one immutable `authenticated_at` instant on every account session. Authentication creates
it from the database clock; merge rotation copies it unchanged. Every privacy request, metadata
read, and download authorization requires an active session whose own authentication instant is
within the explicitly configured recent-authentication window.

Create one account-owned, idempotent privacy-export request under the production-pack
`POST /api/v1/privacy/export` route. Serialize same-account creation with a transaction advisory
lock and apply a database-clock request window. Build one consistent SQL-statement snapshot over
all retained implemented categories reachable through immutable subject links plus direct account
commerce data. Use explicit output allowlists, decrypt private fields only in the Web server
builder, and package the same data as machine-readable JSON plus human-readable Markdown.

Encrypt the package with a dedicated non-reusable AES-256-GCM key, bind its authenticated data to
account, export ID, schema, key version, creation, and expiry, and store only ciphertext plus
integrity/size/count evidence in PostgreSQL. Owner-scoped metadata uses
`GET /api/v1/privacy/exports/{id}`; download uses a same-origin, session-CSRF-protected
`POST /api/v1/privacy/exports/{id}/download`, never a bearer URL. Append requested, completed,
failed, and download-authorized audit rows containing no private content. Database constraints and
separate immutable request, one-per-request artifact, and audit tables make lifecycle evidence
append-only; runtime can select/insert but cannot update or delete any of those rows.

Until the shared outbox/worker and approved private object-storage lifecycle exist, keep the
bounded 16 MiB artifact build synchronous inside the modular monolith and the encrypted artifact
in PostgreSQL. This is a local production-capable workflow, not approval to activate production
storage, email delivery, legal retention, deployment, or public launch.

## Alternatives considered

| Option                              | Benefits               | Costs/risks                                                   | Why not selected                                      |
| ----------------------------------- | ---------------------- | ------------------------------------------------------------- | ----------------------------------------------------- |
| Use session creation as reauth time | No schema change       | Merge rotation turns stale auth into fresh auth               | Preserve authentication truth explicitly              |
| Use identity last-sign-in time      | Existing timestamp     | Another device can refresh an old session                     | Bind authority to the requesting session              |
| Put a raw download token in the URL | Familiar expiring link | URL/referrer/history/log leakage and replay                   | Require session plus CSRF POST                        |
| Reuse private-content key           | Fewer secrets          | Cross-purpose blast radius and unsafe rotation coupling       | Require an independent export key                     |
| Store plaintext JSON/ZIP            | Simple download        | Database/backup compromise reveals all private data           | Store authenticated ciphertext only                   |
| Add object storage and worker now   | Scalable delivery      | Duplicates missing shared infrastructure and lifecycle policy | Defer provider activation without weakening the slice |

## Consequences

The export includes retained rows even when ordinary product history hides them after expiry or
soft deletion, because an access request must describe data the system still holds. It omits raw
bearers, token/idempotency/claim hashes, provider checkout URLs, payment-object identifiers,
credential public keys, and other internal authority material. The synchronous bounded builder is
not suitable for large production accounts; a future infrastructure task must move the same
versioned package and cryptographic binding behind the worker/object-storage adapter before
production scale.

## Rollout and rollback

The migration is expand-only: it adds nullable immutable session authentication evidence and new
export request/artifact/audit tables. Existing sessions remain NULL and must reauthenticate.
Rollback disables the privacy routes and builder while retaining encrypted artifacts and
append-only audit until an owner-approved retention/deletion process handles them. Do not drop
tables, rewrite authentication instants, delete evidence, rotate production keys, or activate a
provider as part of rollback.

## Validation

Focused configuration, cryptography, package-builder, route, account-session, and real PostgreSQL
tests cover independent keys, AAD/tamper failure, private-field decryption, merge-preserved
authentication time, stale-auth denial, owner isolation, same-key replay, concurrent rate
serialization, expiry, NULL ciphertext rejection, append-only lifecycle derivation,
one-per-request artifact uniqueness, append-only audit behavior, and runtime update/delete/DDL
denial. Milestone RIT-057 retains the complete cross-resource privacy/authorization suite.

## Sources and approvals

The owner approved continued autonomous implementation and unrestricted local validation. This
decision does not finalize privacy/legal wording or retention periods and does not approve
production object storage, email delivery, deployment, public launch, or destructive cleanup.
