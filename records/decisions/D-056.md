# D-056: Immediate access revocation and crypto-shredding deletion boundary

- Date: 2026-07-25
- Owners: owner, backend, privacy, security, qa_security
- Related tasks: RIT-054
- Evidence references: docs/05_DATA_MODEL.md, docs/10_SECURITY_PRIVACY_RELIABILITY.md,
  docs/13_API_CONTRACTS.md, docs/14_TEST_STRATEGY.md, records/tasks/RIT-054.md

## Context

RIT-054 must make private content unavailable immediately without deleting immutable financial,
consent, security, or privacy evidence, inventing a jurisdictional retention period, or depending
on production KMS/outbox/provider infrastructure that is not yet approved. Existing private rows
are linked through immutable anonymous subjects and use shared versioned encryption keys, so
per-user key destruction is not currently available. Existing resource soft deletion hides rows
but deliberately retains ciphertext and therefore is insufficient for account deletion.

## Decision

Create immutable account-owned deletion requests and one-per-request completion evidence. Require
the requesting session itself to be active and recently authenticated, serialize by account,
enforce a bounded request window, bind idempotency to the exact scope, and derive terminal state
from append-only completion rather than mutable status.

For `private_content`, revoke every linked anonymous session, mark every existing account-subject
link privacy-deleted, replace all implemented private plaintext-bearing ciphertext and generated
interpretation prose with non-user tombstones under the non-existent `privacy-deleted.v1` key
version, and destroy encrypted privacy-export artifacts. Existing lifecycle timestamps remain
unchanged where their source constraints make a new timestamp invalid. Account
authorization must ignore privacy-deleted links everywhere. The account and its current session
remain active so the person may create new, independently owned data later.

For `account`, perform the private-content operation and additionally mark the account `deleted`,
clear direct profile and temporary checkout capability fields, persist a one-way provider-subject
suppression before tombstoning each provider subject and encrypted verified email, revoke all
account sessions, and revoke passkeys. Exact result replay is bound to the revoked request token
without restoring account authority. The stable account UUID, subject links, derived
reflection metadata, consent history, commerce/entitlement records, privacy request/audit, and
deletion evidence remain only as pseudonymous relational or integrity evidence under their
existing source retention. No new duration or legal basis is created by this decision.

Export prepare/finalize and deletion use one account fence, preventing an older snapshot from
recreating an artifact after deletion. The Web route returns `202` after the database transaction
completes and clears the account cookie for account scope. Destructive reads/updates run through
the dedicated `PRIVACY_DELETION_DATABASE_URL` and `rituvia_privacy_deletion` login with exact
column grants and deletion-only RLS policies; the ordinary application and interpretation roles
cannot erase export artifacts or verification output. The local modular-monolith implementation
is not permission to mutate
production data, activate provider-side deletion, finalize retention/legal copy, delete backups,
deploy, or launch.

## Alternatives considered

| Option | Benefits | Costs/risks | Why not selected |
| --- | --- | --- | --- |
| Soft-delete existing rows only | Small change | Ciphertext remains decryptable | Does not satisfy private-content deletion |
| Hard-delete the complete subject graph | Removes metadata | Breaks consent, entitlement, pass, report, and audit FKs | Preserve required integrity evidence |
| Delete the account row | Simple mental model | Commerce, audit, session, and privacy evidence use restrictive FKs | Keep a pseudonymous tombstone |
| Shared-key rotation | Uses existing crypto | Deletes every account using that key | Replace only targeted ciphertext |
| Add per-user KMS keys now | Strong crypto-shredding | Requires unapproved KMS migration and re-encryption | Defer without retaining plaintext |
| Finalize legal retention in code | Clear cleanup dates | Requires jurisdiction/provider/legal approval | Keep existing source expiry only |

## Consequences

Deleted private ciphertext cannot be recovered because no tombstone key exists. Derived
reflection metadata may remain until its already-defined source expiry, but no account or
anonymous bearer can authorize it after link/session revocation. Stable pseudonymous identifiers
remain necessary for restrictive foreign keys and evidence integrity. A future approved per-user
key hierarchy and retention worker may replace tombstones and enforce backup/provider deletion
without changing this request contract.

## Rollout and rollback

The migration is expand-only and local. Rollback disables the deletion route before activation.
Requests that did not complete remain retryable by exact idempotency; completed crypto-shredding
cannot and must not be rolled back. Do not restore private plaintext, re-enable deleted identities,
drop evidence, mutate production data, or invoke providers during rollback.

## Validation

Focused tests cover recent-auth denial, exact request replay, concurrent different-scope
serialization, cross-account denial, anonymous/account/passkey revocation, link-denied reads,
ciphertext canary removal, export-artifact deletion, retained commerce/consent/audit evidence,
account reauthentication denial, immutable completion, least privilege, migration replay, and
restore.

## Sources and approvals

The owner approved continued autonomous local implementation and validation. Final retention
periods, provider deletion, legal/privacy text, production migration/data mutation, deployment,
and public launch remain explicit owner gates.
