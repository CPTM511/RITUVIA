# D-026: Finite environment-safe crawl inventory

- Date: 2026-07-17
- Owners: growth_seo, frontend, qa_security, architect
- Related tasks: RIT-013, RIT-103, RIT-114
- Evidence references: apps/web/app/_i18n, apps/web/proxy.ts, apps/web/test, scripts/verify-configuration-boundary.mjs, scripts/web-shell-build-policy.mjs, tests/web-shell-build-policy.test.ts

## Context

The first public surface has four reviewed English pages behind a server-side safe-off flag. Search
metadata exists per page, but the repository needs an explicit crawl inventory, environment rules,
robots and sitemap routes, and protection against query, RSC, segment, unsupported, and future
private-route indexing. Multi-locale routing and schema publishing have later dedicated backlog
owners.

## Decision

Use one typed, exact English page inventory as the sole source for page paths, production document
allows, and production sitemap URLs. Only exact canonical HTML pages without a query string may be
indexable, and only in the production configuration; every non-production, disabled, unavailable,
unsupported, query-string, redirect-root, framework representation, or future private-path response
is explicitly noindex or a private, non-cacheable HTTP 404. Direct `*.rsc` requests are normalized
and answered by Next.js before Proxy can retain a custom robots header, so their framework error
stream is acceptable only while it remains `404`, `text/x-component`, private, `no-store`, and free
of sensitive configuration or query canaries. Non-production robots disallow the whole site and
advertise no sitemap.
Production robots use end-anchored exact document allows plus a default deny, so `/en` cannot
authorize a longer private path; the only prefix allow is the build-audited `/_next/static/` render
asset directory, alongside exact `/icon.svg` and `/sitemap.xml` resources. The initial sitemap is one
deterministic English URL set and omits `lastmod` until a trustworthy substantive-content revision
source exists.

Keep this task free of published JSON-LD. RIT-103 owns reciprocal multi-locale routes, localized
slugs, sitemap indexes, and redirect history. RIT-114 owns structured-data type eligibility,
visible-content parity, rich-result validation, and full crawl validation.

## Consequences

The allowlist is small, auditable, and privacy-safe, and preview/staging cannot become indexable by
accident. Adding a public page requires one reviewed inventory change and matching tests. Search
engines receive no fabricated freshness signal. Production deployment, domain/DNS changes,
public-shell activation, and actual indexing remain separate owner gates.

## Validation

Unit and mutation tests must prove exact inventory order, canonical origin and robots polarity,
deterministic XML escaping, end-anchored robots document allows, reviewed render resources, absent
`lastmod`, deferred structured data, query/private/internal-route rejection, and strict static Next
configuration. The isolated production HTTP matrix must cover enabled, disabled, dependency-error,
canonical, generic, bare, spoofed, reviewed, direct, and segment RSC behavior plus sensitive response
and log canaries. Browser acceptance must confirm local noindex, absent local sitemap, unique metadata,
server-rendered no-JavaScript content, mobile reflow, keyboard focus, console, and same-origin network
requests.

## Alternatives considered

- Prefix-based robots allows: rejected because `/en` would also authorize future private descendants.
- Build-time `lastmod`: rejected because build time is not substantive editorial change.
- Empty or production-looking non-production sitemap: rejected because either provides no useful
  contract or leaks a misleading index inventory.
- JSON-LD in this task: deferred because RIT-114 explicitly owns structured-data eligibility and
  crawl validation.

## Rollout and rollback

No production deployment, public-shell activation, DNS/domain change, Search Console submission, or
actual indexing occurs in this task. Revert the RIT-013 commit and regenerate evidence to roll back.
The prior per-page metadata and safe-off shell remain intact; no database, content migration, or
external state must be restored.
