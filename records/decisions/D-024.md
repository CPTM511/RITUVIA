# D-024: Semantic-token and native-first UI primitive boundary

- Date: 2026-07-17
- Owners: frontend, design, localization, qa_security
- Related tasks: RIT-011
- Evidence references: packages/ui/src, packages/ui/test, apps/web/app/_components/site-shell.tsx, apps/web/app/layout.tsx

## Context

The English shell already has useful local styles, but later public pages and product flows need a
single contract for semantic colors, typography, spacing, focus, motion, form states, and theme
behavior. Copying component CSS into each application would make WCAG, dark mode, localization,
RTL, performance, and failure-state fixes inconsistent. A broad third-party component framework
would add supply-chain, bundle, styling, and abstraction cost before product interaction needs are
known.

## Decision

Activate the existing registered `@rituvia/ui` boundary as a private, dependency-minimal React
package. Version one exports typed native-first action, form, selection, alert, and loading
primitives plus one statically reviewed stylesheet. Components accept user-visible content from
callers, preserve native elements and attributes, do not own product or routing behavior, and avoid
runtime style generation. Local action links accept only root-relative or same-document targets.

CSS custom properties centralize semantic color, typography, spacing, radius, elevation, motion,
and interactive-size tokens. System preference is the server-rendered default; an explicit
`data-theme="light"` or `data-theme="dark"` on the document overrides it without JavaScript. Motion
is nonessential and collapses under `prefers-reduced-motion`; forced colors retain boundaries and
focus. The existing Web shell consumes the shared stylesheet and action-link primitive, proving the
package is integrated without activating another route, locale, theme preference store, or public
feature.

## Alternatives considered

| Option                                                  | Benefits                                                           | Costs/risks                                              | Why not selected                          |
| ------------------------------------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------- | ----------------------------------------- |
| Keep styles and controls in each app                    | No package activation                                              | Divergent accessibility, tokens, and state behavior      | Fails the shared design-system outcome    |
| Add a third-party component framework                   | Large initial catalog                                              | Dependency, bundle, theme, upgrade, and abstraction cost | Product needs do not yet justify it       |
| Build every component in the design specification now   | Maximum apparent coverage                                          | Speculative APIs and untested domain assumptions         | Violates the one-task vertical-slice rule |
| Shared semantic tokens and native-first core primitives | Small dependency surface, portable semantics, progressive adoption | Requires disciplined contracts and CSS packaging         | Selected                                  |

## Consequences

Web and later applications can reuse one browser-native accessibility and theme foundation. The
first package intentionally does not solve complex composite-widget focus management, theme
persistence, domain presentation, or complete page-level degraded states. Consumers remain
responsible for localized labels, application validation, routing, and live-region timing. A future
component may add a client boundary only when interaction requires it and must keep the public
contract compatible.

No user data, analytics, payment, storage, network, database, or production configuration is added.
The package adds no new external dependency and must remain free of remote CSS resources and unsafe
HTML rendering.

## Validation

Static contracts and server-rendered markup tests cover component semantics, name/description/error
relationships, disabled/loading behavior, safe targets, native input attributes, non-color state
labels, and untranslated-copy absence. CSS tests cover centralized tokens, theme selectors, minimum
targets, logical properties, reduced motion, forced colors, and prohibited remote resources.
Architecture, type, SSR, CSS, contrast, build, resource-budget, HTTP-boundary, long-text, direction,
theme, and reduced-motion contracts validate the repeatable code and integration surface. Codex
Browser verifies native pointer/form interactions, accessibility-tree state, 320px/400%-equivalent
reflow, themes, RTL plus nested LTR overrides, console, and local-only resources. An owner-authorized
isolated Playwright pass verifies native Tab/Shift+Tab/Enter/Space/arrow/typeahead behavior, visible
focus, and actively emulated reduced-motion and forced-color computed/rendered states. Together the
two browser surfaces complete the RIT-011 acceptance matrix. Reconsider the catalog as real RIT-012,
RIT-015, and product-flow needs establish composite interaction requirements.

## Rollout and rollback

Adopt the package first in the existing safe-off English shell. No feature flag, migration, or
external rollout is required because this changes only repository presentation contracts and does
not activate the shell. Revert the RIT-011 commit and regenerate evidence to roll back.
