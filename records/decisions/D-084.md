# D-084: Visible-source structured data and complete crawl validation

- Owners: growth_seo, frontend, content, qa_security
- Related tasks: RIT-114

## Context

The approved public-route and quality inventories establish which pages may be crawled, but they do
not by themselves prove that JSON-LD remains limited to visible, source-authorized claims. Earlier
family implementations could repeat schema logic, represent invisible breadcrumbs, publish
optional dates without one shared authority rule, and leave HTTP validation concentrated on a
small core-page subset.

## Decision

Generate one JSON-LD graph node per approved public document from the exact current quality
inventory and visibly rendered page title and description. Map `product-landing` to `WebSite`,
`public-trust-article` to `WebPage`, `educational-collection` to `CollectionPage`, and the five
approved guide shapes to `Article`. Use `name` for non-articles and `headline` for articles.

Derive `isPartOf` only from the inventory's explicit reviewed parent route: core trust pages and
collection hubs belong to the English home page, while guide pages belong to their exact family
hub. The parent must also be a visible internal link. Publish no `BreadcrumbList` until visible
breadcrumbs exist, and publish no author, publisher, date, FAQ, HowTo, Product, Offer, rating, or
review claim without a separate visible source-authority contract.

Require one bounded graph, an exact canonical URL and entity ID, English language, exact visible
H1 parity, a description present in visible main content, an allowed exact key set, and inert
escaping for HTML-sensitive characters and Unicode line separators. Hidden, `aria-hidden`,
template, script, and style content cannot satisfy visible-title, description, or parent-link
evidence.

Validate all 45 approved English pages in the optimized build and production HTTP crawl. Retain a
small real-Chromium matrix for the four schema types and representative families, plus an
executable JSON-LD injection probe. This decision does not activate deployment, DNS, Search
Console, public launch, another locale, or actual indexing.

## Alternatives considered

| Option                                | Benefits                 | Costs/risks                                                   | Decision |
| ------------------------------------- | ------------------------ | ------------------------------------------------------------- | -------- |
| Keep family-local schema components   | Minimal immediate change | Drift, duplicated policy, and inconsistent claim authority    | Rejected |
| Publish broad rich-result vocabulary  | More potential features  | Invisible or unsupported authorship, rating, and FAQ claims   | Rejected |
| Inventory-bound visible minimal graph | Small and auditable      | Richer schema requires later explicit visible source evidence | Selected |

## Consequences

Structured data fails closed when inventory, route hierarchy, type mapping, canonical identity, or
visible copy drifts. Every new content shape requires an explicit reviewed schema mapping. Removing
unsupported breadcrumbs and optional claims may reduce nominal schema breadth, but improves
truthfulness and prevents crawler-only representations.

## Validation

Focused unit and mutation tests cover all 45 type mappings, exact parent authority, malformed
inventory records, hidden-content substitution, unknown keys and types, canonical poisoning,
private-data exclusion, and script-breaking input. The production build policy audits every
generated public document, the configuration boundary requests all 45 canonical URLs, and the
Chromium gate verifies representative page shapes plus inert JSON-LD parsing.

## Rollout and rollback

No migration or external state exists. Roll back by removing the centralized component and
structured-data checks while preserving the D-083 route-quality inventory. Such a rollback removes
the RIT-114 crawl-safety evidence and requires a new reviewed decision before production indexing.
