# D-052: Safe-off authentication provider and hardened session boundary

- Date: 2026-07-24
- Owners: owner, backend, privacy, qa_security
- Related tasks: RIT-050, RIT-051, RIT-052, RIT-056
- Evidence references: docs/05_DATA_MODEL.md, docs/10_SECURITY_PRIVACY_RELIABILITY.md,
  docs/13_API_CONTRACTS.md, records/tasks/RIT-050.md

## Context

The repository already had a local-only passwordless account foundation with encrypted email,
hashed challenges and sessions, and owner-scoped session revocation. It still returned raw local
callback material to browser code, had no database-atomic login-start limits, did not bind a
cross-site magic-link completion to the browser that initiated it, lacked session-bound CSRF for
account mutations, treated durable logout failure as success, and had no provider capability or
passkey persistence contract. No production email provider, WebAuthn ceremony, identity vendor,
retention change, or deployment is approved.

## Decision

Keep authentication behind a closed provider capability contract. The current adapter exposes
email magic-link capability only in local development and reports passkeys as schema-ready, not
active. A local start returns the same `202` shape for every valid email and exposes only a constant
`/api/v1/auth/local-preview` path. Its one-time token and state remain server-side or in an
`HttpOnly` state cookie; neither appears in response bodies, browser storage, or local preview
URLs. Preview/staging/production composition remains unavailable until an approved provider is
implemented.

Enforce start limits in PostgreSQL before challenge insertion. Use one global keyed digest and one
keyed 16-bit identifier bucket re-HMACed to a 32-byte database key. This stores no plaintext email,
IP address, user agent, or device fingerprint, bounds identifier rows to 65,536, and accepts a
small temporary false-positive collision risk. Both counters use one transaction and a fixed
window; exceeding either rolls back the challenge and returns `429` with a bounded `Retry-After`.

Persist only encrypted normalized email and hashes of challenge token, state, previous account
session, and final session bearer. Challenge completion is one-time and creates a fresh
provider-neutral session. The previous session digest captured at start may revoke only an active
session for the same resolved user, which supports cross-site top-level magic-link navigation
without accepting a client-supplied rotation target at completion.

Use host-only `Secure`, `HttpOnly`, fixed-expiry cookies: `SameSite=Lax` for the short-lived
authentication state needed by a top-level email navigation and `SameSite=Strict` for the account
session. Derive a session-bound CSRF token for state-changing account/session routes and keep it in
browser memory. Logout and revocation report dependency failure instead of clearing a cookie while
durable server-side revocation is unknown.

Add a provider-neutral passkey credential table with unique credential material, RP ID checks,
public key bounds, nonnegative sign count, lifecycle timestamps, owner linkage, and exact
least-privilege columns. Do not implement WebAuthn registration/assertion or mark passkeys active.

## Alternatives considered

| Option                                      | Benefits                        | Costs/risks                                                               | Why not selected                                         |
| ------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------- |
| Return the local callback URL               | Simple developer flow           | Exposes raw token/state to browser code, history, and logs                | Use a constant preview route plus `HttpOnly` state       |
| Limit by plaintext email/IP/device          | More precise abuse segmentation | Expands personal/network data collection and retention                    | Use keyed bounded identifier buckets plus a global limit |
| Keep a full HMAC row per email forever      | Exact per-email limits          | Allows unbounded table growth under identifier spray                      | Bound the key space and document collision risk          |
| Clear cookies when revocation storage fails | Appears responsive              | Leaves a valid server session while claiming logout                       | Fail visibly and preserve retry capability               |
| Activate WebAuthn now                       | Phishing-resistant login        | Requires RP/origin ceremony, recovery, attestation, UX, and approval work | Freeze schema/capability only                            |

## Consequences

Local authentication now proves enumeration resistance, one-time completion, same-account session
rotation, CSRF, durable logout, rate limiting, mobile keyboard flow, and accessibility against the
real PostgreSQL boundary. A rare identifier-bucket collision may temporarily throttle two
unrelated addresses; the global limit protects the service independently. Production email,
passkeys, recovery, device/session UI, merge, and admin MFA remain later tasks and approval gates.

## Rollout and rollback

The migration is expand-only and does not rewrite existing identities or sessions. Roll back
application use by removing the new start-rate composition, CSRF requirement, local preview route,
and passkey capability declaration; leave the additive column/tables inert. Do not drop identity
data, alter retention, activate a provider, or mutate production data without separate approval.

## Validation

Focused provider, service, route, proxy, CSRF, configuration, and database tests cover safe-off
composition, uniform responses, bearer isolation, one-time use, rate errors, ownership, and durable
revoke failures. PostgreSQL integration covers all migrations, exact privileges, constraints,
concurrent rate updates, reset, and logical restore. A dedicated production-artifact Chromium gate
covers 320px layout, keyboard completion, serious/critical axe findings, cookie flags, replay,
session rotation, old-token rejection, missing-CSRF rejection, logout, and `429`.

The owner approved autonomous RIT-050 implementation and unrestricted local validation. This

retention change, production deployment, or public launch.
