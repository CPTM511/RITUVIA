# D-041: Monotonic post-generation verification and append-only safe results

- Date: 2026-07-18
- Owners: ai_safety, architect, backend, qa_security, privacy, operations
- Related tasks: RIT-034, RIT-035, RIT-036, RIT-038, RIT-122
- Evidence references: packages/ai/src/verification.ts, packages/ai/src/generation.ts, apps/web/server/interpretation-generation.ts, packages/db/src/interpretation-generation-persistence.ts, packages/db/prisma/schema.prisma, packages/db/prisma/migrations/202607180002_interpretation_verification/migration.sql

## Context

RIT-033 validates output structure and exact fact/source reference sets, but its provider candidate
is deliberately non-displayable and transient. A candidate can still make a fabricated prose claim,
repeat an injected instruction, overstate certainty, offer professional advice, sell spiritual
efficacy, or encourage dependency while self-reporting safe literals. The existing interpretation
row terminates as immutable `pending_verification` without storing candidate prose, so RIT-034 must
verify in memory and durably record only the approved or independently safe result.

## Decision

Use a pure provider-neutral verifier in `@rituvia/ai`. It accepts only an exact runtime-issued,
single-use pending candidate bound to the exact input, retrieved bundle, generation provenance,
canonical candidate digest, and approved verifier policy/reviewer runtime. Candidate safety fields
are data, not authority. Deterministic checks inspect every displayable text leaf and can only add
restrictions. An independently registered semantic reviewer returns a strict fixed verdict and can
never override a deterministic rejection. Uncertain, timed-out, malformed, contradictory, or failed
review cannot approve.

For an unsafe or uncertain candidate, render the exact checksum-verified and independently
authorized fallback already sealed into the RIT-033 candidate context. Verification never invokes
the generation provider again. Trust, binding, registration, configuration, or authority failure is
a no-output error rather than a fallback.

Keep detailed findings transient. Persist only the verified or safe-replacement output, a keyed
output/candidate digest, fixed categorical outcome, and bounded policy/reviewer/version provenance.
Never persist rejected prose, raw reviewer material, excerpts, prompts, detailed safety categories,
or private/user/request identifiers beyond the owning database relationship required for access.

Preserve the immutable RIT-033 interpretation row. Add a one-to-one append-only verification child
record with forced RLS, exact owner/expiry inheritance, exact read/insert privileges, and no runtime
update/delete/DDL path. The generation row and verification child are finalized in one fenced
transaction, and an exact finalization replay is accepted only when its keyed HMAC binding matches.
Persistence responses and replays never expose the transient provider output while verification is
pending. A legacy terminal `pending_verification` row without a child remains non-displayable and
has no recovery or completion API; this slice does not fabricate a replacement for missing
verification evidence.

Keep the slice safe-off: no production provider/reviewer/model, SDK, API key, network request, paid
inference, policy/content activation, API/UI, retention change, payment, deployment, or public
launch is selected.

## Alternatives considered

| Option | Benefits | Costs/risks | Why not selected |
| --- | --- | --- | --- |
| Persist provisional provider prose before verification | Easier asynchronous handoff | Unsafe or fabricated text becomes durable and can leak through replay or debugging | Keep provider prose transient until an atomic verified finalization succeeds |
| Treat provider safety fields as authoritative | Less verifier work | Self-reported literals are forgeable and do not inspect displayable prose | Recheck every visible leaf with independent deterministic and semantic controls |
| Allow semantic review to override deterministic rejection | Fewer fallback results | A probabilistic reviewer could approve a known fact, source, or policy violation | Deterministic rejection is monotonic and final |
| Mutate the immutable generation row with final prose | One fewer table | Weakens RIT-033 history, fencing, least privilege, and append-only auditability | Add a one-to-one append-only verification child in the same transaction |
| Reconstruct historical childless pending rows through a recovery API | More old rows become available | Missing verification evidence would be invented and ordinary-object recovery could forge authority | Keep those rows non-displayable and provide no recovery API |

## Consequences

RIT-035 can consume a durable final verified or safe-replacement result instead of trusting
provisional text or an in-memory verdict. A rejected candidate never becomes stored content, and a
failed atomic finalization cannot expose provider output or leave a partially inserted child.
Append-only verification preserves the historical generation outcome and avoids weakening an
immutable migration constraint. Pre-existing pending rows without a verification child remain
intentionally unavailable to RIT-035.

The policy and reviewer contracts are capability boundaries, not production approvals. RIT-036
still owns release-level regression and adversarial thresholds; RIT-122 owns production cost and
denial-of-wallet controls.

## Rollout and rollback

The migration is additive and is not applied to production by this decision. Before activation,
rollback removes unused verifier/composition/persistence code and the unapplied migration. After a
production migration or stored verification exists, destructive rollback requires separate owner
approval and a forward-fix/data-preservation plan.
