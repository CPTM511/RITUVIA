# D-059: Immutable successor Country Policy registry

- Date: 2026-07-25
- Owners: owner, payments_risk, backend, security
- Related tasks: RIT-060
- Evidence references: packages/country-policy/src/versioned-policy.ts,
  packages/db/prisma/migrations/202607250005_country_policy_registry/migration.sql,
  packages/db/src/country-policies.ts, apps/web/server/commerce.ts

## Context

The prior local commerce rule authorized one exact product/payment tuple but could not represent
service status, disclosures, legal versions, data/marketing constraints, reliable country
evidence, subscriptions, crypto, review expiry, dry-run comparison, or an operational kill switch.
Rules were hardcoded in Web and had no durable immutable registry or runtime privilege proof.

## Decision

Use one strict `country-policy-version.v1` document for each country/environment version. Resolve
country evidence in descending authority from billing, declared country, and reliable geolocation;
deny conflicts; and never allow locale or weak geolocation to authorize paid service. Select one
active immutable successor-chain head, require a mandatory review time, and fail closed for missing,
malformed, future, expired, stale, disabled, disconnected, or ambiguous versions.

Represent fiat and crypto approvals independently. A non-local enabled fiat route requires an
`OWN-002` reference and an enabled crypto route requires an `OWN-006` reference; neither can stand
in for the other. Store the complete strict document plus mirrored indexed selectors and approval
references in an append-only PostgreSQL registry. The application receives only a bounded
SELECT-only capability with live privilege attestation. Control may append but never update,
delete, or truncate.

Emergency shutdown appends a disabled successor. Rollback appends another successor containing the
prior approved behavior. Only the attested local/CI seed path may insert the synthetic local policy.
Staging and production remain empty and paid authorization therefore remains safe-off.

## Alternatives considered

| Option | Benefits | Costs/risks | Why not selected |
| --- | --- | --- | --- |
| Keep per-product hardcoded rules | Smallest change | No service/legal/data policy or durable provenance | Cannot satisfy RIT-060 |
| Mutate the active policy row | Simple operator action | Destroys evidence and makes orders unexplained | Policy history must be immutable |
| Treat IP/locale as country truth | Easy anonymous routing | Bypasses stronger billing/account facts | Conflicts must fail closed |
| Use one payment approval reference | Fewer fields | Fiat approval could accidentally enable crypto | Payment gates are independent |
| Seed a production disabled row | Explicit shape | Can be mistaken for reviewed market policy | Production must remain empty |

## Consequences

Commerce now reads strict policy documents from PostgreSQL and records the exact selected version
on each order. The returned snapshot also carries disclosure and legal-document versions for
server-authoritative presentation. Local development remains functional through synthetic seed
data, while preview/staging/production deny when no approved policy exists. Future policy
administration must append reviewed versions and should use dry-run comparison before publication.

## Rollout and rollback

The migration is additive. Deploying code without a production policy keeps paid behavior off.
Rollback stops the policy-backed commerce path or appends an approved successor; do not edit/delete
registry history. Publishing a production policy, activating a provider/country/crypto asset,
changing legal/tax/refund terms, deploying, or launching requires the existing owner gates.

## Validation

Focused tests cover strict parsing, country evidence precedence/conflict, service/product/age,
fiat/crypto/provider/method/currency/recurring decisions, independent approvals, review expiry,
overlap, kill-switch/rollback chains, dry runs, runtime parsing, order version persistence, RLS,
immutable triggers, bounded reads, privilege escalation denial, idempotent synthetic seed, and
logical dump/restore.

## Sources and approvals

This decision implements existing canonical policy and owner gates. It does not approve a country,
provider, payment method, crypto asset, legal document, tax/refund policy, deployment, or public
launch.
