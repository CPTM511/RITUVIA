# D-067: Versioned self-hosted location and historical time-zone boundary

- Date: 2026-07-26
- Owners: architect, backend, qa_security, privacy
- Related tasks: RIT-091, RIT-092, RIT-094, OWN-014
- Evidence references: official GeoNames export/licensing pages; Google Time Zone API
  documentation; OpenStreetMap Foundation public Nominatim policy; Node.js `process.versions`
  documentation

## Context

Astrology needs a selected place and historical local-time resolution before it can create a
reproducible UTC birth instant. Place queries and birth locations are sensitive. A current offset,
browser locale, first search result, or silently selected nearby place cannot safely substitute for
historical time-zone rules or explicit user selection.

The canonical API inventory still names `GET /api/v1/locations/search`. Putting a birthplace query
in a URL conflicts with the repository rule that birth data must not enter URLs, browser history,
access logs, analytics, or public metadata. RIT-091 therefore implements no HTTP route and records
the smallest owner decision as OWN-014.

## Decision

Use an injected, provider-neutral `astrology-location-time-zone` V1 contract in
`@rituvia/divination`, with a self-hosted GeoNames export as the intended production gazetteer
source. A production snapshot must be imported outside request handling and identified by an
immutable provider ID, adapter version, provider version, snapshot version, SHA-256 digest, source
URL, license ID, attribution text, and cache TTL. This decision does not import or activate a real
GeoNames snapshot.

Resolve historical local time with the pinned Node `24.18.0`, ICU `78.3`, and tzdata `2026b`
runtime. Every successful result carries the original local date/time, opaque location ID,
coordinates, IANA zone, provider provenance, exact runtime/ICU/tzdata versions, UTC instant,
historical offset, and confidence. Pre-1970 results explicitly report limited tzdb confidence.

Ambiguous clock folds return both candidate instants until the caller supplies `earlier` or
`later`. Nonexistent clock gaps return no instant. Provider/runtime failure, malformed output,
unknown location, version drift, or unexpected zone behavior fails unavailable; there is no UTC,
current-offset, nearest-place, first-result, remote-provider, or alternate-source fallback.

Search input is normalized and bounded. Results contain no dedicated query field or arbitrary
provider echo; a canonical provider place label may naturally match the searched place name. The
Web composition uses only bounded process memory, HMAC-only keys partitioned by provider/data
versions, single flight, a provider-declared TTL capped at 15 minutes, failure eviction, timeout
cancellation, and stable redacted errors. Resolution is never cached by birth time, and a selected
opaque location ID is reread from the provider rather than trusting client-supplied coordinates or
zone data.

## Alternatives considered

| Option                      | Benefits                                                           | Costs/risks                                                                                              | Decision                          |
| --------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- | --------------------------------- |
| Self-hosted GeoNames export | CC BY data, stable IDs, coordinates and IANA zones, offline replay | Snapshot import, attribution, updates, search index and operations are owned by RITUVIA                  | Selected target                   |
| Google Time Zone API        | Managed request API                                                | Official documentation says historical time zones are not considered                                     | Rejected for historical authority |
| Public Nominatim service    | Familiar place search                                              | Public policy has strict shared-service limits and attribution requirements; not a production dependency | Rejected as default               |
| Browser/current offset      | No provider                                                        | Cannot resolve historical DST, folds, gaps, or place identity                                            | Rejected                          |

## Consequences

RIT-091 can close without external network access, database changes, a production data snapshot, or
an HTTP/UI surface. RIT-092 may persist encrypted birth profiles against this exact contract.

OWN-014 must approve a privacy-safe replacement for the planned GET search route before location
search UI work. The recommendation is an authenticated, same-origin, session-CSRF-protected,
rate-limited `POST /api/v1/locations/search` with a bounded JSON body, `Cache-Control: no-store`,
redacted telemetry, no raw query retention, and no shared cache.

Production GeoNames ingestion still requires an exact snapshot/date/digest inventory, attribution
placement review, update/rollback procedure, local search-index limits, performance evidence, and
operations ownership. A different provider or dataset requires a new descriptor and decision; it
must not reuse an existing version.

## Validation

Contract tests cover normalized/limited search, no raw-query return, zero/one/multiple candidates,
duplicate and hostile provider output, unknown locations, provider/runtime failures, versioned
HMAC cache partitioning, single-flight/expiry/failure eviction, timeout cancellation, Kathmandu's
non-hour offset, New York DST fold/gap, Samoa's skipped local date, and explicit pre-1970
confidence.

## Rollout and rollback

No production rollout occurs. Rollback removes the pure contract, Web runtime/cache composition,
exports, tests, and records. There is no database migration, retained birth data, external request,
provider account, secret, deployment, or public behavior to reverse.
