# D-047: Production ritual catalog and legacy replay separation

- Date: 2026-07-24
- Owners: product, architect, backend, qa_security, payments_risk
- Related tasks: RIT-041, RIT-042, RIT-043
- Evidence references: docs/codex/rituvia-production-2026-07-23/contracts/catalog.json, records/decisions/D-045.md, packages/domain/src/reflection.ts, docs/05_DATA_MODEL.md

## Context

The historical local MVP represents six candle/incense/symbolic selections as one ritual object
code set. The production pack instead defines `free_candle` and `free_incense`, four permanent
objects, five consumable rituals, and `golden_bowl` rather than the historical
`golden_intention_bowl`. It also requires permanent ownership to remain distinct from a pass that
is consumed once per ritual start.

Silently replacing the historical constants would make persisted `reflection-ritual.v1` rows and
idempotent replay ambiguous. Reusing the old permanent-entitlement model for consumable rituals
would create durable access where the production contract requires one-use authorization. Copying
Credit prices into the ritual definition domain would also let presentation/content code become
commercial authority before the Credit transaction foundation exists.

## Decision

Use the production-pack codes for the new `ritual-catalog.v1` contract. Model catalog items as
exactly one of `free_object`, `permanent_object`, or `consumable_ritual`, with matching `free`,
`permanent_entitlement`, or `consumable_pass` access requirements. The ritual domain records only
an abstract requirement code; it does not determine Credit cost, balance, purchase eligibility,
entitlement fulfillment, or pass consumption.

Retain the historical reflection ritual code set unchanged for `reflection-ritual.v1`. Publish an
explicit `historical_replay_only` mapping from every legacy code to one exact new item version,
including `candle` to `free_candle`, `incense` to `free_incense`, and
`golden_intention_bowl` to `golden_bowl`. New code must never infer a latest definition from a
legacy row.

Store the new original-secular ritual catalog as reviewed Git-authored content with publication,
rights, safety, source, locale, effective-date, and review-date evidence. Keep template and item
contracts free of arbitrary user-facing prose, efficacy fields, prices, Credit costs, payment
authority, and ownership claims. Durable session version/access snapshots and atomic pass
consumption remain part of the later ritual start/completion persistence slice.

## Alternatives considered

| Option | Benefits | Costs/risks | Why not selected |
| --- | --- | --- | --- |
| Rename historical constants in place | Smallest code set | Corrupts replay meaning and DB constraints | Preserve v1 semantics |
| Keep only legacy codes | No compatibility layer | Ignores the owner-approved production pack | New contracts use canonical codes |
| Treat consumables as permanent objects | Reuses current entitlement code | Allows repeated use without a pass | Access kinds remain distinct |
| Put Credit costs in ritual definitions | One combined catalog | Couples content to money authority | Commerce remains authoritative |
| Copy proposed SQL now | Fast apparent parity | Prematurely freezes lifecycle and owner model | Adapt persistence in the sequenced task |

## Consequences

RIT-041 can deliver a claim-safe, exact-version catalog without changing the historical local
ritual API, payment behavior, database rows, or production activation. RIT-042 can render the new
definitions without inventing access semantics. The later persistence slice must snapshot exact
catalog/template/item/access evidence and implement permanent-entitlement or consumable-pass
authorization atomically rather than reusing the legacy pre-transaction check.

## Validation

Validation requires exact production code sets, free candle/incense presence, strict
unknown-field rejection, approved publication metadata, closed presentation dimensions, fixed
symbolic-only/no-guarantee values, template/access reference integrity, exact-version lookup,
complete legacy mapping, payment-authority absence, compiled build exports, and public-route
contract tests.

## Rollout and rollback

Rollout is a read-only catalog contract and endpoint. Existing ritual creation remains on its
historical contract. Rollback removes the new endpoint and catalog exports while retaining legacy
reflection behavior. No migration, entitlement, pass, payment, production content activation, or
customer data rollback is involved.
