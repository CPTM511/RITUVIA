# D-058: Request-scoped privacy deletion and composed security gate

- Date: 2026-07-25
- Owners: owner, backend, security, qa_security
- Related tasks: RIT-057
- Evidence references: apps/web/proxy.ts, apps/web/app/api/v1/privacy/_http.ts,
  packages/db/prisma/migrations/202607250004_privacy_authorization_hardening/migration.sql,
  packages/db/src/privacy-deletion.ts, scripts/verify-identity-privacy-authorization.mjs,
  scripts/verify-privacy-control-browser.mjs

## Context

The separately verified account, export, deletion, and admin slices did not yet prove one
integrated identity/privacy boundary. Security review also found that the Web proxy did not
explicitly admit the privacy routes, export metadata reads did not reject cross-site requests, and
the dedicated deletion login could select or mutate rows outside the account authenticated by the
presented deletion token.

## Decision

Keep privacy routes on an exact-method/path proxy allowlist and require same-site request metadata
for authenticated export metadata reads. Before using the dedicated deletion login, hash the
presented bearer and set it as a transaction-local PostgreSQL setting. A security-barrier view and
forced row-level policies resolve that hash to one authorized account and expose or mutate only
that account's deletion graph. Preserve every non-deletion runtime role's existing access while
keeping the deletion role unable to broaden its subject through query parameters or application
mistakes.

Compose the account authentication, merge, account control, export, deletion, admin authorization,
redaction, metadata, analytics, PostgreSQL recovery, and production-artifact browser boundaries in
one independently runnable `test:identity-privacy-authorization` gate. Run the complete workspace
matrix once at RIT-057 milestone closure under D-050 rather than repeating it during every
implementation slice.

The admin service credential remains undeployed and no admin route or UI exists. Before any admin
surface or production admin credential is activated, role mutation and its audit append must be
placed behind a reviewed database-bound privileged procedure or equivalent database-enforced
step-up capability; possession of the service credential alone must not become sufficient
production authority.

## Alternatives considered

| Option                                      | Benefits                    | Costs/risks                                        | Why not selected                              |
| ------------------------------------------- | --------------------------- | -------------------------------------------------- | --------------------------------------------- |
| Trust account IDs supplied by Web code      | Minimal database changes    | One query mistake becomes cross-user destruction   | Authorization must survive application errors |
| Give the deletion role broad table access   | Simple deletion transaction | Cross-user read and mutation remain possible       | Violates least privilege                      |
| Put the bearer hash in SQL parameters only  | Explicit per query          | Easy to omit on one query in a long transaction    | Transaction-local policy is comprehensive     |
| Activate admin routes during RIT-057         | End-to-end admin flow       | Crosses WebAuthn, enrollment, and owner gates       | Admin remains intentionally safe-off          |
| Rerun every workspace gate after every edit | Maximum repeated evidence   | High runtime with little additional confidence     | D-050 requires layered verification           |

## Consequences

Deletion authorization is enforced by both application validation and PostgreSQL policy, and
direct use of the deletion credential cannot inspect or mutate a second account under the first
account's token. Privacy metadata has a read-side cross-site boundary, and the exact production
proxy surface is regression tested. The composed security gate remains useful for focused
Milestone 5 regression without forcing the full workspace suite.

The RLS policies depend on the transaction-local token-hash setting and the immutable request
ledger. Any future asynchronous deletion worker must propagate only the opaque request capability,
set the transaction-local hash, and retain the same policies. Production admin activation remains
blocked on the database-bound step-up requirement above.

## Rollout and rollback

The migration is additive and applies restrictive policies only to the dedicated deletion login;
existing runtime roles retain their prior access. Rollback disables use of the deletion login and
privacy routes before removing the policies or view. Do not weaken the policies, deploy an admin
credential, mutate production data, or activate a public service as rollback shortcuts.

## Validation

Focused route tests cover exact proxy admission, foreign-origin metadata denial, authentication,
CSRF, owner scope, and private response headers. The isolated PostgreSQL deletion gate proves
cross-user invisibility and zero-row mutation when the deletion role presents another account's
token, then re-proves deletion, replay, restore, and least privilege. The browser gate performs
sign-in, export, metadata, download, deletion, old-session/export denial, dropped-response replay,
and private-canary checks in one real browser flow.

## Sources and approvals

This hardening implements existing privacy and least-privilege requirements and introduces no new
retention, legal text, production data mutation, provider, deployment, or launch decision.
Production admin credentials, WebAuthn activation, role enrollment, and public admin routes remain
explicit owner gates.
