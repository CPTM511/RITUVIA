## Context

Anonymous consent is purpose/version scoped but becomes unavailable after account merge because
the anonymous bearer is revoked. Treating any linked anonymous grant as current account consent
would let an old subject grant override a later account withdrawal. Mutable profile booleans would
also erase notice-version and withdrawal evidence. The production pack requires AI
personalization to remain separate from analytics, model improvement, service notifications, and
marketing, while current production analytics and private-content AI paths remain disabled.

## Decision

Add a separate account-owned append-only consent authority for
`optional_product_analytics`, `ai_personalization`, and `model_improvement`. Each purpose has its
own exact notice version and contiguous sequence. Record grant, denial, and withdrawal with
database time, locale, fixed source, request digests, and same-account/same-purpose withdrawal
reference. Serialize mutations on the account, preserve exact idempotency replay, reject
same-key changed requests, and deny runtime update/delete privileges.

Derive current state only from the bounded ledger. Absence, denial, withdrawal, stale version,
malformed history, invalid session, or more than 256 records fails closed. Recheck the exact
purpose and notice at each sensitive data-flow boundary rather than caching a value at login,
page load, purchase, merge, or queue creation. AI personalization permits only an excerpt the user
explicitly selects; it never implies model improvement or access to names, email, payment data,
full journal history, marketing, or service notifications.

Expose strict private account controls and same-origin/session-CSRF/idempotent API operations.
Report UI success only after the append commits. Include account consent in privacy export while
retaining the evidence under the existing deletion policy.

## Alternatives considered

| Option                                       | Benefits                   | Costs/risks                                                                       | Why not selected                          |
| -------------------------------------------- | -------------------------- | --------------------------------------------------------------------------------- | ----------------------------------------- |
| Reuse any linked anonymous grant             | No new table               | Old grants can revive after account withdrawal; bearer is revoked                 | Account state needs one current authority |
| Mutable profile booleans                     | Simple reads               | Erases versions, denial, withdrawal, and idempotency evidence                     | Consent is append-only audit evidence     |
| Cache consent in session/UI                  | Fewer reads                | Withdrawal remains effective only after refresh/login                             | Immediate data-flow effect is required    |
| Bundle personalization and model improvement | Fewer controls             | Training/eval use is materially different                                         | Purposes must remain independent          |
| Activate analytics or provider AI now        | End-to-end production path | Missing retention, legal/provider, outbox, cancellation, and deployment approvals | Keep external capabilities safe-off       |

## Consequences

Every account session sees committed withdrawal immediately through the shared account sequence.
The extra database read is accepted at sensitive boundaries. Reaching the history bound disables
the purpose rather than preserving a grant. The current UI records technical preferences, but
production analytics collection, model training, and provider private-content processing still
have no active path.

## Rollout and rollback

The migration is additive and does not rewrite anonymous consent or profile rows. Rollback removes
the API/UI/data-flow composition and stops new ledger writes while retaining records. Do not drop,
rewrite, or bulk-delete consent evidence. Legal notice activation, retention changes, analytics
collection, model improvement with real user data, private-content provider AI, deployment, and
public launch remain explicit owner gates.

## Validation

Focused domain, parser, route, proxy, server, and browser tests cover strict versions, no bundled
purposes, same-origin/session-CSRF/idempotency, safe UI states, and repeated data-flow checks. The
isolated PostgreSQL gate covers defaults, cross-account isolation, cross-session visibility,
grant/withdraw replay, concurrent sequence serialization, stale notices, 257-record fail-closed
evaluation, and runtime update/delete denial.

## Sources and approvals

The owner requested continued autonomous implementation. Approved prototype copy is used where
available; final legal consent text and production activation remain owner-gated. This decision
does not approve analytics persistence, browser beacons, marketing/service-notification delivery,
real-user model training/evaluation, AI-provider private-content processing, deployment, or launch.
