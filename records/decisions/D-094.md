# D-094: Separate commerce command acceptance from provider execution

- Date: 2026-07-31
- Owners: owner, backend, payments_risk, security, operations
- Related tasks: RIT-073, RIT-074, RIT-075, RIT-125
- Evidence references: `packages/db/src/commerce-admin.ts`;
  `packages/db/prisma/migrations/202607310003_commerce_admin_timeline/migration.sql`;
  `packages/db/scripts/verify-commerce-admin.ts`

## Context

Support needs one order-centric view across payment, Credit, refund, reconciliation, subscription,
and administrative events. It also needs narrowly bounded manual reconciliation and refund
authority without letting a browser or general application role mutate payment facts.

An accepted administrative command is not proof that a provider action completed. Network failure
can occur after a provider accepted an idempotent request, concurrent retries can race, and mutable
current-state rows cannot truthfully represent historical event state.

## Decision

Create a safe-off, owner-only commerce administration kernel for one order at a time. Require an
active owner role, recent account authentication, a recent same-session passkey assertion, a reason
code, a ticket reference, and typed confirmation for reconciliation or refund commands.

Expose only two database-owner-defined, security-barrier projections to the admin service role:
one bounded order summary and one event timeline. Keep raw commerce tables and private journals
unreadable. Historical creation events use immutable creation state rather than current mutable
status.

Persist command acceptance before provider execution in a dedicated append-only operation record.
Append separate requested, execution-started, succeeded, and failed evidence events. Bind each
event digest to its operation, attempt, event type, result reference, and database timestamp.
Use the durable operation identifier as the provider-neutral executor idempotency key. Exact retries
reuse the operation across policy-version changes; changed order, amount, or currency conflicts
fail closed.

Serialize reconciliation limits per order and refund limits per owner. Bound timeline reads,
inspection frequency, reconciliation frequency, refund amount, daily refund value, execution lease,
and retry attempts. Record every authorization, scope, idempotency, and limit denial with actor role
when an authenticated session exists. Because this kernel has no HTTP entrypoint, a future route
must add reviewed request-rate enforcement without dropping audit evidence.

Keep command acceptance distinct from provider completion. The audit chain records `accepted` for a
durable command and `completed` only for a completed read. Provider execution outcome belongs to the
operation-event ledger.

## Alternatives considered

| Option | Benefit | Risk | Decision |
| --- | --- | --- | --- |
| Let the admin role query and update commerce tables | Short implementation | Excessive access and unreviewable mutations | Rejected |
| Treat command persistence as provider completion | Simple status | False completion after timeout or failure | Rejected |
| Add an admin microservice and queue now | Runtime isolation | Extra deployment and operations surface before need | Rejected |
| Safe views plus append-only commands and evidence | Small, auditable modular-monolith slice | UI and production credentials remain future work | Selected |

## Consequences

The admin service can read only reviewed commerce projections and append administrative evidence.
It cannot update or delete operations, audit events, payment facts, Credits, refunds, subscriptions,
or private journals. Runtime privilege attestation runs automatically and fails closed on direct
raw-table access, mutation authority, DDL authority, owner membership, or privileged-role drift.

The kernel is intentionally not exposed by an HTTP route and has no production passkey issuer,
Stripe Live executor, deployment, or customer-visible workflow. Those remain separate approval and
implementation gates.

## Validation

Focused unit, type, architecture, migration, and real PostgreSQL checks must prove owner-only access,
same-session passkey reauthentication, immutable timeline state, bounded reads, complete denial
evidence, concurrent idempotency convergence, replay across policy versions, executor failure and
retry, hash-chain audit verification, per-event evidence verification, raw-table denial,
append-only storage, and automatic privilege-drift shutdown.

## Rollout and rollback

Rollout remains limited to local and approved non-production Stripe Test environments after the
additive migration and focused gates pass. A later route must default off and require its own
reviewed passkey challenge/verification flow.

Rollback disables the future entrypoint and executors. Existing operations, attempts, outcomes, and
audit-chain records remain append-only and queryable; no destructive migration, payment-fact
rewrite, or audit deletion is permitted.
