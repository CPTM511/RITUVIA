# D-023: English-first locale-prefixed public shell

- Date: 2026-07-17
- Owners: frontend, localization, product
- Related tasks: RIT-010
- Evidence references: apps/web/app/_i18n/routing.ts, apps/web/app/_i18n/messages.ts, apps/web/app/[locale]/page.tsx, apps/web/proxy.ts, apps/web/test

## Context

The roadmap requires a useful English public shell now and global locale support later. Additional
language launches need owner approval and reviewed content, while unprefixed or silently inferred
routes would make canonical behavior, fallback, indexing, privacy, and future localization
ambiguous. The working brand is also configurable and not legally cleared.

## Decision

Version 1 activates only the exact BCP 47 locale `en`. When the existing server-side
`experience.public_shell` flag is explicitly enabled, `/` redirects to `/en`; disabled, invalid,
or unavailable flag state fails closed with 404. The dynamic locale segment uses an exact
allowlist, case-sensitive framework matching, and no dynamic fallback, returning 404 for every
unsupported or non-canonical spelling without generating arbitrary locale caches.
Components receive a complete typed English message catalog and the server-configured working brand.
Metadata derives its canonical origin from validated server configuration, emits self-referencing
English/x-default alternates, and permits indexing only in the production deployment environment.
Direction helpers and CSS logical properties prepare the shell for later reviewed RTL work without
activating or silently falling back to another language.

## Alternatives considered

| Option | Benefits | Costs/risks | Why not selected |
|---|---|---|---|
| Unprefixed English routes | Short initial URLs | Requires later canonical migration and conflicts with the locale architecture | Fails the current routing requirement |
| Infer locale from `Accept-Language` | Automatic personalization | Silent switching, unstable canonicals, unreviewed publication, and privacy ambiguity | Additional locales are not approved or complete |
| Activate placeholder locales | Exercises switching immediately | Mixed or machine-drafted language would be presented as live | Violates review and owner gates |
| Exact English allowlist | Stable URL, explicit behavior, simplest safe foundation | A later locale rollout must extend the catalog and allowlist deliberately | Selected |

## Consequences

The built shell has a stable localized URL and meaningful server HTML with no account or feature
claim, while request delivery remains safe-off until an explicit valid activation record exists.
Unsupported locales fail closed instead of silently mixing English or producing unbounded runtime
caches. Future locale work must add a complete reviewed catalog, tests, direction behavior, and
owner approval before extending the allowlist. Request-time locale choice is intentionally absent,
and non-production crawl behavior is conservative. No user data, payment state, or production
configuration is introduced.

## Validation

Unit and contract tests cover exact parsing, finite case-sensitive route artifacts, safe-off HTML
and RSC delivery, root/canonical paths, direction helpers, message completeness, server-rendered
landmarks, trusted metadata, source-copy boundaries, and local resource budgets. A production build
plus real-browser desktop/mobile/keyboard/zoom/no-JavaScript/RTL-assisted checks validates runtime
output. Reconsider when RIT-100/RIT-101/RIT-103 add complete reviewed locales, ICU workflow, RTL
coverage, localized slugs, and sitemap/redirect matrices.

## Rollout and rollback

This is a repository-local foundation with no remote or production rollout. Later locale additions
remain feature/owner gated. Roll back by reverting the RIT-010 commit and regenerating repository
evidence; no data migration or external reversal is required.
