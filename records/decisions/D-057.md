# D-057: Safe-off admin authorization and passkey-assurance foundation

- Date: 2026-07-25
- Owners: owner, backend, security, qa_security
- Related tasks: RIT-056, RIT-057
- Evidence references: apps/admin/AGENTS.md, docs/05_DATA_MODEL.md,

## Context

RIT-056 must establish server-authoritative admin roles, phishing-resistant MFA requirements,
recent reauthentication, and immutable audit evidence before any operational admin product is
built. The repository has secure account sessions and passkey storage, but production WebAuthn
registration/assertion, an admin application, support grants, and production role enrollment are
not approved or implemented. A magic-link session alone must never become admin authority.

## Decision

Define one dependency-free `@rituvia/security` policy catalog with the canonical roles owner,
content editor, support/refund reviewer, risk/safety reviewer, and analyst/read-only. Every action
is finite and default-denied. Only owner may assign or revoke roles in this foundation; the other
roles receive only their exact content, refund-review, safety-review, or analytics/audit-read
capability. No private-content read capability exists.

Persist role grants and revocations as append-only rows. Permit exactly one database-operator
bootstrap owner with no grantor, expose no application bootstrap method, reject duplicate active
roles, and prevent revocation of the final active owner. Every service-driven role change requires
an active account session, a runtime-supplied recent-authentication window, a still-live passkey
MFA assertion bound by composite foreign keys to the same user/session/auth identity/credential,
and exact typed confirmation. The repository issues no MFA assertion in production; WebAuthn
ceremony, RP/origin policy, challenge verification, sign-counter enforcement, admin enrollment,
and production TTL selection remain safe-off approval gates.

Execute authorization, role mutation, and audit append in one serializable transaction. Record
successful and denied privileged attempts with controlled action/reason codes, actor/session/role,
target identifiers, allow-listed changed field names, and before/after state digests only. Chain
events with predecessor and event SHA-256 hashes under a global transaction lock and uniqueness
constraints. Audit persistence failure rolls back the role mutation. The dedicated
`rituvia_admin_service` login can select only account-session/passkey/admin evidence and can insert
only role grants, revocations, and audit events; it cannot issue MFA assertions, update/delete/
truncate audit rows, or read private journals.

## Alternatives considered

| Option                                 | Benefits               | Costs/risks                                         | Why not selected                         |
| -------------------------------------- | ---------------------- | --------------------------------------------------- | ---------------------------------------- |
| Reuse ordinary Web database role       | Fewer credentials      | Broad unrelated data access and passkey mutation    | Violates least privilege                 |
| Treat magic link as admin MFA          | No new ceremony        | Phishable single factor                             | Explicitly prohibited                    |
| Activate WebAuthn now                  | End-to-end MFA         | Requires RP/origin/provider/enrollment approval     | Keep production activation safe-off      |
| Store raw before/after values          | Easier operator review | Can copy private data or credentials into audit     | Store fields and digests only            |
| Mutable role and audit rows            | Simple queries         | Weak revocation history and tamper evidence         | Append-only grants/revocations/events    |
| Add support private-content grants now | Broader admin utility  | Requires case/purpose/approval/expiry UX and policy | No private-content capability in RIT-056 |

## Consequences

The database and service can prove least-privileged role changes, recent reauthentication, matching
passkey assurance, atomic audit evidence, and immediate revocation without claiming that an admin
surface or production MFA exists. Future admin routes must use this service, add separate
origin/CSRF/rate/network controls, and implement an approved WebAuthn verifier that alone may write
MFA assertions. Future support access must add a narrow ticket/purpose/target/approver/expiry grant
rather than broad private-data permission.

## Rollout and rollback

The migration is expand-only and introduces no role or MFA assertion. Rollback keeps all admin
routes absent and stops using the dedicated login; do not delete audit evidence or role history.
Production bootstrap, role grants, WebAuthn activation, deployment, data mutation, or public launch
remain explicit owner gates.

## Validation

Focused policy tests cover the complete role/action matrix and default denial. The isolated
PostgreSQL gate covers migration replay, composite user/session/identity/passkey binding, singleton
bootstrap, ordinary-user denial, missing MFA, stale reauthentication, successful grant/revoke,
concurrent duplicate role conflict, final-owner protection, audit-failure rollback, hash-chain
verification, immutable privileges, private-table denial, and logical dump/restore.

## Sources and approvals

The canonical role names and admin security requirements already appear in the owner-approved PRD,
security specifications, and admin instructions. Exact production reauthentication/MFA durations,
WebAuthn RP/origin/provider configuration, initial production enrollment, audit retention,
deployment, and public launch remain owner decisions.
