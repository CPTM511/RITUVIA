# D-033: Owner-bound immutable tarot reading facts and safe-off API

- Date: 2026-07-17
- Owners: backend, architect, qa_security, product
- Related tasks: RIT-024, RIT-025, RIT-027, RIT-030, RIT-032, RIT-122
- Evidence references: packages/domain/src/tarot-reading.ts, apps/web/server/tarot-reading.ts, apps/web/server/tarot-reading-crypto.ts, apps/web/app/api/v1/readings/tarot/route.ts, apps/web/app/api/v1/readings/[readingId]/route.ts, packages/db/src/tarot-reading-persistence.ts, packages/db/prisma/migrations/202607170003_tarot_reading_persistence/migration.sql

## Context

RIT-023 proves deterministic draw behavior but deliberately leaves ownership, entropy sourcing,
keyed integrity, persistence, concurrency, limits, and HTTP semantics to an application boundary.
RIT-024 must establish those guarantees without allowing a client, AI model, raw intake question, or
publication-ineligible catalog to influence card facts.

The anonymous subject and session model already supplies fixed expiry and runtime revocation.
Reading persistence must preserve that privacy boundary, replay safely across key rotation and later
catalog changes, and keep unknown and cross-owner reads indistinguishable. The only repository tarot
catalog is synthetic internal validation content and is structurally ineligible for publication, so
an implemented API cannot imply that a useful production reading is approved or active.

## Decision

Accept exactly `tarot-reading-create.v1` with locale `en`, one-card or three-card reading type, and
one of the ten reviewed theme codes. Reject unknown properties, raw questions, intake results,
catalog/card/orientation selections, seeds, entropy, digests, histories, and any client-provided
execution fact. The Web service maps that narrow command to server-owned exact catalog, deck,
spread, rules, and orientation references.

Use Node's operating-system-backed cryptographic random bytes for every new execution. Derive the
client idempotency digest and canonical draw-request digest server-side. Bind the complete execution
with a versioned, domain-separated HMAC-SHA256 key ring covering the anonymous owner, database-issued
reading identifier, client/request digests, policy, exact catalog identity/version/checksum/approval,
draw facts, entropy counts, and engine/rules/algorithm/key versions. Never persist or log raw entropy,
HMAC keys, bearer tokens, raw questions, or free-text intake. Verify the complete historical envelope
before replay or public projection, and support bounded key rotation without recalculating facts.

Authenticate and lock the active anonymous session, resolve matching replay or conflicting reuse,
apply the database-clock subject limit, allocate the reading identifier, draw, and insert immutable
`reading` and `tarot_draw` rows inside one transaction. A matching replay occurs before current
catalog loading, limit consumption, or entropy use. Database constraints, restrictive grants, and
application validation jointly enforce exact ownership, expiry, versions, digest shapes, public
facts, and one immutable draw per reading. Reading expiry equals the anonymous subject expiry.

Expose only the canonical `POST /api/v1/readings/tarot` and `GET /api/v1/readings/{uuid}` contracts.
Responses contain reading metadata and verified public draw facts only; internal digests, audit
counts, owner/session identifiers, raw input, and cryptographic evidence never cross the API. Use
bounded exact JSON/media/origin/idempotency validation, no-store/noindex responses, safe Problem
Details, and the same redacted 404 for missing, invalid, unknown, expired, or cross-owner reads.

Keep production Web composition deliberately unavailable until a structurally eligible, exact
catalog and approval reference are independently supplied through a reviewed runtime adapter. Tests
may inject an eligible synthetic catalog, but the Git-authored internal fixture must never become a
runtime fallback. RIT-024 does not activate a route, publish content, deploy a migration, or consume
RIT-021 raw intake text.

## Alternatives considered

| Option                               | Benefits                   | Costs/risks                                                                   | Why not selected                               |
| ------------------------------------ | -------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------- |
| Derive draws from idempotency keys   | Easy deterministic retries | Client-predictable, rerollable, no CSPRNG authority                           | Retries must replay persisted facts            |
| Load current catalog before replay   | Simple composition order   | Old valid readings fail after retirement; unnecessary work leaks availability | Historical execution carries exact provenance  |
| Persist only public facts            | Smaller schema             | Cannot authenticate replay or detect damaged historical execution             | Internal audit remains server-only and bounded |
| Use the synthetic fixture at runtime | Immediate visible output   | Publishes incomplete, unapproved content by accident                          | Runtime must remain safe-off                   |
| Return owner/audit identifiers       | Easier debugging           | Expands private correlation and attack surface                                | Observability must not alter public contracts  |

## Consequences

The repository gains a complete local server-authority and persistence boundary for immutable tarot
facts. Exact retries consume no new entropy or quota; conflicts and limit failures are stable;
concurrent winners are determined before entropy use; key rotation and historical catalogs remain
verifiable; and public responses cannot expose internal audit material.

The API remains intentionally unavailable in normal runtime because there is no approved production
catalog. RIT-025 may build and test the one-card UI with an isolated test adapter, but a public useful
reading still requires independently reviewed content and activation. RIT-027 retains calm redraw
UX/report controls, RIT-032 retains intake-to-pre-generation safety, and RIT-122 retains broader
abuse/denial-of-wallet controls.

## Validation

Focused domain, crypto, service, proxy, and HTTP tests cover strict input, bounded transport, safe
errors, owner isolation, replay/conflict, key rotation, complete binding, damaged history, public
projection, runtime safe-off behavior, and route allowlisting. Real PostgreSQL 17 integration covers
clean/idempotent migration, owner/session authorization, duplicate and out-of-order operations,
concurrent first-writer behavior, limits, immutability, least privilege, and logical restore.
Repository lint, type, architecture, build, migration, record, generated-evidence, and secret gates
remain required. No browser gate applies because this task adds no UI.

## Rollout and rollback

No production deployment, runtime activation, catalog publication, or production migration is
authorized. Roll back the route/service/persistence code and the expand-only migration before any
retained reading exists. After a reading is persisted in any environment of record, retain the V1
parsers, verification key, and catalog provenance needed to replay it; disable new creation through
the safe-off composition rather than deleting historical contracts.
