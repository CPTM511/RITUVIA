# D-102: Use one source-bound metadata-only operational case kernel

- Date: 2026-08-01
- Owners: operations, privacy, qa_security, support, content
- Related tasks: RIT-074, RIT-120, RIT-125, RIT-128, RIT-130
- Evidence references: `packages/db/src/operational-cases.ts`;
  `packages/db/prisma/migrations/202608010002_operational_case_queue/migration.sql`;
  `packages/db/scripts/verify-operational-cases.ts`;
  `docs/runbooks/RIT-125_CASE_OPERATIONS.md`

## Context

RITUVIA already accepted bounded reading reports, privacy requests, and refund requests, but those
sources had no shared operational triage, SLA, escalation, or resolution timeline. Building four
independent case systems, copying private content into an admin database, or inventing a production
support promise would increase both code and privacy risk.

## Decision

Use one additive `operational_case_v1` kernel for `support`, `privacy`, `safety`, and
`content_report`. Every case is bound by a real foreign key to exactly one source record. New source
writes enqueue in the same application transaction; the database derives queue, category,
priority, local due times, draft template, and inherited expiry from that source. The migration
does not scan or backfill historical sources.

Store only bounded categorical metadata and append-only transition/audit evidence. Do not copy a
question, reading prose, interpretation, journal, prayer, birth data, attachment, email, provider
payload, or arbitrary support message. Listing and transitions require an allowed role, recent
authentication, same-session passkey MFA, reason code, and ticket reference. The admin service can
read case metadata and append events/audit but cannot mutate the case row or read source/private
tables. Drafts are fixed English acknowledgements marked `draft_only_not_sent`; no automation sends
them.

Use `protected-beta-operations.local.en.v1` only as a local acceptance policy. It is not a public or
production SLA. Final contact channel, operating hours, response/resolution commitments, retention,
escalation ownership, and automated delivery require separate Owner and applicable legal/provider
approval. RIT-120 may surface this kernel in the Owner dashboard without broadening data access.

## Alternatives considered

| Option | Benefits | Costs/risks | Decision |
| --- | --- | --- | --- |
| Four independent queues | Local specialization | Duplicate state, permissions, audit, and retention logic | Rejected |
| Copy source/private content into cases | Easier operator reading | Creates a new sensitive-content store and access path | Rejected |
| Database routines/triggers | Automatic enqueue | Conflicts with migration policy and hides authority | Rejected |
| One source-bound metadata kernel | Small, auditable, reusable | Operator UI and production policy remain separate | Selected |

## Consequences

The repository can now prove category-only intake, deterministic routing, stable ordering, local SLA
status, role separation, append-only transitions, immutable hash-chained audit, draft-only output,
least privilege, and logical restore. There is still no ordinary Support button, admin dashboard,
admin HTTP endpoint, external paging/status integration, production contact address, or production
SLA. Those omissions are explicit rather than hidden behind test data.

## Validation

RIT-125 must pass security authorization tests, package typechecks, migration policy, the isolated
PostgreSQL queue test, and affected source-workflow database tests. The isolated test must cover all
four queues, wrong-role denial, recent-auth/passkey enforcement, breached SLA calculation,
idempotent transitions, changed-request conflict, source/private-table denial, audit-chain
verification, and logical restore.

## Rollout and rollback

Roll out only to local or separately approved protected environments. Application rollback stops
new enqueue calls and operator service use while leaving additive source-bound records and audit
history intact. Removing tables, deleting cases, changing retention, backfilling historical
sources, activating a production support channel, or sending drafts requires a later reviewed
forward change and applicable Owner approval.
