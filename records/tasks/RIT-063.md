# RIT-063: First Fiat Hosted-Checkout Sandbox Adapter

- Backlog item: RIT-063
- Related records: D-091

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Create a Stripe Test Mode, one-time hosted-checkout slice that resolves an approved synthetic
United States USD product from immutable server catalog and Country Policy records, creates or
replays one v2 commercial order and payment attempt, and redirects only to a Stripe-hosted HTTPS
Checkout Session without granting paid state or fulfillment.

## Scope

Included: a dedicated v2 commercial-checkout persistence boundary; exact request idempotency;
server-owned product, amount, currency, terms, policy, and catalog snapshots; deterministic
provider idempotency; Stripe test Price verification through the existing gateway; a same-origin
JSON API for `POST /api/v1/checkout/stripe`; safe replay and provider-result attachment; focused
unit, route, configuration, PostgreSQL, and security evidence; and task/status documentation.

Excluded: live Stripe; production provider underwriting; subscriptions; signed webhook
processing; paid-state transitions; Credits or entitlement grants; product or return UX; refunds,
disputes, reconciliation, taxes, production Country Policy/catalog activation, deployment, DNS,
indexing, customer communication, or public launch.

## Acceptance criteria

- [x] Only Stripe Test Mode is accepted, and missing or live credentials fail closed.
- [x] Product, exact contents, amount, currency, refund terms, catalog version, price version, and
      synthetic US policy version are server-authoritative and persisted on the v2 order/item.
- [x] The same account, idempotency key, and canonical request replay one order, attempt, and
      unexpired checkout; a changed request with the same key conflicts.
- [x] Stripe receives one-time mode, exact server-owned amount/currency/product metadata, the
      configured test Price ID, and deterministic provider idempotency derived from the internal
      order and attempt.
- [x] Provider checkout identifiers and HTTPS URL attach atomically to the pending v2 records;
      retry after an interrupted attachment is recoverable without creating another Stripe
      Checkout Session.
- [x] The API requires an authenticated account, same-origin JSON request, bounded paths, a valid
      idempotency key, approved country/provider/product policy, and returns no-store `201` or an
      exact replay response without exposing internal database identifiers.
- [x] Redirect or return state cannot mark an order paid or create Credits/entitlements.
- [x] Focused package, Web, database, configuration, architecture, and evidence checks pass.
- [x] A real Stripe Test Mode call is either evidenced with securely configured test credentials
      and exact test Price IDs or explicitly remains an external dynamic-verification blocker.

## Risks and rollback

- Provider success followed by database attachment failure is controlled by deterministic Stripe
  idempotency and a retryable unattached attempt.
- Catalog, Country Policy, or provider configuration drift is controlled by exact immutable
  snapshots and fail-closed resolution before provider invocation.
- Redirect spoofing and open redirects are controlled by bounded same-origin paths and a
  server-owned canonical origin.
- Test/live confusion is controlled by explicit Test Mode key and Checkout Session validation.
- Redirect completion has no fulfillment authority; RIT-064 remains the only future signed-event
  processing path.

Rollout is code and synthetic/test evidence only. The new route remains unavailable unless
database, Stripe Test Mode configuration, approved catalog, and synthetic US policy are all
present. Rollback removes the route/service and leaves append-only created or checkout-created v2
records as non-paid audit evidence; it does not delete payment records or activate a fallback
provider.
