# RIT-162: Simplify the core-loop implementation and retire approved dead code

- Backlog item: RIT-162
- Related records: D-095

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Reduce the current change surface without rewriting the product or deleting any active caller,
historical replay path, privacy obligation, migration, audit trail, or rollback mechanism.

## Scope

Included: exact static and runtime caller analysis; database, migration, replay, export, deletion,
audit, rollback, route, flag, test, record, and generated-evidence review; removal of one uncalled
Worker wrapper and one byte-identical duplicate report; corresponding architecture-policy cleanup;
and classification of every other candidate as keep, consolidate, or quarantine.

Excluded: deleting local checkout, Stripe, historical tarot/ritual/journal projections, migration
history, privacy export/delete paths, birth profiles, Revisit reminders, golden screenshots, or the
authoritative production-pack source; broad module rewrites; database changes; production action.

## Acceptance criteria

- [x] Every candidate class in the Owner capability map has an exact dependency and durable-
      obligation classification.
- [x] Removed files have no static/runtime caller, route, flag, test, database, migration, replay,
      export, deletion, audit, or rollback obligation.
- [x] The duplicate report is byte-identical to the retained authority and is not referenced by
      current records or code.
- [x] Focused Worker, architecture, records, generated-evidence, link, and diff checks pass.
- [x] The production build and retained full-loop browser acceptance pass after deletion.
- [x] Backlog, project status, Owner map, engineering runbook, audit report, and generated evidence
      agree.

## Risks and rollback

The primary risk is mistaking inactive product scope for dead implementation while the code still
serves replay, privacy, payment, audit, or recovery. The audit therefore approves only two files
whose remaining references are mechanical allowlist/checksum entries.

Rollback restores the two deleted files and the two architecture exceptions from Git, removes the
RIT-162 audit/status additions, and regenerates repository evidence. No schema, persisted data,
golden screenshot, provider setting, deployment, DNS, or production state changes.
