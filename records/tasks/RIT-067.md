# RIT-067: Commercial Reconciliation and Discrepancy Cases

- Backlog item: RIT-067
- Related records: D-091, D-092

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Run one bounded, idempotent daily Stripe Test comparison that detects provider, internal order,
Credit issuance, fulfillment, and provider settlement-availability evidence differences; persists
digest-only append-only operations cases; and safely recovers only an exactly matched missed
successful webhook through the existing payment-event reducer and fulfillment outbox.

## Scope

Included: current Stripe Test Mode account; one-time US/USD Credit-pack orders; at most 100
provider Checkout reads per daily slot; provider API unavailable/missing states; amount, currency,
order, Checkout and PaymentIntent comparison; payment-state drift; missing, duplicate or
wrong-amount purchased-Credit grants; current fulfillment-state/version drift; missing
balance-transaction settlement evidence; append-only run/case evidence; alert-grade worker
outcomes; and exact missed-webhook recovery after the case commits.

Excluded: Stripe Live Mode; subscriptions; Coinbase; actual payout accounting or bank settlement;
refund initiation; dispute ingestion; automatic reversal or balance repair; admin case UI;
production provider activation; deployment; DNS; and public launch.

## Acceptance criteria

- [x] A scheduled run is bounded to 100 candidates, idempotent for an unchanged observation within
      each configured account/UTC-day slot, rotates overflow windows, and marks truncation.
- [x] Provider API failure is distinct from a missing provider payment and never becomes an
      unpaid/failed assertion.
- [x] Amount, currency, public order, Checkout, PaymentIntent, payment state, purchased-Credit
      grant count/amount, fulfillment status/version, and provider balance-transaction availability
      evidence are compared; payout or bank-settlement accounting is not claimed.
- [x] Every difference creates a digest-only append-only case without raw provider payload,
      customer identity, journal, prayer, birth, question, or other private content.
- [x] A missed paid webhook repairs internal state only after the case commits and only when Test
      account, order, Checkout, PaymentIntent, amount and currency match exactly.
- [x] Repair reuses the existing serializable payment timeline/outbox path, so webhook races cannot
      create a second payment transition or Credit grant.
- [x] Other discrepancies never mutate orders, attempts, Credits, projections, fulfillment or
      entitlements.

## Risks and rollback

Primary risks are accepting untrusted provider observations as payment authority, duplicate cases
under worker retries, false missing-payment assertions during provider outages, scan starvation,
private metadata leakage, and a reconciliation repair racing a signed webhook. The worker reads
only the configured Stripe Test account, separates unavailable from missing, rotates bounded daily
windows, stores normalized digests only, commits its case before repair, and delegates any exact
repair to the existing serializable payment-event reducer.

Rollback stops the reconciliation loop while leaving append-only runs, cases, provider events and
outbox evidence intact. The additive migration does not rewrite an existing money fact and needs
no destructive rollback. The Web source-map setting can be removed independently if production
debugging later requires mapped server stacks.
