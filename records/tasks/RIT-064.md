# RIT-064: Signed Payment Webhook Ingestion and Processing

- Backlog item: RIT-064
- Related records: D-091

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Accept Stripe Test Mode Checkout Session webhooks only after raw-body signature and replay-window
verification, persist immutable account-bound event evidence, deterministically recompute payment
state under duplicate and out-of-order delivery, and publish state changes to a transactional
outbox without granting Credits or entitlements.

## Scope

Included: a stable configured Stripe account identity; account-bound v2 checkout attempts; an
additive signed-event inbox and transactional state-change outbox; exact raw-payload digests,
signature timestamps, verifier and normalization versions; provider-event idempotency; altered
same-ID conflict handling; deterministic full-timeline replay; order, amount, currency, Checkout
Session, payment-intent, environment, and provider-account matching; composite order/attempt
foreign keys; a dedicated webhook database role; monotonic payment-state versions; serializable
concurrency retries; leased outbox claim, completion, retry, final-lease recovery, and dead-letter
contracts; a same-database/different-credential DSN binding; runtime least-privilege attestation;
shared Stripe account startup proof; a direct raw-body Stripe route; and focused unit, route,
PostgreSQL, configuration, privilege, and build evidence.

Excluded: live Stripe; production provider activation; secondary provider-object retrieval during
webhook receipt; active refund or dispute event routes; Credits or entitlement fulfillment;
subscriptions; reconciliation; refund requests; outbox business consumers; deployment; and public
launch. The active Stripe runtime accepts only Test Mode `checkout.session.completed`,
`checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, and
`checkout.session.expired`; later payment tasks own refund, dispute, fulfillment, and
reconciliation behavior.

## Acceptance criteria

- [x] The Stripe route preserves the exact raw body and accepts only a valid bounded
      `Stripe-Signature` envelope inside the five-minute replay window.
- [x] Live-mode events and unsupported event types fail closed before provider-object network
      retrieval; a stable configured Stripe account ID, rather than a rotating secret-key digest,
      binds checkout attempts and webhook processing; Node startup proves the current Test Mode key
      belongs to that account before webhooks become available, and checkout repeats the cached
      proof defensively.
- [x] The inbox stores raw-payload digest, provider event/object/timestamps, signature timestamp,
      verifier version, normalization version, claimed order, amount/currency, and matched
      order/attempt references without storing secrets or full provider payloads.
- [x] Exact duplicates return duplicate without another state change or outbox row; an altered
      payload reusing the same provider event identity conflicts.
- [x] Serializable processing and deterministic full-timeline reduction handle concurrent
      duplicate and out-of-order delivery while preserving valid late success.
- [x] Account, Checkout Session, amount, currency, payment-intent, or order mismatches are
      persisted as rejected evidence and cannot mutate payment state.
- [x] Composite foreign keys prevent an event or outbox row from crossing order and payment
      attempt boundaries.
- [x] State changes increment one monotonic order version and create one transactionally bound
      outbox row with bounded lease, completion, retry, final-lease recovery, and dead-letter
      operations.
- [x] Webhook processing creates no Credit ledger entry or entitlement and cannot activate
      production payments; configuration binds a distinct dedicated-role DSN to the same database,
      rejects percent-encoded equivalent credentials, and runtime privilege attestation rejects any
      other role or whole-table/column-level Credit or entitlement access.

## Risks and rollback

The primary risks are forged signatures, replay, same-ID payload collision, wrong-account
delivery, cross-order binding, out-of-order transition regression, and granting value from an
unverified redirect or event. Raw signature verification, stable account identity, immutable
payload digests, uniqueness, composite foreign keys, serializable transactions, deterministic
timeline replay, and zero-fulfillment assertions control those risks.

The outbox business consumer and deployment topology remain later-task concerns, while this slice
is Test Mode and production-safe-off. Rollback disables the Stripe webhook route and dedicated
database connection, then stops new inbox/outbox writes. Existing append-only payment evidence
remains retained; rollback does not delete payment records, grant value, activate another
provider, or reverse customer funds.
