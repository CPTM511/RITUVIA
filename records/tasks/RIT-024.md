# RIT-024: Tarot reading application service and API

- Backlog item: RIT-024
- Related records: D-028, D-029, D-030, D-031, D-032, D-033

The queue state, priority, milestone, dependencies, and owner gates remain canonical in

## Outcome

The repository can validate a narrow theme-only tarot command, create and persist an immutable
owner-bound server-authoritative draw with OS entropy and keyed integrity, safely replay it under
concurrency and key rotation, and expose only verified public facts through canonical no-store APIs.

## Scope

Included: strict V1 application command; server-owned policy/catalog mapping; OS CSPRNG; canonical
server-derived digests; domain-separated HMAC execution binding and rotation; anonymous-owner
authorization; database-clock limits; transactional idempotency, draw, and persistence; immutable
`reading` and `tarot_draw` schema; owner-scoped historical GET; safe HTTP errors and transport
limits; exact proxy allowlisting; hard safe-off runtime composition; unit, HTTP, build, architecture,
and real PostgreSQL integration evidence; and durable records.

Excluded: raw question/intake consumption, interpretation prose or AI, UI, redraw/report UX,
analytics, notification/reminder behavior, a production content corpus, catalog publication,
runtime activation, production migration application, deployment, and public launch.

## Acceptance criteria

- [x] Creation accepts only the exact theme-only V1 command and rejects unknown, private,
      client-selected, entropy, digest, or historical-execution fields.
- [x] Every new draw uses operating-system CSPRNG entropy and a versioned domain-separated keyed
      binding across owner, reading ID, request/policy, exact catalog approval/checksum, facts,
      counts, and algorithm versions; raw entropy and keys are never persisted or exposed.
- [x] One transaction authenticates and locks the active owner session, resolves replay/conflict
      before limit or entropy use, applies atomic limits, allocates the reading ID, and inserts one
      immutable reading/draw pair whose expiry matches the anonymous subject.
- [x] Matching retries replay verified historical facts across key rotation and current-catalog
      changes; changed or damaged executions fail closed; concurrent attempts select one winner
      before entropy consumption.
- [x] Canonical create/read APIs expose only reading metadata and verified public facts, reject
      unsupported transport/input, use safe Problem Details, and make invalid/unknown/cross-owner
      reads indistinguishable.
- [x] Runtime composition is hard unavailable without an independently eligible production catalog;
      the synthetic internal fixture cannot activate or publish the API.
- [x] Focused tests, real PostgreSQL integration, strict types, lint, architecture, production build,
      migration/record/generated-evidence/secret gates, and independent P0/P1 review pass. No UI or
      browser gate applies.
- [x] Backlog, project status, decision/task records, record index, compiled manual, and checksums
      reflect the final verified slice.

## Risks and rollback

The cryptographic commitment authenticates repository execution evidence; it is not a public proof
of randomness or a substitute for operational key management. A production key must be stored and
rotated through approved secret infrastructure, with old verification keys retained for the data
retention window. Rate limits here are a domain policy, not the complete abuse/denial-of-wallet
system assigned to RIT-122.

The only current catalog remains synthetic and publication-ineligible, so normal runtime deliberately
returns unavailable. RIT-025 can use isolated test composition for UI development but cannot claim a
production-quality reading. No production database or customer data was changed. Roll back by
removing the service/routes/schema additions and the expand-only migration before retained data
exists; once executions exist, preserve V1 verification contracts and disable creation through the
safe-off composition instead.
