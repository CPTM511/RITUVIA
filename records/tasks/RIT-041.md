# RIT-041: Ritual template and object domain

- Backlog item: RIT-041
- Related records: D-047

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Publish one framework-independent, source-governed, versioned ritual template and item catalog
that always contains dignified free candle and incense experiences, distinguishes permanent
objects from consumable ritual passes, and makes spiritual efficacy or stronger paid outcomes
impossible to express in the accepted contract.

## Scope

Included: strict publication, template, item, access, interaction, accessibility, completion,
source, legacy-mapping, and presentation-enhancement value objects; an immutable Git-authored
English catalog adapted from the production pack; exact-version lookup; a public read-only API
projection that carries no price or Credit authority; and domain, route, compatibility, build,
architecture, localization-key, and negative-claim tests.

Excluded: the immersive Sanctuary interface; ritual start/pause/resume/completion state; session
template/version and access snapshots; entitlement/pass reservation or consumption; audio or
animation assets; journal changes; purchases, pricing, Credit costs, entitlement grants,
subscriptions, production content activation, additional traditions, additional locales,
deployment, and public launch. RIT-042 owns the accessible Sanctuary experience and RIT-043 owns
durable ritual completion and transactional session provenance.

## Acceptance criteria

- [x] Every accepted template has an immutable schema/code/version, bounded interaction steps,
      explicit duration/audio/motion behavior, a linear accessibility equivalent, and reflective
      completion rather than an external-outcome claim.
- [x] Every accepted item has an immutable schema/code/version, exact template and approved
      publication references, localization keys, symbolic-only scope, and exactly one free,
      permanent-entitlement, or consumable-pass access kind.
- [x] `free_candle` and `free_incense` remain active free objects; permanent objects and consumable
      rituals use the production-pack code sets and can differ only through enumerated art,
      animation, audio, arrangement, duration, memory, collection, or persistence dimensions.
- [x] Unknown fields, arbitrary scripts/copy, prices, payment authority, traditions, efficacy,
      certainty, protection, stronger-power, or external-result fields cannot enter the accepted
      contract.
- [x] The public API returns only the validated current catalog without price, Credit, payment, or
      ownership authority; historical `reflection-ritual.v1` codes remain unchanged and resolve
      only through explicit replay mappings, including `golden_intention_bowl` to `golden_bowl`.
- [x] Focused tests plus formatting, lint, type checking, architecture, unit, configuration,
      database, build, accessibility, evidence, instruction-pack, and secret gates pass.

## Verification evidence

Task-entry review found six historical ritual object codes and two always-free codes embedded in
the reflection contract, four paid object codes duplicated in commerce entitlement logic, and
unversioned object selection in the historical `reflection-ritual.v1` request. The production pack
instead defines `free_candle`, `free_incense`, four permanent objects, five consumable rituals, and
the corrected `golden_bowl` code. The current commerce catalog versions legacy paid products but
does not define free objects, ritual templates, pass access, accessibility behavior, source
classification, or an efficacy-proof item contract.

Closure evidence validates 11 canonical items, eight immutable templates, six explicit historical
replay mappings, 55 focused tests, 1,526 full unit/contract tests, 145 AI release assertions, 301
architecture-audited source files, 13 immutable migration-policy files, 83 production build
artifacts/exports, all PostgreSQL foundation matrices, and 39 production-artifact axe scans across
four public and three private routes. The read-only route was verified in the production build;
the new catalog remains disconnected from historical ritual-session creation and payment access.

## Risks and rollback

The primary risks are silently reinterpreting legacy codes, conflating permanent ownership with
single-use passes, accidentally presenting paid items as more spiritually effective, accepting
arbitrary copy or cultural claims, mutating a published version, or breaking historical v1 ritual
requests. The implementation must therefore use exact parsers, closed enums, fixed symbolic-only
safety values, strict unknown-field rejection, approved source metadata, immutable versioned
definitions, and explicit historical mappings.

Rollback removes the new public route and stops exporting the unused catalog while retaining the
historical reflection v1 codes and behavior. No database data, payment state, entitlement,
production content, or customer-facing deployment requires rollback.
