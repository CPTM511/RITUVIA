## Outcome

Reuse each immutable matched payment dispute fact and asynchronously project every current,
fulfilled Credit Pack dispute into one immutable privacy-minimal high-priority support work item
without changing the existing Credit hold/refund authority or activating any provider/user/admin
surface.

## Scope

Included: additive immutable support-projection table, payment-event foreign key, RLS, exact runtime
grants, independent retrying Worker projector, fixed template/SLA metadata,
duplicate/current-state behavior, database verification, runbook, and records. Excluded: a
duplicate dispute table, a second mutable case state machine, user/admin buttons,
free-form evidence, journals/prayers/questions/readings/intentions/birth data, chargeback response,
provider API/network, credentials, win/loss outcome, Live Mode, pricing, paid UI, deployment, and
production migration.

## Acceptance criteria

- [x] Existing matched, processed `payment_disputed` rows remain the sole dispute facts.
- [x] Only applied signed events with completed matching outbox/current order/current Credit Pack
      fulfillment state are eligible for a current support work item.
- [x] Ignored-out-of-order, mismatched, unfulfilled, stale-version, subscription, and already-
      refunded observations do not open a current work item.
- [x] Duplicate delivery and projector replay create no second support work item.
- [x] An independent retrying loop creates one immutable high-priority work item with fixed 4-hour
      first-response and 24-hour resolution targets and a draft-only acknowledgement.
- [x] Support persistence failure cannot roll back payment ingestion, order state, fulfillment,
      Credit hold, or review shortfall.
- [x] Disputes and projections contain no private journal or reflective content and expose no automatic
      send/provider/refund/account action.
- [x] The payment-fulfillment role receives only exact projector columns and cannot read provider
      object/amount/payload details or private journals, or mutate support projections.

## Risks and rollback

This slice projects a current support work item from an existing dispute fact; it does not know
provider win/loss state and must not be presented as a completed chargeback response. Projection is
eventually consistent, and an outage must alert/retry without blocking payment correctness. The
fixed local SLA is repository operating metadata, not a public support promise. Rollback stops the
projector and retains immutable facts; any record deletion or production migration rollback
requires a new reviewed forward migration and Owner approval.
