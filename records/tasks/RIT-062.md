# RIT-062: Commercial Transaction and Credits Foundation

- Backlog item: RIT-062
- Related records: D-061

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Provide provider-neutral, server-authoritative order, payment-attempt, Credit
ledger/reservation/projection, and entitlement contracts that preserve exact catalog and policy
snapshots, reject illegal transitions, prevent concurrent overspend, and leave all external
payment and value-fulfillment paths safe-off for later tasks.

## Scope

Included: canonical order and payment-attempt state unions; exact duplicate/out-of-order
transition behavior; exact canonical-request idempotency resolution; deterministic Credit
allocation in subscription, promotional, then purchased order; nonnegative projections;
append-only linked grant/reserve/release/consume/reverse/expire entries; hard-expiry reservations;
permanent/Plus entitlement source separation; an additive v2 PostgreSQL transaction schema; RLS
and least-privilege writes; real PostgreSQL concurrency, constraint, migration replay, and logical
restore evidence; and canonical task/status/decision updates.

Excluded: Stripe/Coinbase checkout creation; signed provider webhook ingestion; provider-event
storage/processing; automatic Credit or entitlement fulfillment; subscription periods; checkout
or account UX; refund requests; reconciliation/outbox workers; production policy/catalog/provider
activation; real money/crypto collection; deployment; public launch; and modification of legacy
local-commerce replay records.

## Acceptance criteria

- [x] Order and payment-attempt state machines use finite canonical unions, preserve valid late
      success, and record duplicates or out-of-order refund/dispute events without illegal
      transitions.
- [x] Exact idempotency distinguishes create, exact replay, and same-key changed-request conflict;
      database uniqueness covers orders, payment attempts, reservations, ledger operations, and
      entitlements.
- [x] Credit allocation consumes subscription, promotional, then purchased sources; expired
      sources are excluded and projection arithmetic cannot become negative.
- [x] Credit ledger entries are append-only, positive integers, direction/source linked, and
      support reserve/release/consume/reverse/expire evidence without representing money,
      transfer, withdrawal, or cash value.
- [x] Permanent-object and Plus entitlements require different authoritative source kinds, remain
      uniquely owner/fulfillment scoped, and support pending/active/frozen/revoked projections.
- [x] Real PostgreSQL evidence proves 20 concurrent one-Credit requests against six available
      Credits accept exactly six, application roles cannot update/delete the ledger, invalid
      crypto/state/source rows fail, migrations replay, and logical dump/restore succeeds.
- [x] Focused unit/property, database, type, formatting, lint, architecture, migration,
      CI-contract, secret, record, generated-evidence, and affected-build gates pass without
      repeating the complete workspace suite.

## Planned files and verification

Primary areas are the provider-neutral Payments transaction domain, an additive v2 commercial
transaction migration and Prisma model, local/CI least-privilege role provisioning, one isolated
PostgreSQL gate, canonical data/payment documentation, and task/decision/status evidence.

Run pure transition/allocation properties first, then the isolated PostgreSQL migration,
concurrency, privilege, and restore gate. Close with affected formatting, linting, type checking,
architecture, migration, CI-contract, secret, record, generated-evidence, and package builds. The
complete provider/payment integrity matrix remains reserved for RIT-069.

## Risks and rollback

Main risks are reusing the obsolete direct-object USD model, treating payment attempts as
refund/dispute aggregates, allowing changed-request idempotency replay, mutable Credit history,
negative projections, cross-source entitlement grants, or accidentally enabling an unapproved
provider. Rollback stops v2 writes and leaves append-only v2 evidence unused; it does not delete
historical or new rows. Provider onboarding, prices, legal/tax/refund policy, production
migrations, deployment, and launch remain owner gates.
