# RIT-040: Intention domain and composer

- Backlog item: RIT-040
- Related records: None

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Let an anonymous or signed-in owner write one private, agency-based intention and small action,
optionally link it to an owned Tarot reading, choose a revisit date without activating delivery,
and safely edit, complete, archive, or delete the intention from the accessible Sanctuary
composer.

## Scope

Included: a backward-compatible strict v2 intention contract; private-by-default intention text;
deterministic coercive-control detection and a theme-safe self-owned rewrite; optional revisit
date with an IANA time zone; an explicit no-reminder default; owner-scoped optimistic mutations;
active, completed, archived, and soft-deleted lifecycle states; additive encrypted persistence;
least-privilege runtime access; PATCH/DELETE resource behavior; and focused domain, persistence,
API, component, PostgreSQL, privacy, accessibility, RTL, narrow-layout, offline, and error tests.

Excluded: notification channel capture or delivery; quiet hours; scheduled jobs; revisit
comparison; retention-policy changes; physical deletion of rows referenced by rituals or journals;
account history; analytics; payment changes; AI generation; production activation; deployment; and
public launch. RIT-044 owns revisit scheduling/comparison behavior and RIT-045 owns consented
transactional reminder delivery.

## Acceptance criteria

- [x] A strict v2 create request accepts normalized user-owned intention text, one small action, an
      optional owned reading, an optional future revisit date and valid IANA time zone, private
      privacy state, and an explicit no-reminder preference without weakening v1 historical reads.
- [x] Deterministic policy rejects attempts to control another person's feelings or actions and
      returns a reviewed theme-specific self-owned rewrite without echoing private text in errors,
      logs, analytics, or public metadata.
- [x] Intention text and small action are independently encrypted with owner/resource-bound
      contexts; plaintext is absent from database rows, request digests, error details, and
      operational evidence.
- [x] Owner-scoped optimistic mutations support edit, complete, archive, and soft delete; stale or
      changed replay conflicts, unknown/cross-owner/deleted reads remain indistinguishable, and
      archive/delete cannot start a new ritual.
- [x] The Sanctuary composer exposes templates, privacy and reminder disclosures, revisit input,
      loading/success/error/offline states, keyboard-safe editing, and explicit confirmations for
      archive/delete at 320px, RTL, reduced motion, and WCAG 2.2 AA.
- [x] An expand-only migration preserves v1 rows, constrains v2 lifecycle and ciphertext fields,
      grants only required columns, and passes migration, ownership, concurrency, negative
      constraint, logical restore, and rollback-policy verification.
- [x] Formatting, lint, type checking, unit tests, AI release evals, configuration-boundary,
      database-foundation, production build, accessibility, evidence, and production-pack gates
      pass without production access or paid services.

## Risks and rollback

The primary risks are breaking strict v1 idempotency/replay, decrypting with the wrong resource
binding after edits, allowing stale lifecycle transitions, leaking private text through policy
feedback, or physically deleting a row still referenced by a ritual or journal. The
implementation therefore keeps v1 parsing/projection intact, introduces explicit v2 contracts,
uses resource-bound authenticated encryption, requires optimistic revisions and operation IDs,
returns reviewed non-echoing reframes, and uses immediate owner-hidden soft deletion.

Rollback disables v2 create/mutation handling and removes unused grants through a forward
migration while preserving nullable additive columns and any already-created private records until
an owner-approved retention policy removes them. Production deployment, destructive deletion, and
retention changes remain separate owner gates.
