# RIT-050: Authentication provider abstraction and secure account sessions

- Backlog item: RIT-050
- Related records: D-029, D-052

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Harden the existing local-only passwordless account foundation into a provider-replaceable,
enumeration-safe, rate-limited, provider-neutral session boundary that can accept a future passkey
identity without changing the account-session model.

## Scope

Included: a typed authentication-provider capability contract; local magic-link preview delivery
that remains hard-disabled outside local development; uniform accepted start responses independent
of account existence; privacy-minimal database-backed start limits using keyed identifier digests
and a global capacity bound; short-lived one-time hashed challenges; fresh session creation and
same-account previous-session revocation; host-only secure cookies; session-bound CSRF for account
mutations, logout, logout-all, and targeted session revocation; owner-scoped session summaries and
revocation; additive passkey credential persistence constraints; focused unit, route, database,
configuration, security-negative, and browser evidence.

Excluded: production email-provider selection or activation; email delivery credentials; OAuth,
Google, Apple, WebAuthn registration/assertion ceremony, or wallet/SIWE implementation; payment
wallets; anonymous-to-account merge changes owned by RIT-051; account/settings redesign owned by
RIT-052; legal retention changes; production deployment; public launch; and golden screenshot
updates.

## Acceptance criteria

- [x] Authentication providers expose a closed capability contract, and the local preview adapter
      cannot activate outside the local environment.
- [x] Magic-link starts validate bounded input but return the same accepted status and body for
      existing and unknown valid emails without returning the email or raw token.
- [x] Database-atomic identifier and global limits return a bounded retry interval without storing
      plaintext email, IP address, user agent, or device fingerprint.
- [x] Challenges are short-lived, one-time, hashed at rest, replay-safe, and create a fresh
      provider-neutral account session while revoking only a same-account prior session.
- [x] Account cookies are host-only, `Secure`, `HttpOnly`, `SameSite=Strict`, fixed-expiry bearer
      cookies, and state-changing account/session routes require a valid session-bound CSRF token.
- [x] Current, all, and owner-selected session revocation plus logout are idempotent, clear the
      browser cookie where applicable, and do not expose another account's session existence.
- [x] Additive passkey credential constraints preserve credential uniqueness, RP binding, public
      key material, sign-count state, and owner linkage without activating WebAuthn.
- [x] Focused format, lint, type, architecture, migration, secret, unit, database, and real-browser
      gates pass with no critical/high security finding.

## Risks and rollback

Main risks are account enumeration, login flooding, magic-link replay, session fixation, CSRF,
cross-account revocation, exposing local callback material outside local development, accidental
collection of network fingerprints, and creating an unusable schema for passkeys. Rollback
disables the account identity configuration and reverts application use of the additive columns
and table; the expand-only migration may remain inert. Dropping identity data, changing retention,
activating a provider, or mutating production data requires separate owner approval.
