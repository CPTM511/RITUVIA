# RIT-068: Refund Request and Stripe Sandbox Refund Path

- Backlog item: RIT-068
- Related records: D-093

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Provide one owner-scoped, full unused-Credit refund request for the exact US/USD Stripe Test Mode
pack, while keeping purchased Credits nonspendable before the provider call and treating only the
matched refund event plus fulfillment outbox as confirmation.

## Scope

Included: authenticated same-origin request; exact no-body and idempotency contracts; server-owned
amount, reason and provider object; versioned US/USD/Stripe/Test/Credit-pack/refund-policy
eligibility; request-time Credit hold; deterministic Stripe idempotency; definitive rejection
release; ambiguous-failure replay; provider-submitted versus provider-confirmed states; signed
refund-event linkage; source-linked reversal; privacy export; owner isolation; least privilege;
and refund-versus-reservation concurrency.

Excluded: Stripe Live Mode; partial refunds; subscriptions; Coinbase; user-entered amount or
reason; automatic legal-policy activation; production migration; public launch; admin/support UI;
and final refund, tax, terms, or country approval.

## Acceptance criteria

- [x] Only the active owner of an eligible paid one-time Credit pack can request a refund.
- [x] Eligibility is bound to the exact synthetic US/USD Stripe sandbox Credit-pack and
      `local.refund.v1`; used, reserved, held, reversed, shortfall, unpaid, disputed, partial, and
      completed states fail closed.
- [x] A serializable transaction creates one request and source-linked hold, then moves the exact
      purchased Credits from available to held before Stripe is called.
- [x] Client and provider idempotency are separate; twelve concurrent exact requests converge on
      one request and one hold, while changed authority conflicts.
- [x] A definitive Stripe rejection releases the hold; an ambiguous outage retains it and exact
      replay authority.
- [x] Stripe API acceptance records only `submitted`; the matched refund event and fulfillment
      outbox record `confirmed` and append one linked Credit reversal.
- [x] Duplicate success events cannot regress `refund_requested` to `paid`, and a refund webhook
      arriving before the API response converges safely.
- [x] Refund-versus-reservation concurrency has one winner and never creates a negative projection.
- [x] Privacy export includes user-readable refund/hold evidence without private payloads,
      idempotency hashes, or internal confirming-event identifiers.

## Risks and rollback

Primary risks are double refund, refund after Credit use, provider timeout after acceptance,
webhook/API reordering, duplicate or stale payment events, cross-owner linkage, privilege drift,
and falsely reporting completion. Exact owner/composite keys, source allocation evidence,
serializable projection locking, durable request/hold state, provider idempotency, matched payment
events, and source-linked fulfillment contain those risks.

Ambiguous requests remain intentionally held and retryable; later support/admin work must surface
them without inventing a provider result. Rollback disables the route and provider adapter method.
The additive request, hold, event, and ledger evidence remains intact.
