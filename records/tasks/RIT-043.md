# RIT-043: Transactional ritual completion and private journal

- Backlog item: RIT-043
- Related records: D-047, D-048

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Replace the temporary final-only historical ritual write with an owner-scoped durable lifecycle
that snapshots the exact approved catalog item, template, and access rule at start; atomically
consumes at most one eligible ritual pass; persists pause, resume, completion, and expiry/abandonment
without impossible transitions; and creates, updates, reads, and deletes an encrypted private
journal entry linked to the completed ritual.

## Scope

Included: strict versioned ritual start, lifecycle-mutation, journal-create, and journal-mutation
contracts; backward-readable historical v1 resources; additive v2 ritual, journal, and
ritual-pass tables; exact catalog/item/template/publication/access snapshots; free,
permanent-entitlement, and consumable-pass start authorization inside the session transaction;
single-winner pass consumption; owner/resource-bound state transitions with optimistic revision and
idempotent replay; encrypted journal text with resource-bound authenticated encryption; owner-only
GET/PATCH/DELETE; same-origin and session-bound CSRF enforcement; stable browser retry keys;
Sanctuary start/pause/resume/complete/leave-as-pause and journal create/edit/delete integration; failure,
offline, expired, cross-owner, and deleted behavior; PostgreSQL race/constraint/privilege/restore
evidence; and focused API, browser, privacy, accessibility, and full quality gates.

Excluded: selling or granting consumable passes through Credits or checkout; changing live payment
products; refill/reversal/refund policy for passes; a general Credit ledger redesign; revisit
scheduling or completion; notifications; analytics; export/account-wide deletion; production
activation; deployment; new locale activation; and changes to the owner-gated visual baseline.
RIT-044 owns revisit scheduling, RIT-046 owns privacy-safe analytics, and later commerce tasks own
pass issuance and reversal.

## Acceptance criteria

- [x] Starting a canonical ritual resolves one active approved catalog item and snapshots exact
      catalog, item, template, publication, and access versions; the client supplies no access,
      entitlement, pass, price, or completion authority.
- [x] Free starts work for an active anonymous or account owner; permanent objects require the
      linked account's active entitlement; consumable rituals require an available matching pass
      and consume exactly one pass in the same transaction that creates the session.
- [x] Concurrent starts against one pass produce exactly one session and one consumed pass;
      same-key replay returns the same session, changed reuse conflicts, and failed/rolled-back
      starts leave the pass available.
- [x] Active, paused, completed, and abandoned lifecycle transitions are owner-scoped,
      revision-checked, idempotent, timestamp-consistent, expiry-bounded, and reject impossible or
      cross-owner transitions without exposing resource existence.
- [x] A journal entry can be created only for the same owner's completed ritual and linked
      intention, is encrypted with resource-bound authenticated context, supports optimistic
      update and soft deletion, and never exposes ciphertext, owner IDs, keys, or deleted plaintext.
- [x] Every cookie-authenticated mutation requires exact same-origin evidence and a valid
      session-derived CSRF token; bounded bodies, strict schemas, no-store/noindex responses, safe
      Problem Details, and indistinguishable private not-found behavior remain enforced.
- [x] The Sanctuary uses durable start/pause/resume/complete behavior, treats visible exit as a
      durable pause rather than terminal abandonment, preserves the current
      step and private journal text across offline/error retry, uses stable idempotency keys, and
      exposes accessible success, conflict, expired, deleted, and retry states without outcome or
      paid-efficacy claims.
- [x] PostgreSQL and browser evidence cover free start/completion, pause/resume, abandonment,
      permanent access, pass races, rollback, replay/conflict, CSRF, IDOR, encryption, edit/delete,
      private canaries, reduced motion, keyboard, 320px, RTL, axe, console, request, and storage

- [x] Formatting, lint, type checking, architecture, unit, AI-eval, configuration, migration,

## Risks and rollback

The primary risks are double-consuming a pass, creating a session without durable access evidence,
accepting a stale catalog or client-selected access rule, crossing owner boundaries, reviving an
expired/deleted resource, losing private text on a transient failure, weakening historical replay,
or leaking journal plaintext into errors, logs, analytics, browser storage, screenshots, or payment
metadata.

The implementation therefore treats catalog resolution as server authority, validates the exact
snapshot again at persistence entry, locks and updates a matching pass inside the session
transaction, keeps every mutation revisioned and idempotent, binds ciphertext to the owner and
journal resource, and retains historical v1 rows and projections. Rollback disables the new v2
routes/UI path and leaves the additive columns/table unused; no historical row is rewritten and no
pass issuance or production customer data exists in this local slice.
