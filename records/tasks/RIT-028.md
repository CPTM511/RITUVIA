# RIT-028: Deterministic tarot browser acceptance matrix

- Backlog item: RIT-028
- Related records: D-027, D-028, D-034, D-035, D-036

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Turn the existing anonymous one-card and three-card flows into durable, deterministic
production-artifact browser evidence that proves the fixed result, recovery, resume, categorical
reporting, accessibility, responsive layout, and local-only privacy boundary without activating a
production catalog or adding product behavior.

## Scope

Included: exact one-card and three-card theme-only request ledgers; separate session, reading, and
report idempotency; fixed card/orientation/position assertions; explicit reveal with zero redraw;
keyboard and focus behavior; mobile and desktop reflow; RTL, expanded text, dark mode, reduced
motion, touch targets, and axe coverage; offline zero-request behavior; service-failure manual
same-key retry; calm rate-limit behavior; same-tab UUID-only refresh resume; stale private-result
clearing; whole-reading and canonical-position categorical reports without free text; deterministic
screenshots; local-only network, console, HTTP, and storage checks; CI integration; and durable
verification/status evidence.

Excluded: production catalog publication or activation; AI/provider/reviewer/model behavior beyond
retaining the already accepted separate M3 gate; new UI, route, API, storage, report, retry, quota,
or persistence behavior; cross-tab, cross-device, account-history, or offline-result caching;
production data, migration, deployment, public launch, payment, Credits, analytics, another locale,
pixel-perfect cross-platform screenshot baselines, and manual screen-reader certification.

## Acceptance criteria

- [x] One-card and three-card paths each pass desktop and 320px mobile states, send only exact
      theme-only commands, use independent UUID-v4 operation keys, display the fixed expected
      cards/orientations/positions, and reveal without another request or redraw.
- [x] The interactive result states pass keyboard/focus, layout, 44px touch-target, reduced-motion,
      RTL/expanded/dark, and blocking axe checks, with deterministic screenshots for the stable
      one-card and three-card results.
- [x] Offline creation sends no session or reading request; a transient service failure exposes only
      manual same-key retry; and a rate-limit response provides a calm stop with no immediate retry
      or automatic request.
- [x] Refresh resume stores only the exact per-type UUID, performs only the owner-scoped no-store
      GET, returns to explicit reveal without redrawing, and removes a stale identifier after the
      private `404`.
- [x] One-card whole-reading and three-card canonical-position reports submit only the closed
      category/target request with an independent UUID-v4 key, no free text, no redraw, and exact
      empty `204` success behavior.
- [x] All browser traffic remains same-origin and allowlisted; storage contains no result text,
      question, report body, session token, or analytics payload. Screenshots contain only the
      reviewed synthetic fixture, and no private canary, credential-bearing trace, unexpected HTTP
      failure, page error, or console warning/error enters evidence.
- [x] Focused policy tests, production build, deterministic browser matrix, existing accessibility
      gate, formatting, lint, types, unit tests, architecture, configuration, database, generated
      evidence, records, migration, secret, and pack checks pass without weakening existing gates.

## Verification evidence

The existing production-artifact accessibility runner now contains six ordered M2 scenarios:
one-card report and refresh resume; three-card canonical-position report and refresh resume;
offline creation with explicit recovery; transient service failure with same-key manual retry;
rate-limit stop with previous-result preservation; and stale private-result clearing. A
zero-dependency policy audits exact theme-only bodies, empty anonymous-session bodies, request
counts, UUID-v4 operation keys, retry-key stability, cross-operation key independence, exact
closed report bodies, and zero unexpected or interpretation requests.

The browser matrix asserts the fixed one-card and ordered three-card presentations, zero
reveal-time requests, UUID-only per-type `sessionStorage`, GET-only restore, explicit no-redraw
reveal, stale `404` cleanup, whole-reading safety reporting, Action-position translation
reporting, keyboard and focus behavior, 44px targets, reduced motion, dark mode, 40% expansion,
desktop RTL mirroring, 320px reflow, blocking axe results, and same-origin-only traffic. It emits
supporting deterministic PNG captures under the ignored local
`output/playwright/rit028/` directory without changing owner-gated golden baselines.

Dynamic acceptance exposed two real browser defects and the implementation corrected both at
their source: resume transport now invokes a native-compatible `fetch` without an invalid object
receiver, and semantic `summary` controls receive the same visible focus ring as links and
selects. Dedicated transport coverage prevents the receiver regression, while the browser matrix
checks complete forward and reverse focus order including `summary`.

Final local evidence passes Prettier, ESLint with zero warnings, strict type checking across all
11 workspace packages, 1,478 unit/contract assertions in 106 files, 34 AI release cases with 145
assertions and no external or paid calls, the production build and 80-artifact verifier,
configuration-boundary validation, all 11 PostgreSQL migrations and foundation/identity/tarot
integration suites, and the production-artifact accessibility gate. The latter completes 39 axe
scans, retains 460 reviewed contrast nodes for the existing token/manual review, executes all six
new deterministic scenarios, writes two supporting screenshots, and records no unexpected local
or external browser request, HTTP failure, page error, console warning, or console error.

Independent review findings were resolved before closure: a separate new reflection must use fresh
session and reading operation keys; page readiness now waits for hydration, cleared busy states,
and two stable animation frames without reintroducing the unbounded `networkidle` wait; broad axe
selectors are guarded by exact Tarot-component scope and count limits; and screenshot evidence
requires exact PNG dimensions, no textual metadata, and no private-canary or credential-shaped
page text.

## Risks and rollback

The largest risk is overstating isolated deterministic fixtures as a publishable production tarot
catalog or as manual assistive-technology certification. A second risk is brittle visual evidence
that passes while behavior regresses or fails across pinned CI platforms. Behavioral, semantic,
request-ledger, layout, and privacy assertions therefore remain authoritative; screenshots are
bounded supporting evidence only.

Rollback removes the added browser matrix, screenshot generation, and CI wiring while retaining all
existing one-card, three-card, resume, report, accessibility, and safe-off product behavior. No
database, retained evidence, customer data, provider, payment, deployment, or production rollback
is involved.
