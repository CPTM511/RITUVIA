# RIT-020: Anonymous subject, session, and consent baseline

- Backlog item: RIT-020
- Related records: D-028, D-029

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

The Web can create or resume one privacy-minimal anonymous subject/session on the same device while
the database stores only an expiring token digest and append-only per-purpose consent history that
defaults to no optional consent.

## Scope

Included: framework-independent identity values and state transitions; 256-bit opaque session
tokens with SHA-256 persistence; fixed database-clock expiry and revocation; required versioned
session policy configuration; anonymous subject/session, consent-record, and global-capacity tables;
exact runtime database privileges with live attestation; idempotent concurrent creation; real exact
same-origin `POST /api/v1/anonymous/session`; host-only secure cookie issuance; server-side safe-off
feature gating; localized safe Problem Details; non-empty logical restore; and domain, configuration,
database, Web, build, and browser evidence.

Excluded: collecting email, IP address, user-agent, fingerprint, question, prayer, journal, birth,
or payment data; a consent or privacy-control UI; legal consent copy; choosing a production
retention period; account authentication/merge; private reading resources; analytics; per-client
abuse scoring; deletion/export; another locale; production activation/deployment; or destructive
schema/data changes.

## Acceptance criteria

- [x] Anonymous subjects and sessions use random opaque identifiers, token-digest-only persistence,
      fixed configured expiry, revocation, restrictive relationships, and no fingerprint/private
      content fields.
- [x] Optional consent is append-only per subject/purpose/notice version; denial, withdrawal,
      absence, stale notice, invalid history, and inactive sessions fail closed.
- [x] The exact API is same-origin, empty-body, idempotent, safe-off, non-cacheable/non-indexable,
      and returns no token or identity body; the cookie is host-only, Secure, HttpOnly,
      SameSite=Strict, Path=/, and fixed-expiry.
- [x] Runtime privileges permit only exact identity reads/inserts and lifecycle columns; owners,
      privilege escalation, DDL, deletion, consent mutation, and expiry/hash/ownership mutation are
      rejected at live attestation and by PostgreSQL.
- [x] Unit/mutation, architecture, format/lint/type, production/configuration build, real PostgreSQL
      migration/concurrency/restore, accessibility, and Playwright browser evidence pass.
- [x] Canonical specifications, migration policy, decision, task, queue, status, generated records,
      manual, and checksums reflect the implemented boundary and rollback.

## Risks and rollback

The bearer cookie can authorize future anonymous private resources until fixed expiry or revocation,
so every later endpoint must enforce subject ownership and avoid credential exposure. The global
capacity gate is deliberately privacy-minimal and can reject legitimate issuance during an attack.
The shared bounded pool removes per-request pool creation from both Web database paths, but catalog attestation still occurs before the
global gate, so production load/admission testing and an earlier abuse control remain release work;
this is not a complete production abuse system. Retention duration, legal notice, consent UX, deletion, merge,
and production activation remain separate tasks/gates.

Rollback by disabling session-policy configuration and route use and reverting application/role
grants while leaving the additive tables intact. Do not drop tables or delete rows; any destructive
forward migration requires backup/restore evidence, retention review, and explicit owner approval.
