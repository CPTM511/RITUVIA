# RIT-023: Deterministic server-authoritative tarot draw engine

- Backlog item: RIT-023
- Related records: D-031, D-032

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

The repository can turn a strictly validated exact-version tarot catalog and server-internal draw
command into immutable, ordered, unbiased, without-replacement draw facts, with bounded entropy,
safe idempotent replay, and a public projection that excludes internal audit fields.

## Scope

Included: exact V1 request/facts/execution/rules/engine/algorithm versions; canonical card and spread
order; partial Fisher–Yates selection; uint8 rejection sampling; one-card and three-card draws;
upright-only and balanced upright/reversed rules; injected CSPRNG contract; bounded commitment and
consumption audit; server-derived digest shapes; exact existing-execution validation; replay without
entropy; caller-injected execution verification; conflict detection; verified public fact
projection; fixed compatibility vector; property/boundary tests; build verification; and durable
decision/status evidence.

Excluded: an OS CSPRNG adapter, HTTP API, client input mapping, database persistence or migration,
concurrent transaction/unique-index behavior, reading limits, redraw policy, content publication or
activation, UI, AI interpretation, analytics, and deployment. Those remain RIT-024 or later work.

## Acceptance criteria

- [x] Exact, strict, immutable request, public-facts, internal-execution, rules, engine, and algorithm
      versions are exported without accepting card, orientation result, seed, entropy, or history in
      the request schema.
- [x] V1 performs canonical partial Fisher–Yates draws without replacement, uses bounded rejection
      sampling for every non-power-of-two bound, preserves spread order, and produces only supported
      orientations.
- [x] Fixed vectors and deterministic property tests prove one/three-card behavior, uniqueness,
      all deck bounds through 200, balanced orientations, exact byte consumption, rejection limits,
      input non-mutation, deep freezing, and historical parse/replay compatibility.
- [x] Matching existing execution replays exactly without entropy; changed key/request/rules/refs or
      damaged facts/audit fail closed through required execution verification and stable
      non-content-bearing codes. Durable keyed verification and concurrent idempotency remain
      explicitly assigned to RIT-024.
- [x] The explicit public fact projection contains no idempotency/request digest, entropy commitment
      or counts, raw bytes, question text, interpretation prose, analytics, or logging surface, and
      refuses unverified execution.
- [x] Package-focused type/tests, independent review, formatting, lint, architecture, full unit and
      applicable configuration-boundary integration, production build, records, generated evidence,
      and checksums pass; no UI, browser behavior, database change, or migration applies.
- [x] Backlog, project status, decision/task records, record index, compiled manual, and checksums
      reflect the final verified slice.

## Risks and rollback

The pure engine can validate an entropy interface but cannot prove that a future adapter uses an OS
CSPRNG. The audit commitment and execution verifier are caller-provided integrity boundaries, not a
fairness proof. RIT-024 must implement them with a keyed domain-separated binding across the
non-sensitive canonical request, exact facts, audit counts, and engine versions inside a server-only
adapter; raw entropy/key material, private questions, and client-derived digest values must never be
retained or logged.

This slice proves pure replay semantics, not database concurrency. RIT-024 must enforce owner-scoped
transactional uniqueness, same-key/same-request replay, same-key/different-request conflict, rollback,
and immutable storage under real races. It must expose only projected facts and must reject client
catalog/card/orientation/seed/entropy/history inputs.

The synthetic catalog remains internal-only and non-publishable. There is no migration, route,
runtime consumer, feature activation, user data, or deployment. Roll back by removing the draw
module, fixtures, tests, and build assertions. After persistence exists, V1 contracts must remain for
historical replay rather than recalculating stored facts.
