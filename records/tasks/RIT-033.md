# RIT-033: Structured generation, validation, fallback, and persistence

- Backlog item: RIT-033
- Related records: D-037, D-038, D-039, D-040

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

RIT-033 establishes a safe-off, provider-neutral orchestration boundary for bounded structured
generation, exact schema and deterministic-reference validation, real deadline and cancellation
handling, at most one safe retry, an independently authorized deterministic fallback, redacted
operational metadata, and owner-bound PostgreSQL claim/fencing persistence.

## Scope

Included: exact runtime-issued input, prompt, and pre-generation authorization binding;
server-owned provider/model registration and authority; provider-neutral structured request and
normalized-result validation; real per-attempt deadline and cancellation; bounded retry policy;
strict output-schema and deterministic fact/source/ritual-reference validation; runtime-issued,
checksummed, separately authorized deterministic fallback templates; fixed redacted operational
metadata; anonymous-owner-scoped interpretation claims; canonical request hashing; idempotent
replay and conflict handling; leases, fencing tokens, compare-and-set finalization, inherited parent
expiry, least-privilege database access, and additive migration evidence.

Excluded: a real provider or model, provider SDK, API key or other credential, network request,
paid inference, production prompt/content/template activation, post-generation prose/fabrication
verification, provider candidate display, API route, streaming or polling UI, another locale,
modality, or tradition, independent interpretation-retention duration, analytics/exporter
activation, deployment, public launch, payments, and destructive production migration work.

## Acceptance criteria

- [x] Orchestration accepts only the exact runtime-issued parsed input, prompt artifact, and opaque
      allowed authorization for that request, and independently verifies the exact server-owned
      provider/model registration and approval before constructing a provider request.
- [x] Provider requests are immutable and bounded; normalized responses require exact keys,
      successful completion, safe usage bounds, and the existing output parser's exact schema,
      fact, source, and approved-ritual bindings.
- [x] A host-enforced deadline cancels timed-out work, consumes late settlement without allowing it
      to replace the terminal result, and never starts an unsafe retry after an unacknowledged
      timeout.
- [x] Retry is limited to one additional identical request for an explicit finite allowlist of
      settled transient failures or one invalid structured response; trust, authority,
      registration, configuration, and persistence failures fail closed.
- [x] Fallback output is deterministic, schema-valid, and derived only from the exact branded facts
      and retrieved published content plus an exact checksummed and externally authorized template
      issued at runtime; there is no permissive or hardcoded production fallback.
- [x] Provider prose remains an in-memory, unverified, non-displayable candidate for RIT-034. Before
      that verifier, persistence stores only categorical generation status and approved provenance;
      only the independently authorized deterministic fallback may persist its validated output.
- [x] Operational metadata is a closed, recursively immutable allowlist of categorical outcomes,
      versions, locale/theme, attempt count, bounded latency/usage/cost fields, and failure codes;
      it contains no question, prompt messages, excerpts, generated prose, raw provider response or
      error, safety categories, session/reading/request identifiers, or arbitrary diagnostics.
- [x] PostgreSQL claims authenticate the active anonymous owner, bind the interpretation to the
      parent reading and its expiry, reject conflicting idempotency/request hashes, replay exact
      terminal work without another provider call, and protect finalization with lease and fencing
      compare-and-set semantics.
- [x] Expired in-progress work cannot create duplicate paid inference: a reclaimed claim is
      fallback-only unless a later independently reviewed provider contract proves stable external
      idempotency. Runtime roles have only the exact required interpretation operations and no DDL,
      ownership, broad mutation, or role-escalation path.
- [x] Focused AI, Web-composition, database migration/constraint/race/ownership/retention/restore,
      architecture, type, lint, compiled-workspace, and repository evidence gates pass while the
      runtime remains safe-off.

## Risks and rollback

The principal residual boundary is deliberate: structurally valid provider prose is not safe or
displayable until RIT-034 performs post-generation fact and safety verification. No runtime
provider/model mapping, key, network adapter, production content/template, API, UI, or paid usage
is activated by this task. Generation retention duration remains owner-gated; the database may
only inherit the already-bound parent reading expiry and does not approve a new retention policy.

The additive migration is not applied to production by this task. Before activation, rollback can
remove the unused orchestration, composition, persistence code, and unapplied migration. After a
production migration or stored interpretation exists, removal or destructive cleanup requires a
separate owner-approved forward-fix/rollback plan that preserves auditability and retained data.
