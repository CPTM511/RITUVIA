# RIT-123: Implement backups and isolated restore test

- Backlog item: RIT-123
- Related records: None
- Owner approval: repository-local and ephemeral CI backup/restore rehearsals with synthetic data
  are allowed; production infrastructure, credentials, customer data, retention, backup deletion,
  PITR activation, destructive migration, and production restore remain separately gated

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Create one automated, fail-closed PostgreSQL backup and isolated-restore rehearsal that produces
privacy-minimal integrity evidence, runs against exact synthetic local or GitHub Actions database
targets, and cannot be redirected to preview, staging, production, or an arbitrary database.

## Scope

Included: custom-format logical backup; exact source and isolated empty target guards; artifact
permissions, digest, non-empty and tamper checks; migration, schema, table-count, sentinel, and
least-privilege verification after restore; cleanup on success or failure; local ignored evidence;
CI enforcement; RPO/RTO and restore runbook documentation.

Excluded: production provider selection or provisioning, physical backup/PITR configuration,
customer or copied production data, production secrets, production restore, backup deletion,
retention activation, destructive migration, DNS, deployment, or public launch.

## Acceptance criteria

- [x] One command performs a complete logical backup and isolated restore against only an attested
      repository-owned local test database or the exact ephemeral GitHub Actions PostgreSQL target.
- [x] The source and target are distinct and synthetic; the restore target is empty and
      invocation-owned; production, preview, staging, arbitrary URLs, unsafe identifiers, and
      caller-selected output paths fail closed.
- [x] The temporary custom-format artifact is non-empty, mode `0600`, not a symlink, SHA-256
      verified before restore, and removed on success or failure.
- [x] Restore uses a non-superuser migrator in one transaction, then reapplies local runtime grants
      or restores exact CI ACL and reattests least privilege without weakening row security,
      append-only controls, or ownership.
- [x] Pre/post migration inventory, table inventory, row counts, synthetic sentinel, schema
      constraints, and idempotent migration deployment match after restore.
- [x] A bounded schema-versioned evidence report contains revision, PostgreSQL version, artifact
      digest/size, source/target identities, timings, checks, and cleanup result but no URL,
      password, private row, secret, SQL payload, or customer identifier.
- [x] The digest-pinned PostgreSQL CI job runs the rehearsal after database foundation verification;
      focused policy tests reject target drift, artifact tampering, evidence leakage, and cleanup
      failure.
- [x] Recovery documentation records the existing RPO/RTO targets, production encryption/PITR,
      access, retention, restore, audit, quarterly rehearsal, and owner gates without claiming
      standing production backup infrastructure.

## Risks and rollback

Logical dumps do not prove provider-managed physical backup or point-in-time recovery. This task
must label local/CI evidence as a synthetic logical rehearsal and keep production Gate H open until
the selected managed PostgreSQL service proves encrypted isolated backups, PITR, retention,
separate access, and an isolated provider-level restore for the exact production configuration.

Rollback removes the rehearsal scripts, CI step, and documentation references. Every rehearsal
must delete its invocation-owned source/target databases and temporary artifact; rollback never
drops a standing database, deletes a backup, changes retention, or mutates production.
