# RIT-027: Tarot limits, explicit new reflection, and categorical report control

- Backlog item: RIT-027
- Related records: D-033, D-034, D-035

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

One-card and three-card tarot flows now apply one server-authoritative reading limit, distinguish
same-operation retry from an explicit new reflection, preserve the last useful result during a new
attempt, and let an anonymous owner submit a durable category-and-target-only report without free
text, redraw, quota use, analytics, or cross-owner disclosure.

## Scope

Included: exact application/database limit-policy matching; database-clock atomic quota; bounded
`Retry-After`; no immediate limit retry; explicit post-result new-reflection transition; previous
result preservation; controlled theme reset; six exact report categories; whole-reading or
canonical-position targets; independent report idempotency; owner-bound append-only persistence;
inherited reading expiry; exact same-origin JSON route; safe private `204`/`404`/`409`/`503`
responses; proxy and safe-off runtime coverage; responsive, keyboard, RTL, forced-color, offline,
manual-retry, and screen-reader behavior; migration/least-privilege/restore evidence; and durable
decision, task, status, build, browser, and test evidence.

Excluded: production catalog activation, production limit selection, report triage or admin UI,
notifications, severity, support SLA, deletion/export orchestration, analytics, AI regeneration,
new artwork, accounts, payments, deployment, public launch, and any production migration.

## Acceptance criteria

- [x] Application startup fails closed if maximum, window, or reading-policy version differs from
      the persistence authority; the approved local baseline is three new readings per rolling
      hour, while matching replay is resolved before quota or entropy use.
- [x] A limit response is server-authoritative and bounded, presents a calm stop point without an
      immediate retry, and never removes the previously revealed result.
- [x] Retry reuses the existing session and reading idempotency keys; reveal makes no request; only
      the explicit post-result new-reflection action can create another operation.
- [x] New reflection returns to an actually empty controlled theme choice, keeps the old result
      until the new fixed result is revealed, and does not imply that another draw is more certain.
- [x] The report command accepts exactly six approved categories and either the whole reading or a
      canonical stored position; no free-text or private question/journal field exists.
- [x] Report create/replay is owner-bound, append-only, independently idempotent, quota-neutral,
      inherits the reading expiry, returns exact private status contracts, and cannot update,
      delete, own, or perform DDL on report rows through the runtime role.
- [x] Normal runtime remains unavailable until a separately approved publication-eligible tarot
      catalog exists; no synthetic fixture, production migration, deployment, or payment action is
      activated by this task.
- [x] Focused/full tests, strict types, formatting, lint, architecture, migrations, production
      build/budgets, configuration isolation, Chromium/axe, Playwright, record, generated-evidence,
      and secret gates pass or have an explicitly bounded environment note below.

## Risks and rollback

The production-shaped UI/API remains deliberately safe-off because no publishable tarot catalog is
approved. Browser success uses isolated deterministic responses and is not catalog-publication or
deployment evidence. The current shared gate also blocks historical read/report access when new
creation is disabled; separate operational kill switches are required before retained customer
readings exist. Report triage, privacy-rights orchestration, broader abuse controls, and production
limit selection remain later work.

Apply the expand-only migration before compatible application code in any future environment.
Before retained reports exist, rollback may remove the report UI/route/method and table. After
reports exist, keep the parser, digest verification, and records for their approved inherited
lifetime, disable new reporting through a reviewed forward gate, and never use destructive schema
rollback. Revert the controlled RadioGroup change only together with a replacement that explicitly
clears every checked radio when a controlled value becomes empty.
