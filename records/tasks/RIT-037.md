# RIT-037: Exact-version interpretation reporting

- Backlog item: RIT-037
- Related records: D-035, D-042, D-046

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Allow an owner to categorically report one exact, immutable, displayable Tarot interpretation
result without starting a new generation, changing deterministic reading facts or output, consuming
Tarot quota, exposing private generation evidence, or pre-empting the production Deep Reading and
Credits transaction model.

## Scope

Included: a backward-compatible strict report schema version; an exact interpretation operation
identifier resolved to its immutable interpretation row within the owner-scoped source reading;
displayable-result eligibility; strict
categorical reports without free text; inherited expiry; idempotency; append-only persistence;
database constraints and least privilege; safe empty/error/private-resource behavior; and contract,
persistence, API, security, restore, and database concurrency tests.

Excluded: history/list UI or API; `generationNumber > 1`; lineage/supersession changes; a
regeneration/start endpoint; a second provider attempt presented as a new purchased result; Credit
quote, reservation, consumption, release, expiry, reversal, or projection; Deep Reading
product/catalog behavior; account-history retention changes; a live provider, model, reviewer,
SDK, credential, network call, or paid inference; raw question/context persistence; analytics;
admin triage; production activation; migration of historical interpretation rows; deployment; and
public launch.

## Acceptance criteria

- [x] The existing reading/position report request remains compatible while one strict new request
      arm can target an exact interpretation operation identifier and rejects unknown fields, free
      text, malformed identifiers, unsupported targets, and oversized bodies.
- [x] Only an owner-scoped interpretation belonging to the exact source reading and containing a
      durable verified, safe-replacement, or authorized fallback result is reportable. Generating,
      failed, childless pending-verification, expired, unknown, cross-reading, and cross-owner
      targets return the same private-resource `404`.
- [x] The append-only report row binds the exact interpretation identifier, source reading, owner,
      categorical reason, policy/schema version, idempotency evidence, creation time, and inherited
      expiry. Database constraints reject target mismatch and prevent mutation.
- [x] Same-key same-request replay returns the same empty private `204`; same-key changed target or
      body conflicts; concurrent identical requests create exactly one report; and report creation
      does not change reading, interpretation, verification, quota, AI, payment, or Credit state.
- [x] Runtime roles receive only the exact new read/write columns required, logical restore
      preserves report replay, and no report response contains provider, reviewer, provenance,
      digest, claim, lease, token, cost, output, question, context, identity, or payment data.
- [x] No route or runtime in this task can start or regenerate an interpretation. The existing
      generation runtime remains hard safe-off, and paid regeneration remains deferred until a
      separately accepted Credits/Deep Reading transaction task can reserve, consume, or release
      Credits exactly once.
- [x] Contract, persistence, route, private-response, architecture, configuration, migration,
      database-foundation, unit, AI-eval, build, and relevant accessibility checks pass without
      weakening existing gates.

## Planned files and verification

Likely implementation areas are the existing domain report contract, `ReadingReport` persistence,
an expand-only exact interpretation target in `packages/db/prisma/`, the existing private Web
reading report runtime/API, and focused unit/database tests. The implementation must reuse
`POST /api/v1/readings/{readingId}/report`, preserve the current reading/position request, and adapt
the existing `Interpretation`, `InterpretationVerification`, and `ReadingReport` models rather than
introducing a parallel service or `deep_readings` history table.

Run focused contract and persistence tests first, then
`pnpm test:configuration-boundary`, `pnpm test:database-foundation`, `pnpm test:accessibility`,
`pnpm check:evidence`, formatting, lint, type checking, the full unit suite, AI release
evaluations, and the production build.

## Verification evidence

Task-entry review confirmed that the prior report contract supported only reading/position targets,
the interpretation persistence constrains generation number to one, the interpretation persistence
interface exposes claim/finalize rather than history/regeneration, and the ordinary Web
interpretation runtime remains hard safe-off.

The implementation now adds a strict `tarot-reading-report.v2` arm whose UUID-v4
`interpretationRequestId` is the browser-held interpretation operation identifier. Persistence
resolves that identifier inside the exact owner/reading/expiry boundary, accepts only durable
verified, safe-replacement, or authorized fallback results, and stores only the resolved immutable
interpretation primary key plus parent/verification status evidence. The old v1 request and storage
envelope remain intact. One additive migration introduces composite target keys, nullable exact
target columns, CHECK constraints, and two restrictive composite foreign keys without rewriting
historical rows.

Final evidence passes 1,465 unit/contract assertions in 105 files, 34 AI release cases with 145
assertions and no external or paid calls, migration policy for 12 immutable files, Prisma
validation, architecture, formatting, lint, type checking, secret scanning, the production-pack
verifier, and all 11 production build tasks. The browser acceptance ledger submits strict v2
reports for both verified and reviewed-fallback results and requires the exact interpretation
operation identifier with no free text.

## Dynamic verification

The unrestricted local environment executed all three authoritative dynamic gates without
production access or paid services. `pnpm test:configuration-boundary` passes typed environment
parsing, fail-closed startup, server-only imports, and client secret isolation.
`pnpm test:database-foundation` applies all 11 migrations and passes owner/reading scoping,
displayability, eight-way report races, changed-key conflicts, immutable state, exact privileges,
negative constraints, and non-empty logical restore/replay. That run exposed and corrected a real
PostgreSQL CHECK weakness where `NULL IN (...)` evaluated to unknown; pending-verification report
targets now require an explicitly non-null verified or safe-replacement child.
`pnpm test:accessibility` passes four public and three private routes with 31 axe scans, complete
keyboard/RTL/reflow/offline coverage, and verified plus reviewed-fallback interpretation report
submissions. That run also exposed and corrected an invalid native `fetch` receiver in the report
transport; a dedicated receiver regression test now prevents recurrence.

## Risks and rollback

The primary risk is binding a report to an interpretation from another owner or reading, accepting
a non-displayable result, or leaking output/provider evidence while resolving the target. A second
risk is treating this exact report target as a future Deep Reading lineage model. The implementation
must therefore resolve ownership and displayability atomically, keep start/regeneration/history
absent, and preserve the existing private empty response.

Rollback disables the new request arm and removes unused contracts/grants through a forward
migration while preserving any already-created immutable report evidence according to the
repository migration policy. Destructive row deletion, retention changes, Credits mutation,
provider activation, and production rollback remain separate owner gates.
