# RIT-026: Private three-card tarot reflection flow

- Backlog item: RIT-026
- Related records: D-034

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

The repository now contains a private, accessible, mobile-first Situation/Action/Possibility flow
that creates or resumes an anonymous session, requests one server-authoritative three-card draw,
reveals the already fixed ordered cards, and presents reviewed limitations, reflection questions,
and small actions without AI, account, payment, raw-question transfer, analytics, or redraw
behavior.

## Scope

Included: exact private route and metadata; ten-theme choice; no-JavaScript safe state; separate Web
Crypto idempotency keys; cancellable session/read transport; manual same-key retry; conflict-only
start-over; strict three-card V2 fact/presentation parsing; exact Situation/Action/Possibility order
and unique-card enforcement; explicit reveal; loading/offline/session/conflict/limit/unavailable/error
states; responsive, RTL, dark, reduced-motion, forced-color, keyboard, focus, touch-target, and
screen-reader behavior; shared catalog safe-off routing; build and browser evidence; and durable
status/task records.

Excluded: production catalog publication or activation, real card artwork, raw intake-question
consumption, AI interpretation or spread synthesis, user-visible redraw, report/share,
intention/ritual continuation, analytics, offline caching, account/payment behavior, database or
migration changes, deployment, and public launch.

## Acceptance criteria

- [x] An anonymous mobile user can select one of ten reviewed themes and reach a useful ordered
      three-card result with Situation, Action, and Possibility positions, unique cards, reviewed
      limitations, reflection questions, and one small action per position.
- [x] The browser sends only the exact theme-only V1 command, never controls cards, orientation,
      order, or content, and rejects malformed, oversized, extra, mismatched, duplicated, or
      incorrectly ordered three-card V2 responses.
- [x] Session and reading commands use distinct UUID V4 idempotency keys; explicit retry preserves
      them, conflict requires start-over, and reveal performs no request or redraw.
- [x] Page, API, framework representations, query variants, caching, metadata, and normal runtime
      fail closed behind the same approved-catalog gate; the synthetic fixture is never activated.
- [x] Loading, validation, offline, session, conflict, limit, service, generic error, ready, replay,
      revealed, mobile, no-JavaScript, dark, RTL, expanded-text, forced-color, and reduced-motion
      behavior have automated or browser evidence.
- [x] Focused/full tests, strict types, formatting, lint, architecture, production build/budgets,
      Chromium/axe, Playwright, configuration, record, generated-evidence, and secret gates pass.
- [x] Backlog, project status, task record, record index, compiled manual, and checksums reflect the
      final verified slice; no new product decision or ADR was required.

## Risks and rollback

The UI and server projection are production-shaped, but no production tarot catalog or artwork is
approved; normal runtime therefore remains deliberately unavailable. Browser success uses an
isolated intercepted eligible response and is not evidence that the synthetic placeholder is
publishable. At 320px the complete result is intentionally linear and readable but long; broader
cross-spread summarization and visual polish must not obscure limitations and remain future work.
RIT-027 still owns limits/redraw/report UX, and RIT-028 owns the combined one/three-card deterministic
E2E matrix.

No database schema, production state, customer data, analytics, AI, payment, deployment, decision,
or owner gate changed. Roll back by removing the three-card page, message/component wrapper, exact
proxy allowlist entry, and reading-type generalization while retaining the RIT-025 one-card consumer
and the RIT-024 API. Retain stored historical facts and use the runtime gate for operational rollback.
