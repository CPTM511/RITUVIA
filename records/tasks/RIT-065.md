# RIT-065: Entitlement Fulfillment and Purchase Restoration

- Backlog item: RIT-065
- Related records: D-092

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Consume verified Test Mode payment-state outbox rows through a dedicated least-privilege worker,
grant purchased Credit packs exactly once, apply source-linked dispute/refund adjustments without
negative balances, and privately restore the authenticated owner's purchases.

## Scope

Included: Stripe Test Mode `credit_pack` fulfillment only; ordered outbox leasing/retry/dead-letter
handling; serializable current-order convergence; append-only purchased-Credit grants, dispute
holds, hold-to-refund conversion, and direct refund reversals; consumed/reserved shortfall review;
a rebuildable fulfillment projection; owner/source composite constraints; a dedicated fulfillment
database role and required DSN; authenticated no-store Credit restoration; privacy export; and
focused domain, worker, Web, configuration, privilege, migration, and PostgreSQL evidence.

Excluded: Stripe Live Mode; refund initiation; currently unsupported provider refund/dispute route
activation; subscriptions; Plus/permanent/consumable paid entitlement delivery; reconciliation;
production migration; deployment; DNS; and public launch.

## Acceptance criteria

- [x] Only current verified paid/refunded/disputed order authority can create fulfillment effects.
- [x] Non-settlement outbox states complete with zero fulfillment and cannot block a later paid
      version for the same order.
- [x] Concurrent or duplicate delivery creates one purchased-Credit grant per order.
- [x] A dispute freezes only unspent source Credits; a refund converts holds and reverses remaining
      available source value without a negative projection.
- [x] Reserved or consumed source value creates a durable `review_required` shortfall.
- [x] Outbox versions process in order with bounded lease, stale-token denial, retry, and
      dead-letter behavior.
- [x] Webhook and fulfillment roles are distinct; webhook cannot complete jobs or access Credits,
      fulfillment cannot access payment-event/private-content evidence, and neither can update
      append-only ledger facts.
- [x] Authenticated restoration is owner-scoped, private/no-store, and excludes held Credits from
      spendable total; privacy export includes the new evidence.

## Risks and rollback

Primary risks are double issuance, stale-state fulfillment, cross-account source linking,
misclassifying disputes as refunds, negative balances, and a privilege bridge between ingestion
and value issuance. Unique/composite constraints, ordered claims, serializable convergence,
append-only evidence, source accounting, nonnegative projections, and exact-role runtime
attestation control those risks. New Credit allocations require one owner across the reservation
and source grant; a pre-existing unbound allocation fails fulfillment closed rather than being
silently rewritten.

Rollback stops the fulfillment worker and removes its DSN. Existing payment outbox, Credit,
restriction, fulfillment, and shortfall evidence remains retained. Rollback does not delete
records, mutate customer funds, initiate a provider refund, or activate another payment path.
