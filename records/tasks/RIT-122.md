# RIT-122: Implement rate limits, bot defense, abuse and denial-of-wallet controls

- Backlog item: RIT-122
- Related records: D-033, D-035, D-040, D-041, D-042, D-100

The queue state, priority, milestone, dependencies, and owner gates remain canonical in

## Outcome

Make the approved English, anonymous, free, protected closed-Beta journey resist scripted request
bursts and resource exhaustion without collecting raw questions, IP addresses, user agents, device
fingerprints, or other new sensitive profiling signals, while preserving calm recovery and exact
idempotent behavior for legitimate testers.

## Scope

Included: inventory the reachable Beta entry and mutation surfaces; preserve and verify existing
database-atomic anonymous-session, authentication, Tarot, privacy-export, privacy-deletion, ritual,
body-bound, idempotency, and owner-scope controls; add only the smallest durable admission control
needed for a reproducible uncovered Beta path; return bounded `429` plus `Retry-After`; fail closed
when admission authority is unavailable; prove concurrency, bypass resistance, privacy-minimal
storage, normal-flow recovery, and production-artifact behavior; record excluded retained endpoints
as safe-off or future-gated rather than pretending they are active.

Excluded: deployment, public or Beta launch, production data or credentials, managed edge/WAF or
CAPTCHA activation, IP-prefix/device-risk collection, invasive fingerprinting, payment or crypto
activation, production AI, astrology, new locales/countries, support/admin product expansion,
pricing/legal changes, destructive migration, golden screenshot updates, and broad rewrites.

## Acceptance criteria

- [x] Every approved Beta entry/mutation and retained expensive/auth/checkout/support/privacy surface
      is mapped to an active limit, bounded domain topology, safe-off control, or explicit later gate.
- [x] Any uncovered reachable Beta path receives database-atomic or equivalently durable admission
      before expensive work, bound only to an existing pseudonymous session/owner or a documented
      privacy-minimal aggregate.
- [x] Limits resolve legitimate replay before charging where applicable, reject concurrent over-limit
      requests deterministically, return bounded `Retry-After`, and never offer an immediate retry.
- [x] Missing or drifted limit configuration and unavailable admission storage fail closed without
      exposing private input, identifiers, internal errors, or sensitive telemetry.
- [x] No raw question, journal, intention, birth data, email, IP, user agent, device fingerprint,
      provider secret, or arbitrary abuse attribute is stored or emitted to logs/analytics.
- [x] Focused unit, route, configuration, database race/privilege/restore, browser normal/degraded,
      architecture, build, record, generated-evidence, and secret gates pass under exact Node
      `26.5.1` and pnpm `11.13.1`.
- [x] Backlog, project status, security/threat documentation, user/Owner launch guidance, durable
      records, generated manual, and checksums agree on the result and next single eligible task.

### New durable boundary

Migration `202608010001_anonymous_session_rate_limit` adds one fixed-row table with a closed two-value
scope constraint and maximum two rows per session. Runtime may read and insert exact columns and
update only window/count/policy provenance; it cannot rewrite ownership/scope, delete, truncate,
create schema, switch role, or reach privileged memberships. D-100 records that the request budget
counts HTTP admission attempts, including exact idempotent retries, while domain idempotency still
prevents duplicate state and endpoint-specific quotas preserve their own replay semantics.

## Risks and rollback

The primary safety trade-off is blocking a legitimate invited tester versus leaving a cheap path for
scripted exhaustion. Controls must use calm, bounded recovery and existing pseudonymous authority,
not hidden profiling. Aggregate pre-session limits can be exhausted by one attacker, while
per-session limits can be bypassed by session farming; the existing database-atomic issuance cap and
future OWN-019/RIT-130 invite and protected ingress must remain explicit complementary controls.

The local 12/minute and 120/day values are acceptance defaults, not production policy. Production
must reject a policy version that does not reference `own-019.`. OWN-019 remains Blocked pending the
exact thresholds, cohort assumptions, edge/allowlist controls, observation window, and rollback
criteria. RIT-121's standing staging, DAST, independent penetration, non-Chromium/manual-AT, CSP,
and exact Beta route-profile gaps also remain release evidence rather than local passes.

Rollback disables the new admission policy or reverts its application/route changes while retaining
any expand-only table for a forward fix when evidence may exist. It must not drop records, weaken
existing anonymous-session/Tarot/privacy limits, expose private input, restore frozen features, or
perform a production action.
