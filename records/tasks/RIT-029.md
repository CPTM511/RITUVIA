# RIT-029: Private same-session tarot result resume

- Backlog item: RIT-029
- Related records: D-036

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

One-card and three-card tarot results can now be restored after a refresh in the same browser tab
using only a strict UUID V4. Restore reads the same owner-bound immutable result, returns to an
explicit reveal step, never creates a new session or draw, and never stores private result or
question text in browser storage.

## Scope

Included: per-reading-type `sessionStorage` keys; strict UUID validation; store-after-response
validation; exact credentialed no-store owner GET; reading ID/type binding; explicit restored
reveal; definitive-clear versus transient-retain behavior; manual retry; storage-denied degraded
state; opener-cloned storage rejection; previous-result preservation during a new attempt;
expired-reading exclusion; private
equal-shape errors; RSC/prefetch/cross-origin rejection; responsive and accessibility behavior;
tests, browser evidence, decision/status records, and bounded build-budget accounting.

Excluded: full-response caching, private text storage, `localStorage`, IndexedDB, Cache Storage,
service workers, cross-tab/cross-device sync, account history, production catalog activation,
production retention or logging changes, migration application, deployment, public launch, AI,
rituals, accounts, and payments.

## Acceptance criteria

- [x] Browser storage contains only one strict UUID V4 under a fixed key for each reading type; no
      theme, card/result text, question, session, report, timestamp, or analytics payload is stored.
- [x] A tab with a live opener clears the current reading-type key before reading inherited
      `sessionStorage`, so opener cloning cannot trigger a cross-tab owner GET.
- [x] A validated ID performs one exact owner-scoped `GET`; strict ID/type/content validation must
      pass before the result reaches an explicit ready-to-reveal state.
- [x] Reveal is presentation-only and creates no API request; refresh restoration creates no new
      anonymous session or tarot draw.
- [x] Invalid IDs and definitive private `404` responses remove the stored ID; offline and
      dependency failures retain it and expose only explicit manual retry or dismiss behavior.
- [x] Starting a new reflection keeps the last recoverable ID until a different fixed response
      validates; storage denial never prevents the current result from remaining useful.
- [x] Owner retrieval excludes individually expired readings and preserves indistinguishable
      unknown, cross-owner, revoked/expired-session, and expired-reading behavior.
- [x] One-card and three-card paths pass strict tests and production-browser restore/no-redraw
      acceptance; 320px layout has no horizontal overflow.
- [x] No migration, retention change, runtime activation, catalog publication, deployment, or
      payment action is performed.

## Risks and rollback

Normal runtime remains deliberately safe-off until an approved production catalog exists. A UUID
in a private path remains sensitive metadata for future edge/access-log policy even though it is
not a bearer secret. The shared tarot gate still couples new creation and historical reads; split
kill switches are required before customer readings are retained. Offline result caching,
cross-device history, account merge, and payment access are not implemented.

Rollback can remove the storage adapter and restore state/transport while retaining the stricter
owner GET expiry predicate. Existing tab-scoped IDs become inert and expire with their tabs; no
database cleanup or destructive migration is required.
