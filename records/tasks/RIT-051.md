# RIT-051: Idempotent anonymous-to-account merge

- Backlog item: RIT-051
- Related records: D-029, D-051, D-052, D-053

The queue state, priority, milestone, dependencies, and owner gates remain canonical in
[BACKLOG.md](../../BACKLOG.md).

## Outcome

Complete the existing anonymous-ownership bridge so account conversion preserves one immutable
history exactly once under concurrency, leaves no partial authentication or ownership state when
the merge transaction fails, and produces privacy-minimal durable audit evidence.

## Scope

Included: reuse of immutable `anonymous_subject_id` ownership and the unique
`account_subject_link`; one database transaction for challenge consumption, account/session
creation, optional anonymous merge, and anonymous-session revocation; account-session rotation
after an explicit post-login merge; same-account replay and cross-account conflict behavior;
append-only link audit evidence containing opaque identifiers and hashes only; focused service,
route, database, concurrency, rollback, authorization, and browser verification; and current
identity/data/security/API/test documentation.

Excluded: copying or rewriting every private row to `user_id`; account history/settings UI owned by
RIT-052; export/deletion workflows; analytics identity stitching; production email, OAuth,
WebAuthn, wallet identity, deployment, retention changes, destructive migration, and golden
screenshot changes.

## Acceptance criteria

- [x] Authentication completion and anonymous merge commit or roll back together, so a merge
      failure does not consume the challenge or create an account/session/link.
- [x] Explicit post-login merge atomically creates or replays the unique ownership link, revokes
      anonymous sessions, rotates the account session, and never exposes either bearer in storage
      or response bodies.
- [x] Concurrent same-account requests preserve one link and one history; a different account
      cannot claim an already-linked anonymous subject or reuse another merge key.
- [x] Durable merge evidence is append-only, owner/subject/session scoped, hash-only for request
      material, and remains sufficient to reconstruct the successful ownership transition.
- [x] Focused unit, route, database, browser, architecture, migration, secret, type, lint, and
      formatting gates pass without running the unrelated complete workspace unit suite.

## Planned files and verification

Primary areas are `packages/db/src/account-identity.ts`, focused database and service tests,
`apps/web/server/account-auth.ts`, authentication completion/finalization and merge routes, focused
route/browser tests, and current identity/data/security/API/test records.

Run the narrow account identity and auth route tests first, then the dedicated PostgreSQL merge
gate and account-auth browser gate. Close with affected formatting, linting, type checking,
architecture, migration, CI-contract, secret, record, generated-evidence, and checksum checks. The
complete unrelated workspace unit/browser matrix remains reserved for RIT-057 or another milestone
integration trigger.

## Risks and rollback

Main risks are cross-account subject theft, duplicate history, challenge consumption before merge,
session fixation, lost-cookie failures after session rotation, bearer leakage, and an audit row
that can be altered. Rollback restores the previous application composition while leaving existing
unique link rows intact; no production data deletion, retention change, provider activation, or
deployment is authorized.
